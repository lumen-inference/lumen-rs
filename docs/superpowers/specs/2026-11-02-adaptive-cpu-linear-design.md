# Adaptive CPU linear execution

The executor must work efficiently with the resources available to its own worker pool. A CPU name or the result measured on the development machine must not select an execution strategy. The existing shared LLVM arithmetic remains the portable kernel description; this change selects how to execute it.

## Selection and learning

`LinearPolicy::Adaptive` becomes the executor default. `LinearPolicy::Fixed` explicitly retains the previous dispatcher for controlled comparisons and applications that cannot accept learning latency. `CpuExecutor::with_linear_policy(self, policy) -> Self` selects this policy without changing the configured pool, ISA, weights or numerical contract.

The adaptive selector compares caller execution, half the verified physical group, the full physical group, and the configured logical group when distinct. Without verified topology it compares half and all configured workers. Duplicate plans and plans exceeding the number of outputs are removed. GEMV additionally compares ordinary and streaming arithmetic, including single-worker execution. Native scalar has only ordinary arithmetic. Explicit one-worker Required affinity still executes on its owned worker.

At construction the adaptive selector records the minimum of four empty submissions using the actual joined pool path. This is an estimate of handoff cost, not a bandwidth benchmark. There are no startup matrices. For each exact shape (rows, output width, reduction depth), arithmetic backend and ISA, a safe initial plan uses the full physical group if available, otherwise all configured workers. Known aggregate LLC capacity selects the initial GEMV mode when weights exceed twice that capacity; unknown capacity starts with ordinary arithmetic. No minimum worker count applies to streaming. One-output and no-pool cases start serially.

Only genuine validated calls supply timings. Each call computes its result exactly once, using one candidate. Up to eight distinct candidates receive three consecutive genuine calls each: the first establishes that candidate’s own placement and cache state, and the next two contribute timings. A candidate replaces the initial resource hint only when both usable timings are shorter than the hint’s best timing. Among such candidates, the smallest slower timing wins, with the faster timing breaking ties. Otherwise retain the hint. This is a conservative consistency guard, not a statistical confidence interval; marginal wins can be missed. The total is at most 24 calls; no duplicate calculations occur. Caller execution is explored only when a parallel observation predicts serial arithmetic within eight estimated handoff costs: max(elapsed - handoff, 0) * workers <= 8 * handoff. This bounds exploration of obviously expensive serial GEMM; it is an estimate, not a latency guarantee. No timers are read once a shape has converged. A fixed 32-slot direct-mapped cache bounds metadata; collisions replace learning state. A tiny atomic fingerprint/plan fast path may confuse hash collisions only as a performance hint: cached plans contain no pointers or extents and always resolve against the current executor. Concurrent learners never wait for the learning lock: they execute the safe initial plan. No weights or user pointers enter the cache. No heap allocations occur during linear calls. Failed validation never trains or changes output.

The policy does not periodically re-learn stable entries. Changing load, different memory placement, and cold versus warm matrices of identical shape can change the best choice; reconstructing the executor resets learning. This limitation and the finite warm-up budget must be documented. Fixed policy is available when measurements cannot represent subsequent calls. Measurements may choose fewer workers than configured, but cannot create extra workers or mutate caller affinity. On unbound Rayon pools the selected count limits parallel tasks; the OS chooses the physical CPUs.

## Boundaries

Keep selection separate from arithmetic and output partitioning. A cached plan selects only serial/group/worker count and streaming mode. Every invocation recalculates checked rectangles from its current inputs. Existing compiled vector and register geometry remains target-derived. This work does not add per-CPU algorithm copies, a runtime compiler, full weight packing, hardware-model tables, instruction probing inside loops, or SIMD settings stronger than the explicitly requested ISA.

Maintain Rust 1.89, optional build-time LLVM, no new runtime dependencies, no caller affinity changes, and the checked dense-f32 contract. Read-only input aliasing, strided worker outputs, tails, bias, zero rows and IEEE exceptional values remain supported. Adaptive metadata must be thread-safe and recover safely from concurrent calls and poisoned learning locks.

## Proof

Synthetic observations test decisions on 1/2/4/8-worker resources, SMT groups, unknown caches, ties, finite learning, direct-map replacement and concurrency. These are policy tests, not measurements of other CPUs. Arithmetic tests exercise each real plan and compare the reference with tolerances. Validate both arithmetic backends, both x86 ISAs when available, default/no-LLVM build, and ARM cross/QEMU correctness. Restricting affinity on the development CPU tests resource constraints, not another microarchitecture. Publish a small bounded before/fixed/adaptive benchmark set in TFLOPS, including tiny calls, cached and streaming GEMV, and prefill. No claim of universal physical saturation follows from these results.
