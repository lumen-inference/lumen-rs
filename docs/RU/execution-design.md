# Подготовка и исполнение на CPU/Vulkan

[English](../EN/execution-design.md)

Термины из этого документа собраны в [глоссарии](glossary.md).

**Статус: проект исполнения.** Документ уточняет [архитектуру](architecture.md). Готового Vulkan runtime он не описывает. Прежде чем принять любое ускорение, нужно проверить результат вычислений, время жизни ресурсов и полную задержку выполнения.

## Общий исполнитель и подключённые бэкенды

Runtime работает с подготовленными заданиями и их зависимостями. Он не выбирает способ выполнения по имени CPU, Vulkan или будущего бэкенда. Таблица функций устройства отвечает за запуск и завершение; её контракт описан в [backends.md](backends.md).

Общий план определяет размещение, время жизни данных и передачи между устройствами. Бэкенд готовит собственные кернелы и выполняет необходимые зависимости внутри своего устройства. Для совместной работы разных бэкендов базовый путь использует ограниченные буферы RAM. Прямой обмен и общее отображение памяти — необязательные ускорения с отдельно проверяемой поддержкой.

Передача данных, изменение раскладки и перенос состояния должны быть запланированы до запуска. Отказ одной операции во время шага не разрешает незаметно переключить её на CPU. Если смешанный план допускается настройками, все его устройства и передачи видны в отчёте подготовки.

## Что движок готовит до первого шага

До окончательного выделения памяти подготовка запрашивает поддержку конкретных операций у разрешённых устройств. В пределах бюджета подготовки выбираются реализации, размещение, раскладки, явные преобразования и передачи. Бэкенд может поддерживать часть операций, но план целой модели должен покрывать их все.

Часть сведений о вычислениях не меняется от шага к шагу. Для этой части графа заранее сохраняются выбранные функции ядер, постоянные размеры тензоров, раскладки весов, диапазоны работы потоков, смещения и необходимый объём scratch. Во время исполнения эти решения не нужно принимать заново.

Неизменные веса упаковываются один раз. После подготовки исходное представление можно освободить, если оно больше не нужно, но это освобождение должно быть явным. Если для работы нужны и исходное, и подготовленное представления, в бюджет памяти входят оба.

Подготовленные веса связаны с владельцем и версией исходных данных, устройством, реализацией и форматом упаковки. Разделять представление можно только при совместимости этих признаков. Для каждого сеанса или одновременно работающего слота заранее резервируются изменяемые параметры, команды, объекты завершения и рабочая память.

Длины последовательностей, batch и маршруты MoE могут меняться. Для них план содержит шаблоны с заранее заданными пределами, а перед шагом заполняются только необходимые параметры. В обязанности ядра не входит поиск полей JSON, повторная проверка постоянных дескрипторов или повторное вычисление всей геометрии каждым рабочим потоком.

CPU-пул получает уже подготовленные диапазоны работы. Отдельно измеряются время публикации задания, начала работы потоков, арифметики и завершения. Несколько операций можно объединить в одно задание, если их зависимости сохраняются. Завершение каждого блока само по себе не требует нового барьера.

## Первый совместный путь для GPU и CPU

Общий маршрут — устройство A → согласованное представление в RAM → устройство B. Каждый бэкенд реализует свои передачи в память хоста, поэтому отдельный адаптер для каждой пары бэкендов не нужен. Копирование байтов не меняет раскладку: подготовка должна объявить поддержанную упаковку или распаковку, а при её отсутствии отклонить размещение. В бюджет входят закреплённая staging-память, одновременно выполняемые передачи и фактические добавки выделения. Прямые передачи и импорт внешней памяти требуют отдельной проверки совместимости.

Первый гибридный путь рассчитан на маршрутизируемых экспертов, которые выполняются на CPU. Часть вычислений остаётся на GPU, поэтому нужно точно определить, когда данные готовы для следующего участника:

1. GPU вычисляет маршруты и нужные входные данные, затем копирует их в staging-память, доступную хосту.
2. CPU дожидается подтверждения, что GPU закончил запись, и обеспечивает видимость этих данных. Только после этого рабочие потоки CPU вычисляют выбранных экспертов.
3. CPU завершает свои записи и при необходимости выполняет `flush`. Результат передаётся GPU. Зависимый `dispatch` должен дождаться этой передачи.
4. Слот staging можно использовать повторно только после завершения последнего потребителя его данных.

Для управления такими слотами нужно знать, какая именно незавершённая работа их использует. Одного номера слоя недостаточно: он не заменяет идентификатор конкретной работы.

Первый вариант может использовать fences для ожиданий хоста, binary semaphores для зависимостей между очередями и необходимые memory barriers. Timeline semaphores остаются дополнительным вариантом, а не обязательным условием первого бэкенда. Этот вариант допустим, когда соответствующая возможность Vulkan 1.2 или `VK_KHR_timeline_semaphore` проверена и включена. См. [описание timeline semaphores](https://docs.vulkan.org/refpages/latest/refpages/source/VK_KHR_timeline_semaphore.html).

Memory barriers должны соответствовать реальным чтениям и записям в связанных операциях. При передаче ресурса между разными queue families нужно учитывать владение им.

Наличие отдельной transfer-очереди ещё не означает, что копирование пойдёт параллельно вычислениям. Это проверяется на конкретном устройстве. План зависимостей нельзя заменять отправкой работы на GPU и ожиданием всей очереди после каждой операции.

Внутри устройства используются средства синхронизации бэкенда, а общие объекты завершения отслеживают нужные группы работ. Не требуется отдельное ожидание fence на CPU после каждой операции. Потребитель другого бэкенда ждёт производителя и нужных передач; убрать ожидание CPU через прямую синхронизацию можно лишь после проверки её поддержки.

## Когда CPU и GPU обращаются к отображённой памяти

Свойство `HOST_VISIBLE` разрешает отображение памяти, но не гарантирует, что доступ к ней будет самым быстрым для CPU или GPU. Поэтому одного этого свойства недостаточно для выбора способа передачи данных.

Для некогерентной памяти нужны корректные диапазоны `flush` и `invalidate`, рассчитанные с учётом `nonCoherentAtomSize`. Когерентная память позволяет обойтись без соответствующих операций управления кэшами. При этом по-прежнему нужны ожидания завершения работы и правильно заданные зависимости. Ни C-атомик, ни `volatile` не заменяют протокол Vulkan. Подробности закреплены в [спецификации памяти Vulkan](https://docs.vulkan.org/spec/latest/chapters/memory.html).

На UMA иногда можно избежать копирования данных. Такой путь выбирается по свойствам памяти и результатам измерений. Общая физическая память сама по себе не доказывает, что выбранный способ доступа будет быстрее.

Для дискретного GPU тоже можно рассматривать прямое чтение host-visible памяти вместо копирования в device-local. Это отдельный вариант, который требуется проверить. Разреженность вычислений сама по себе не делает его предпочтительным.

## Какие команды можно использовать повторно

Вычислительные конвейеры и постоянные дескрипторы готовятся заранее. Буферы команд разрешено использовать повторно только при совместимых привязках ресурсов и параметрах. При этом изменяемые данные и слоты сохраняют собственные времена жизни: готовая команда не даёт права перезаписать память, которую ещё использует другая работа.

Повторное использование Vulkan-команд не называется CUDA Graphs. Оно также не обещает тех же возможностей обновления команд.

## Завершение шага, отмена и ошибки

Первый публичный шаг будет синхронным, хотя внутри него разрешено асинхронное исполнение. К моменту возврата результата должны быть готовы и выход, и состояние сеанса. Использованные заимствованные области памяти к этому времени больше не должны быть нужны устройству.

Принятие задания и его успешное завершение — разные события. Если ошибка обнаружена после частичного запуска, бэкенд всё равно возвращает объект завершения для принятой работы. Runtime сохраняет её ресурсы, пока они используются. Отказ до принятия означает, что ничего не запущено и заимствованные данные не удерживаются.

Завершённый объект сообщает итоговый статус и окончание заимствований. Он сам по себе не делает данные GPU доступными CPU: необходимые передачи и операции видимости остаются явными. `poll` проверяет состояние без ожидания, `wait` ждёт нужную работу вместо остановки всех устройств. Объекты и слоты сохраняются до последнего пользователя.

При отмене движок прекращает ставить будущую работу и дожидается уже поставленной. Только после этого можно освобождать используемую память. Нельзя считать отмену разрешением немедленно освободить буфер, к которому ещё обращается CPU или GPU.

Отмена до принятия первой работы шага сохраняет прежнее состояние сеанса. В первой версии отмена после принятия работы требует явного `reset` перед продолжением; частичный шаг не откатывается автоматически. Runtime фиксирует один итог: поздняя отмена после успешного завершения не отменяет готовый результат.

Device loss и ошибка CPU переводят сеанс в определённое ошибочное состояние. Частично записанное состояние не считается успешно полученным токеном. Правила дальнейшего обращения с сеансом описаны в [контракте API](api.md).

При потере устройства применяется процедура остановки и освобождения бэкенда. Ресурсы не переиспользуются, пока их безопасное освобождение не подтверждено.

## Диск и состояние последовательности

Для дисковых таблиц используется ограниченная staging-область. У загруженных данных должен быть явно указан первый потребитель, чтобы чтение с диска было связано с дальнейшими вычислениями.

Базовые операции чтения и отображения файлов должны переноситься между ОС через `platform/`. Специализированный async I/O добавляется по результатам измерений. При измерении диска нужно учитывать файловый кэш: попадание в него не является холодным чтением NVMe.

Окно внимания, откат speculative-токенов и общие префиксы требуют явных правил владения страницами и фиксации состояния. Пока эти правила не реализованы, достаточно корректно работающего последовательного сеанса. До включения каждой такой возможности в бюджет памяти должны войти необходимые резервы истории, снимков и временных данных.

## Как проверять дальнейшие ускорения

Для fusion, overlap, изменения разбиения работы и новых способов ожидания нужен воспроизводимый baseline. С ним сравниваются p50 и p99 полной задержки, расход памяти и корректность отмены.

Высокая доля CPU-сэмплов в ожидании не означает, что такую же долю полной задержки можно убрать. Часть ожиданий может быть необходима из-за зависимостей. Точно так же выводы по машинному коду не заменяют измерение фактического выигрыша.
