# Первый C-модуль GEMV/GEMM

[English](../EN/cpu-linear.md)

В `src/backend/cpu/` появился самостоятельный **внутренний CPU-кернел линейного
слоя**. Он вычисляет `Y = X × Wᵀ + bias`: одна входная строка означает GEMV,
несколько — GEMM. Это проверенный компонент будущего C-движка. Граф вычислений,
пул работников, публичный API приложения и Vulkan-бэкенд этот модуль не реализует.

## Сборка и проверка

```sh
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_C_COMPILER=clang
cmake --build build
ctest --test-dir build --output-on-failure
```

Нужны CMake 3.21 или новее и компилятор C17. Первая сборка поддерживает Clang и
GCC. Зависимости из сети не скачиваются. Работающей библиотеке не нужны Rust и
LLVM. Clang использует LLVM при компиляции; GCC тоже собирает тот же C-код.

`VELRI_CPU_MULTIVERSION=OFF` оставляет только базовый вариант. При включённой
опции на x86-64 также собираются варианты AVX2/FMA и AVX-512F/FMA. Перед выбором
проверяется поддержка процессором и ОС. Сам диспетчер использует базовые
инструкции. `AUTO` выбирает самый широкий доступный вариант. Это не автотюнер
и не обещание лучшей скорости на любом процессоре.

Тот же алгоритм собирается для ARM64. Локальные проверки включают ARM64 под
QEMU: это проверка корректности, а не скорости на настоящем ARM. Windows и
Android остаются целевыми платформами, но сборки этого первого модуля на них
ещё не проверены. CI включает обычный Linux, санитайзеры, сборку только базового
варианта и Linux ARM64 под QEMU.

## Что означает «одинаковый результат»

Каждый выход вычисляется в строго заданном порядке:

1. Начать с аккумулятора FP64, равного `-0.0`.
2. По возрастанию индекса K перевести два входных FP32 в FP64, перемножить
   и добавить произведение в этот аккумулятор.
3. После всей суммы добавить bias в FP64, а при его отсутствии — `+0.0`.
4. Один раз округлить результат до FP32.

Оптимизированный код должен совпадать с независимым эталоном **побитово**.
Допуска по погрешности нет. Нельзя делить сумму по K на независимые части или
хранить промежуточную сумму в FP32. Тесты включают знаковые нули, субнормальные
числа и переполнение. Вызывающий код должен использовать округление к ближайшему
с выбором чётного при равенстве, сохранение субнормальных чисел без обнуления и
отключённые ловушки ошибок арифметики. Кернел не меняет настройки арифметики
вызывающего потока; флаги исключений не входят в контракт результата.

Результат NaN всегда имеет биты `0x7fc00000`. Так его представление одинаково
между вариантами. Это явное уточнение неопределённых битов NaN старого
Rust-эталона: Rust не обещает их переносимость или детерминированность.
Мы **не** заявляем сохранение прежнего payload NaN.
[Документация Rust об арифметике](https://doc.rust-lang.org/std/primitive.f32.html#nan-bit-patterns).

Простой C-эталон с обычными строками весов находится в `tests/cpu/reference.c`.
Он не использует упаковку и арифметические функции быстрого варианта. Обе
реализации также сверяются с сохранённым бинарным результатом неизменённого
Rust-эталона. Происхождение и хеш этой выборки описаны в
`tests/cpu/fixtures/README.md`.

Прежние быстрые FP32-кернелы проверялись с допуском по погрешности и не выполняют
новое требование точного совпадения. Их исторические TFLOPS нельзя выдавать за
скорость этой C-реализации.

## За счёт чего ускоряется кернел

Общий исходник — `linear_kernel.c`. CMake компилирует его с разными размерами
плиток и наборами инструкций, затем создаёт таблицу вариантов. Отдельного
алгоритма для ARM и проверок названия процессора внутри арифметики нет.

SIMD вычисляет разные выходные признаки одновременно. Для каждого выхода
сохраняется исходный порядок K. Полное разворачивание короткого цикла по
столбцам позволяет компилятору держать суммы в регистрах, не записывая их
на стек на каждом шаге.

Здесь FMA может объединить умножение и сложение FP64 без изменения конечных
результатов: у каждого FP32 не больше 24 значащих бит, поэтому произведению
нужно не больше 48 бит. Оно точно помещается в 53 бита FP64; диапазона
экспоненты тоже хватает. Эталон сохраняет отдельные умножение и сложение,
быстрый вариант может их объединить. Это не разрешает менять порядок суммы
или переходить на FMA в FP32.

GEMM обрабатывает две входные строки вместе, разделяя загрузку весов и их
преобразование в FP64. Все строки одной плитки весов обрабатываются до перехода
к следующей плитке, что улучшает повторное использование кеша. Более узкая
плитка пары строк удерживает число аккумуляторов AVX2 в пределах регистров.
GEMV обрабатывает одну строку и использует больше независимых выходных сумм.

## Подготовка и память

В `linear.h` определены три операции:

| Операция | Задача |
| :--- | :--- |
| `velri_linear_query` | Проверить M/K, выбрать доступный вариант и плитку, сообщить размер упаковки |
| `velri_linear_pack` | Один раз переставить W в предоставленный вызывающим кодом буфер |
| `velri_linear_run` | Проверить представления данных и выполнить вычисление с готовой упаковкой |

W содержит M строк по K значений FP32. Порядок после упаковки:
`[плитка столбцов][K][столбец внутри плитки]`. При ширине плитки C элемент
`(c, i)` находится по индексу `(c / C) * C * K + i * C + c % C`. Неиспользованные
столбцы последней плитки заполнены нулями. Нужная ёмкость —
`ceil(M / C) * C * K` значений float.

Выбранная плитка хотя бы один раз помещается в M. Поэтому упаковка содержит
меньше удвоенного фактического числа весов; при M=1 — ровно K значений.
План учитывает всё дополнение нулями. Веса остаются FP32, копии в FP64 нет.
После упаковки исходные W можно освободить, но пока обе копии живы, память
нужно учитывать для обеих.

Планом, упаковкой, входами и выходами владеет вызывающий код. План должен быть
получен через `query`; менять его поля нельзя. Упаковка относится к создавшему
её плану: одинаковый размер в байтах не делает разные раскладки совместимыми.
План и веса можно разделять между одновременными вызовами с разными выходами.
Исполнение не выделяет память в куче и не упаковывает веса повторно.

M и K должны быть положительными; ноль входных строк допустим. Размеры и шаги
между строками задаются в элементах float. Шаг должен вмещать логическую строку,
в том числе при rows=0. Достаточно обычного выравнивания float. Входы только для
чтения могут пересекаться друг с другом. Выход не должен пересекаться с входным
представлением, промежутками между его строками или планом. Упаковка требует
раздельных исходного и конечного буферов. Переполнение размеров, недостаточная
ёмкость и запрещённые пересечения отклоняются до первой записи.

Этот внутренний API не создаёт потоки. Будущий планировщик сможет делить
проверенные целые плитки столбцов на непересекающиеся диапазоны выходов.
Прямой вызов функции кернела предполагает, что проверки уже выполнены;
обычные вызовы идут через `velri_linear_run`. Общий интерфейс бэкендов
остаётся отдельной частью проекта.

## Замер с проверкой результата

```sh
cmake -S . -B build -DVELRI_BUILD_BENCHMARK=ON
cmake --build build
./build/bench_linear auto 1 1024 1024 1000 21
```

Аргументы: вариант, число входных строк, M, K, повторения на один образец и
число образцов. Необязательный последний аргумент — независимо обоснованный
**арифметический потолок в TFLOPS для этого однопоточного запуска**. Без него
инструмент сообщает, что потолок неизвестен, не придумывая частоту CPU или
ограничение памяти.

Инструмент проверяет каждый выход перед замером и после каждого образца.
Подготовка измеряется отдельно, проверки представлений входят во время вызова.
TFLOPS учитывают полезные `2 × rows × M × K` операций, без дополнения нулями
и преобразований типов. Повторяемые веса могут находиться в кеше. Пул работников
и граф модели здесь не измеряются; [правила измерений](performance.md) сохраняются.

Проверки адресов и неопределённого поведения включаются через `VELRI_SANITIZE=ON`;
нужен компилятор с соответствующими библиотеками санитайзеров. На POSIX тесты
также используют защитные страницы и одновременные вызовы с общими весами.
Одного совпадения арифметики недостаточно для проверки границ памяти и владения.

## Замеры точных кернелов, 10 ноября 2026

Парное сравнение запускало новый C-исходник арифметики внутри сохранённого
Rust-стенда с пулом работников на Ryzen 9 9950X. Измерены полные вызовы линейного
слоя с подготовленными весами, а не будущий C runtime. На конфигурацию приходятся
три пары процессов с чередованием порядка, 21 образец на процесс и побитовая
проверка каждого выхода. База — первая **точная C-версия с накоплением в FP64**,
а не более быстрая историческая реализация FP32.

| Задача, 16 работников | Первая точная версия, TFLOPS | Итоговая версия, TFLOPS | Арифметический ориентир FP64, TFLOPS |
| :--- | ---: | ---: | ---: |
| Cached GEMV, M=1024 K=1024, AVX-512 | 0,460 | 0,773 | 2,425 |
| Нечётный GEMV, M=1025 K=1023, AVX2 | 0,173 | 0,538 | 1,287 |
| GEMM, rows=64 M=512 K=512, AVX-512 | 0,497 | 1,133 | 2,448 |
| GEMM, rows=256 M=4096 K=4096, AVX-512 | 0,424 | 1,419 | 2,258 |
| Streaming GEMV, M=8192 K=8192, AVX-512 | 0,0433 | 0,0427 | Предел RAM неизвестен |

Арифметические ориентиры используют показания APERF/MPERF вокруг итоговых
измеряемых циклов: 32 FP64 FLOP/такт/ядро для AVX-512, 16 — для AVX2. Счётчики
относятся ко всему CPU, снимаются не одновременно и включают активность ОС.
Это условные ориентиры для FMA, а не достижимые потолки цикла с преобразованиями,
загрузками и синхронизацией. Streaming-случай немного замедлился; физический
потолок RAM не установлен. Не определяющий его скорость арифметический ориентир
составляет примерно 2,86 TFLOPS.

Сохранённое расширение плитки AVX2 ускоряет cached GEMV, но теряет примерно
2–3% в измеренных контрольных GEMM. В итоговом сравнении cached GEMV на восьми
работниках даёт 0,539 TFLOPS при арифметическом ориентире 1,359 TFLOPS.
Универсального утверждения, что 16 работников или самый широкий ISA всегда
оптимальны, нет.

Отдельный прямой вызов поставляемого C API, закреплённый за одним ядром при
M=64 K=1024, дал 0,0899 TFLOPS. Переданный номинальный арифметический ориентир
0,1824 TFLOPS предполагает 5,7 ГГц на этом ядре; это не измеренная устойчивая
частота. Проверка включает валидацию API и не использует пул работников.

Программное семплирование подтверждает существенные затраты CPU-времени на
координацию и ожидание работников в старом стенде коротких вызовов. Доли семплов
не равны долям задержки. Профилирование аппаратных событий было недоступно
(`perf_event_paranoid=4`). Отдельный контроль чтения через XOR сохранён, но
не выдаётся за физический потолок памяти. Исходные данные, снимки кода,
дизассемблирование, профили, хеши бинарников и отклонённые либо некорректно
поставленные сравнения остаются локально в
`docs/benchmarks/linear-bottlenecks-2026-11-10/`, вне Git.
