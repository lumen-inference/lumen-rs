# Конфигурация и каскадное размещение (lumen-config)

[English](../EN/rust-config.md)

Это справочник по JSON существующего Rust CLI. Для новой реализации читайте [проект конфигурации](config.md); определения терминов находятся в [словаре](glossary.md).

**Статус:** разбор конфигурации, разрешение размещения и `inspect` реализованы. Принятие настройки рантайма/бэкенда не означает готовность или поддержку соответствующего пути исполнения; см. [architecture.md](architecture.md).

Конфигурационный файл в `velri` представляет собой JSON-документ, который определяет:
1. **Модель и размещение её компонентов по устройствам** (секция `model`).
2. **Параметры работы рантайма и бэкендов**: размер контекста, квантование KV-кэша, настройки пулов потоков CPU и чтения с диска, размер чанков CUDA и параметры HTTP-сервера.

При загрузке конфигурация один раз валидируется и разрешается в плоскую структуру `PlacementPlan` (исходник в исторической версии: `crates/lumen-config/src/lib.rs`). Вычислительный путь получает разрешённые настройки, а не исходный JSON.

Примеры конфигураций находятся в каталоге [`examples/`](../../examples/):
- [`examples/example-dense.json`](../../examples/example-dense.json) — гибридная плотная модель на 27 млрд параметров (`Qwen3.8-27B`).
- [`examples/example-moe.json`](../../examples/example-moe.json) — гибридная MoE-модель с таблицей n-грамм и разреженным вниманием (`Qwen3.8-Flash-Next`).

## 1. Принцип каскадного размещения

Модель содержит десятки слоёв, в каждом из которых присутствует около десяти внутренних узлов (матрицы проекций внимания, кэш, роутер, общие и маршрутизируемые эксперты, нормализации). Чтобы не перечислять размещение каждого тензора вручную, конфигурация использует **каскадное наследование**:

1. На верхнем уровне секции `"model"` задаются базовые параметры размещения для всей модели (например, `"store": "vram:0"` и `"compute": "cuda:0"`).
2. Все дочерние модули и слои автоматически наследуют эти значения.
3. Для крупных узлов, не помещающихся в VRAM (например, маршрутизируемых экспертов `moe/routed-experts` или таблицы `ple/table`), параметры `store` и `compute` переопределяются на соответствующем поддереве.
4. Для размещения отдельных слоёв на другом устройстве внутри `"hidden-layers"` используются **селекторы диапазонов слоёв** (например, `"32-47"`).

### Наследуемые свойства размещения

В любом узле дерева модели могут быть заданы три наследуемых ключа:
- **`"store"`** — место постоянного хранения (`"vram:0"`, `"ram:0"`, `"disk"`).
- **`"compute"`** — вычислительное устройство на стадии генерации токенов (`"cuda:0"`, `"cpu:0"`).
- **`"prefill-compute"`** *(опционально)* — вычислительное устройство на стадии обработки промпта (prefill). Например, если для компонента задано `"store": "ram:0"`, `"compute": "cpu:0"` и `"prefill-compute": "cuda:0"`, то на стадии генерации он вычисляется процессором, а на стадии prefill его веса прокачиваются через PCIe в кольцевой буфер VRAM и вычисляются на GPU.

## 2. Дерево компонентов модели

Допустимые пути в конфигурации определяются методом `Architecture::components()` загружаемой модели. Типовое дерево компонентов имеет следующий вид:

```text
model
├── input-layer/                  # Входная таблица эмбеддингов токенов (embed)
├── ple/                          # Послойные эмбеддинги (Gemma 4) или таблица n-грамм (Qwen3.8)
│   ├── table                     # Таблица выборки строк ("store": "disk" или "ram:0")
│   └── projections               # Послойные линейные проекции PLE
├── vision-tower/                 # Визуальный энкодер (ViT)
├── audio-tower/                  # Аудио-энкодер (Conformer)
├── hidden-layers/                # Повторяющиеся слои декодера (0 .. N-1)
│   ├── norms/                    # Нормализации слоя (input-norm, post-attention-norm и др.)
│   ├── attention/                # Модуль полного, скользящего или разреженного внимания
│   │   ├── q, k, v, o            # Матрицы проекций внимания (q включает выходной гейт)
│   │   ├── qk-norm, rope         # Нормализация Q/K и позиционное кодирование RoPE
│   │   ├── indexer/keys          # Кэш ключей индексатора (для разреженного внимания QSA)
│   │   └── kv-cache              # Страничный KV-кэш слоя
│   ├── linear-attention/         # Модуль линейного внимания (Gated DeltaNet / GDN)
│   │   ├── projections/          # Проекции (qkv, z, b, a, qkvz, ba, out)
│   │   ├── conv, norm            # Короткая свёртка conv1d и выходная норма с гейтом
│   │   └── state                 # Рекуррентное состояние слоя (StatePool)
│   ├── hyper-connections/        # Модуль многопоточных остаточных связей (Hyper-Connections)
│   ├── dense-mlp/                # Плотный FFN-блок (gate, up, down)
│   ├── moe/                      # Модуль смеси экспертов (Mixture of Experts)
│   │   ├── router                # Маршрутизатор экспертов
│   │   ├── shared-experts/       # Общие эксперты (gate, projections/...)
│   │   └── routed-experts/       # Банк маршрутизируемых экспертов
│   │       └── projections/      # Матрицы gate, up, down экспертов
│   └── "<селектор слоёв>"/       # Переопределение диапазона слоёв: например, "0-15" или "32-47"
├── output-layer/                 # Финальная норма (norm) и выходная матрица (lm-head)
└── mtp/                          # Модуль Multi-Token Prediction (поддерево аналогичного вида)
```

## 3. Правила разрешения каскада и селекторов слоёв

1. **Наследование:** вниз по дереву наследуются только ключи `compute`, `store` и `prefill-compute`.
2. **Селекторы слоёв:** непосредственно внутри объекта `"hidden-layers"` допускаются ключи-селекторы номеров слоёв вида `"N"` и `"N-M"` (в том числе перечисленные через запятую). Внутри селектора располагается поддерево того же вида, что и в самом `"hidden-layers"`.
3. **Порядок приоритетов:** значение для пары `(слой ℓ, путь компонента)` ищется в следующем порядке (от высшего приоритета к низшему):
   - **Приоритет 1 (селектор слоя):** самый глубокий узел пути внутри селектора слоёв, совпавшего со слоем $\ell$. Селектор слоя имеет приоритет над общим поддеревом `hidden-layers` на любой глубине.
   - **Приоритет 2 (общее дерево слоёв):** самый глубокий узел пути непосредственно под `hidden-layers`.
   - **Приоритет 3 (корень модели):** значения по умолчанию в корне `"model"`.
4. **Валидация:**
   - Пересечение двух селекторов на одном и том же номере слоя вызывает ошибку загрузки.
   - Индексы слоёв за пределами `[0, num_hidden_layers)` вызывают предупреждение (а с флагом `--strict` — ошибку).
   - Неизвестный ключ вызывает ошибку с подсказкой ближайшего допустимого имени (например, `"stor"` → `"store"`).
   - Известные компоненты дерева, отсутствующие у конкретной модели или конкретного слоя (например, `moe` в плотных слоях или `shared-experts` у `gpt-oss`), пропускаются с отметкой в выводе `lumen inspect`.

### Пример разрешения правил (`examples/example-moe.json`, 48 слоёв)

```json
"model": {
  "path": "models/qwen3.8-flash-next/model.vtq",
  "compute": "cuda:0",
  "store": "vram:0",
  "hidden-layers": {
    "moe": {
      "routed-experts": {
        "compute": "cpu:0", "store": "ram:0", "prefill-compute": "cuda:0"
      }
    },
    "32-47": {
      "moe": {
        "routed-experts": {
          "compute": "cuda:0", "store": "vram:0"
        }
      }
    }
  }
}
```

| Слой | Компонент | Итоговые `compute` / `store` | Источник значения |
| :---: | :--- | :---: | :--- |
| `0..47` | `attention`, `linear-attention`, `moe/router`, `moe/shared-experts` | `cuda:0` / `vram:0` | Корень `"model"` |
| `0..31` | `moe/routed-experts` | `cpu:0` / `ram:0` (`prefill`: `cuda:0`) | `hidden-layers → moe → routed-experts` |
| `32..47` | `moe/routed-experts` | `cuda:0` / `vram:0` | `hidden-layers → "32-47" → moe → routed-experts` |

## 4. Секции верхнего уровня и настройки бэкендов

Вне объекта `"model"` на верхнем уровне JSON-файла располагаются настройки последовательности, бэкендов и сервера:

```json
{
  "chat-template": {
    "kwargs": { "enable_thinking": true }
  },
  "context": {
    "size": 262144
  },
  "kv-quantization": {
    "k-bits": 8,
    "v-bits": 5
  },
  "cuda": {
    "prefill-chunk-size": 4096,
    "cuda-graphs": true
  },
  "cpu": {
    "threads": 16,
    "reserve-cores": 1,
    "numa-spread": false,
    "affinity": "auto"
  },
  "disk": {
    "io-threads": 4,
    "mlock": false
  },
  "server": {
    "host": "127.0.0.1",
    "port": 8080,
    "max-concurrent-requests": 1
  },
  "attention-mechanism": "flash-attention"
}
```

- **`chat-template.kwargs`** — сохраняемые настройки переменных Jinja-шаблона чата. Исполнение шаблона пока не подключено.
- **`context.size`** — максимальная длина контекста последовательности в токенах, определяющая размер пулов KV и состояний.
- **`kv-quantization`** — битность ключей (`k-bits`) и значений (`v-bits`) в диапазоне от 2 до 8 бит; при отсутствии секции KV-кэш хранится в `bf16`.
- **`attention-mechanism`** — используемый механизм внимания (по умолчанию `"flash-attention"`).
- **`cuda`** — размер чанка промпта `prefill-chunk-size` и флаг использования `cuda-graphs` (по умолчанию `true`; отключение используется при профилировании).
- **`cpu`** — настройки постоянного пула рабочих потоков CPU, описанные ниже.
- **`disk`** — число потоков чтения с диска `io-threads` и флаг закрепления таблиц в оперативной памяти `mlock`.
- **`server`** — хост, порт и лимит одновременно обрабатываемых запросов `max-concurrent-requests` для команды `lumen serve`.

### Рабочие потоки CPU и привязка к ядрам

| Ключ | По умолчанию | Поведение |
| :--- | :--- | :--- |
| `threads` | `0` | При нуле число потоков определяется по доступным физическим ядрам; ненулевое значение задаёт точное число рабочих потоков. |
| `reserve-cores` | `1` | Число ядер, вычитаемое при автоматическом выборе; остаётся как минимум один рабочий поток. Игнорируется при явно заданном ненулевом `threads`. |
| `numa-spread` | `false` | При `false` предпочтение отдаётся соседним ядрам; при `true` выбор распределяется по доступным NUMA-узлам. Автоматический расчёт числа потоков использует первый доступный узел при `false` и все доступные узлы при `true`. |
| `affinity` | `"auto"` | Политика привязки рабочих потоков: `"auto"`, `"none"` или `"required"`. |

В Linux определение топологии учитывает маску разрешённых CPU вызывающего потока, включая ограничения `taskset` и cpuset. При автоматическом выборе используется по одному логическому CPU на доступное физическое ядро выбранных NUMA-узлов, затем вычитается `reserve-cores`. Явно заданное число потоков при необходимости задействует дополнительные узлы и SMT-потоки одного ядра. Параметр `numa-spread` управляет выбором CPU; он не меняет политику выделения памяти, а NUMA-узлы не обязательно соответствуют сокетам или CCD.

При `affinity: "auto"` рабочие потоки по возможности закрепляются за выбранными CPU. Если топология или привязка недоступна либо запрошенное число потоков превышает возможности размещения, используется пул без привязки, а причина доступна через `CpuExecutor::placement_note()`. Явно заданное число потоков сохраняется; если определение топологии для автоматического выбора не удалось, используются доступные логические CPU за вычетом резерва, с минимумом в один поток. Режим `"required"` превращает невозможность размещения или привязки в ошибку. Режим `"none"` отключает привязку, сохраняя автоматический выбор числа потоков и учёт резерва. При автоматической привязке выполнение одним рабочим потоком и малые операции остаются на вызывающем потоке; исполнитель не меняет его привязку к CPU.

Парсер и `lumen inspect` поддерживают эти настройки, а `lumen_engine::cpu_executor(isa, &config.cpu)` создаёт по ним CPU-бэкенд. Полный движок и команда CLI `lumen run` ещё не реализованы, поэтому JSON-конфигурация пока не запускает инференс. Синтетический пример декодера напрямую использует тот же API настройки потоков CPU:

```bash
cargo run --release -p lumen-exec --example dense_decode -- avx512 8
cargo run --release -p lumen-exec --example dense_decode -- auto 0
```

Необязательный второй аргумент примера задаёт число рабочих потоков CPU; без него сохраняется прежнее поведение с одним рабочим потоком. Значение `0` включает автоматический выбор с резервом в одно ядро, одним NUMA-узлом и автоматической привязкой. Режим `ref` не принимает аргумент числа потоков.
