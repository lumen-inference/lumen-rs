# Стек и библиотеки

[English](../EN/dependencies.md)

Вычислительная сборка, зависимости CPU/Vulkan и CI кернелов относятся к отдельному проекту Velri-lib. Velri подключает экспортированную цель CMake или локальный checkout без копирования исходников; см. [сборку](velri-lib.md). Текущий прототип и будущие зависимости описываются отдельно.

Здесь описаны библиотеки и инструменты для будущего переноса Velri на C и Vulkan. Значения технических терминов собраны в [словаре](glossary.md), а устройство движка — в [описании архитектуры](architecture.md).

**Статус:** библиотеки ещё не подключены. Список проверен по документации проектов 8 ноября 2026 года. Пометка **«предлагается»** означает выбор для будущей реализации. **«Кандидат»** означает, что пригодность библиотеки ещё нужно проверить. Условный выбор VMA зависит от открытого решения о C++.

Первый [C-модуль CPU Linear](cpu-linear.md) уже собирается через CMake и Ninja, без сторонних библиотек. Сборка полного движка остаётся будущей работой.

## Язык и сборка

Код движка и его публичные заголовки планируется писать на **C23**. Основные средства — структуры и функции. Для каждой области памяти должно быть понятно, кто ею владеет и кто её освобождает. Внутренние структуры не обязаны входить в публичный ABI. Платформенные вызовы и SIMD-расширения компилятора размещаются в небольших отдельных модулях.

Внутренний [интерфейс бэкендов](backends.md) также использует C23, непрозрачные ресурсы и таблицы функций. API приложения не становится от этого стабильным ABI сторонних плагинов.

**CMake и Ninja** используются первым [C-модулем CPU Linear](cpu-linear.md); сборка полного движка ещё предстоит. CMake описывает, как собрать библиотеку, приложения и тесты, а также как сгенерировать вычислительные ядра. Ninja выполняет эти действия.

Для собственных C-целей задаём три настройки:

```text
C_STANDARD=23
C_STANDARD_REQUIRED=ON
C_EXTENSIONS=OFF
```

Так сборка требует C23 и не включает расширения языка по умолчанию. Без `C_STANDARD_REQUIRED` CMake может понизить запрошенный стандарт. Поддержка значения C23 появилась в CMake 3.21 — это минимальная версия CMake для Velri. При настройке также проверяется, что компилятор принимает `-std=c23`. Для этих компиляторов CMake может использовать равнозначное написание `-std=c2x`. [Документация CMake](https://cmake.org/cmake/help/latest/prop_tgt/C_STANDARD.html).

Для сборки C23 нужны Clang 18+ или GCC 14+. Эти версии принимают режим C23; это не означает, что каждый поддерживаемый набор инструментов реализует все возможности языка и стандартной библиотеки C23. [Описание Clang 18](https://releases.llvm.org/18.1.8/tools/clang/docs/ReleaseNotes.html#c23-feature-support), [описание GCC 14](https://gcc.gnu.org/gcc-14/changes.html).

В CI указаны Clang 18 и GCC 14 на Linux, включая санитайзеры и сборку только базового варианта. Задача ARM64 использует GCC 14 и QEMU. Сборки через Clang на Windows и Android NDK Clang остаются планами и требуют отдельных проверок инструментов.

Поддержку MSVC и дополнительных ABI объявляем после проверки в CI. Успешная сборка подтверждает возможность собрать программу, но для оценки скорости нужен отдельный замер на устройстве.

### Что требуется при сборке и при запуске

Для оптимизированных CPU-ядер сохраняем общий способ генерации LLVM IR при сборке. Генератор переносим на C. Небольшой существующий помощник, который обращается к LLVM TTI, может остаться инструментом на C++.

**Готовому движку для запуска не нужны LLVM, Rust и компилятор шейдеров.** При кросс-компиляции генераторы работают на машине сборки, а полученный код компилируется для целевого устройства. Например, генератор может работать на Linux x86-64, пока результат собирается для Android arm64.

## Небольшой обязательный набор

Это предлагаемый набор для первой реализации. Инструменты сборки из таблицы не становятся автоматически зависимостями работающего движка.

| Задача | Предлагаемая библиотека или инструмент | Где используется |
| :--- | :--- | :--- |
| Чтение JSON с конфигурацией и метаданными | [yyjson](https://github.com/ibireme/yyjson), MIT, C | При загрузке. После подготовки вычисления работают с проверенными структурами, без JSON-объектов на горячем пути |
| Объявления Vulkan | [Vulkan-Headers](https://github.com/KhronosGroup/Vulkan-Headers), Apache-2.0/MIT в зависимости от файла | При сборке Vulkan-бэкенда. Эти заголовки не заменяют драйвер |
| Загрузка функций Vulkan | [volk](https://github.com/zeux/volk), MIT, C | На Windows, Linux и Android. У каждого устройства своя таблица функций; работа с несколькими GPU не должна подменять глобальные указатели |
| Компиляция GPU-ядер | [glslc из shaderc](https://github.com/google/shaderc), Apache-2.0 | Преобразует GLSL compute в SPIR-V при сборке. Шейдеры поставляются вместе с библиотекой; Vulkan pipelines по-прежнему создаёт драйвер |
| Проверка SPIR-V | [SPIRV-Tools](https://github.com/KhronosGroup/SPIRV-Tools), Apache-2.0 | `spirv-val` запускается при сборке и в CI. Для проверки задаётся тот же Vulkan target environment, для которого собран шейдер |
| Тесты C-кода | [Unity](https://github.com/ThrowTheSwitch/Unity), MIT | Небольшая C-библиотека проверок. CTest запускает тесты, а Python используется для независимых численных фикстур |

CPU-сборке не нужен Vulkan SDK. Для Vulkan-сборки заголовки и инструменты должны быть на машине разработчика. На машине пользователя нужны работающие Vulkan loader и драйвер: `volk` сам драйвер не предоставляет.

Каждый бэкенд подключается отдельным модулем сборки внутри Velri-lib со своими приватными зависимостями. Библиотека экспортирует необходимые требования линковки через цели CMake; Velri не ведёт второй список SDK или модулей. Выключенный модуль не добавляет в сборку своих заголовков, библиотек и инструментов генерации кода, не требует своего SDK и не добавляет библиотек в готовый движок. Список включённых регистраций создаётся при сборке Velri-lib; новые имена не вносятся вручную в код моделей и планировщика. Общий C-интерфейс и проверка такого подключения описаны в [backends.md](backends.md).

При подключении shaderc проверяем лицензии всех входящих компонентов, а не только самого shaderc.

## Память Vulkan и открытое решение о C++

**Политика зависимостей на C++ остаётся открытой: статус OPEN.** Поэтому выбор библиотеки для GPU-памяти пока условный.

Предпочтительный вариант — **[Vulkan Memory Allocator](https://github.com/GPUOpen-LibrariesAndSDKs/VulkanMemoryAllocator)**, или **VMA**, с лицензией MIT. У него C-интерфейс, но реализация требует C++14. Он помогает выбирать типы GPU-памяти и распределять крупные выделенные области между буферами. Технические требования описаны в [документации VMA](https://gpuopen-librariesandsdks.github.io/VulkanMemoryAllocator/html/faq.html).

Дальнейший выбор зависит от политики проекта:

- **Если C++ допустим внутри библиотек**, VMA подключается отдельным внутренним модулем Vulkan-бэкенда. Это граница реализации внутри Velri-lib; исходный код VMA остаётся открытым. Отдельно проверяется, потребует ли поставляемый бинарный файл C++ runtime.
- **Если C++ допустим только в инструментах сборки**, понадобится ограниченный собственный аллокатор Vulkan на C. Он должен учитывать выравнивание, типы памяти, dedicated allocations и обращения к памяти, которые ещё не завершились.

Поддерживать сразу два GPU-аллокатора без необходимости не планируется. Называть вариант с VMA реализацией целиком на C было бы неверно.

Время жизни модели и запросов определяет сам Velri. Это не задача VMA или `malloc`. Бэкенд получает заранее подготовленный план памяти и во время шага использует уже выделенные области.

Общий планировщик отвечает за время жизни ресурсов и суммарный бюджет. Бэкенд выделяет физическую память и сообщает фактический резерв, выравнивание и добавки. Память драйвера без достоверного отчёта явно отмечается как неизвестная.

## Необязательные зависимости и кандидаты

Эти задачи могут понадобиться позже. Перед добавлением библиотеки нужно проверить её на реальном сценарии Velri.

| Задача | Кандидат или текущее решение | Что нужно учитывать |
| :--- | :--- | :--- |
| Работа с Unicode | [utf8proc](https://github.com/JuliaStrings/utf8proc), MIT и лицензия Unicode data | Нормализация и категории символов для токенизации. Версия Unicode должна соответствовать проверяемому поведению токенизатора |
| Регулярные выражения | [PCRE2](https://github.com/PCRE2Project/pcre2), BSD-3-Clause WITH PCRE2-exception | Нужен только при наличии правил pre-tokenization. JIT необязателен. Совпадение с regex-диалектом исходного токенизатора проверяется фикстурами |
| HTTP/SSE | [CivetWeb](https://github.com/civetweb/civetweb), MIT | Кандидат для отдельного серверного приложения. Нужно проверить потоковую выдачу, backpressure и отмену. Зависимости TLS учитываются отдельно |
| Сравнение GEMM/GEMV | [BLIS](https://github.com/flame/blis) или [OpenBLAS](https://github.com/OpenMathLib/OpenBLAS), BSD-3-Clause | Внешняя контрольная реализация для тестов и замеров. Использование при инференсе потребует отдельного решения по результатам измерений |
| Потоки и файлы | Небольшой слой `platform/` поверх Win32 и POSIX/Android | Сохраняем собственный постоянный пул потоков. Данные о ядрах и топологии берём из ОС, насколько она их предоставляет. Нет привязки к Ryzen или конкретному числу CCD |
| Общий аллокатор | Системный по умолчанию, с возможностью передать свой | Замена аллокатора не устраняет лишние выделения памяти на каждый токен. У модели, состояния и scratch разные времена жизни |

### Токенизатор и шаблон диалога

`utf8proc` и PCRE2 решают только отдельные задачи. Готового токенизатора они не дают. Для BPE/Unigram, added tokens, byte fallback и потокового декодирования нужна собственная реализация или проверенный адаптер.

Также нельзя считать, что небольшой шаблонизатор выполнит любой Hugging Face Jinja template. **Для токенизатора и шаблонов пока нет утверждённой библиотеки.** Сначала изучаем реальные метаданные первых моделей и проверяем точное совпадение token IDs.

Если токенизатор или шаблон не поддерживается, пользователь должен получить понятную ошибку. Пока эта часть разрабатывается, библиотека может принимать готовые token IDs: это позволяет независимо развивать вычислительную часть.

### Что пока не входит в стек

CUDA, CUTLASS и FlashInfer не входят в новый обязательный набор. Их идеи и результаты могут пригодиться для сравнения. Чтобы использовать вычисления через Vulkan, нужны соответствующие GPU-ядра; смена языка основного кода не превращает CUDA-ядро в Vulkan-ядро.

Статическому реестру бэкендов не нужен загрузчик динамических плагинов. Стабильный бинарный ABI плагинов, универсальный async runtime и отдельную библиотеку контейнеров пока не вводим: для них нужен конкретный сценарий использования.

## Правила подключения библиотек

При первой интеграции фиксируем точный release или commit, контрольную сумму и лицензионные уведомления. Получение зависимостей должно быть отдельным явным шагом. После него проект должен собираться без сети. Сборка не скачивает меняющуюся ветку `main`.

Сначала используем исходную библиотеку без собственного форка. Её типы не должны попадать в публичный интерфейс Velri. Ошибки переводятся в статусы движка, при этом полезный диагностический текст сохраняется.

До интеграции выясняем, создаёт ли библиотека собственные потоки и хранит ли глобальное состояние. Список и точные версии уточняются вместе с рабочей сборкой: сама по себе таблица зависимостей ещё не подтверждает, что они успешно работают вместе.
