# Как добавить вычислительный бэкенд

[English](../EN/backends.md)

**Владелец реализации:** вычислительные контракты и реализации этой страницы принадлежат **Velri-lib**. Velri использует API библиотеки и управляет моделями и запросами. См. [границу проектов](velri-lib.md).

Бэкенд отвечает за выполнение операций на устройстве. Первые два бэкенда Velri-lib — **CPU** и **Vulkan**. Библиотека управляет их регистрацией, настройками, устройствами и исполнением; Velri обращается к ней через общий C API. Сам движок и внутренний интерфейс бэкендов пишутся на C23. GPU-кернелы Vulkan пишутся на GLSL и поставляются в SPIR-V.

**Статус: проект интерфейса.** Описанные ниже C-типы и каталог `src/` ещё не реализованы. Это предлагаемые границы модулей для нового движка, а не описание текущего Rust API. Термины находятся в [словаре](glossary.md).

Главное требование: добавление бэкенда для уже известных операций не должно требовать изменений описаний моделей, формул операций и общего планировщика. Новая математика может потребовать новой общей операции; новое устройство само по себе — нет.

## Что потребуется написать

Для нового бэкенда в репозитории **Velri-lib** добавляем один каталог, например `src/backend/example/`, и пять частей:

1. **Регистрацию и обнаружение устройств.** Как называется бэкенд и какие устройства доступны через него.
2. **Работу с памятью.** Выделение и освобождение собственных буферов, передача данных в обычную память CPU и обратно.
3. **Проверку поддержки.** Какие конкретные операции, размеры, типы и раскладки устройство может выполнить.
4. **Подготовку и запуск.** Выбор собственных кернелов и исполнение подготовленных заданий.
5. **Проверки общего контракта.** Корректность вычислений, границ памяти, ошибок и времени жизни ресурсов.

Регистрацию подключаем к сборке библиотеки. После этого общая подготовка находит новый модуль через реестр Velri-lib. В движке ничего регистрировать не нужно. В `model/` движка и общих `plan/` и `runtime/` библиотеки не появляется ветка `if backend == example`.

Это уменьшает объём кода вокруг кернелов. Сами быстрые кернелы всё равно нужно реализовать и проверить: интерфейс не превращает GLSL в код любого другого ускорителя.

## Что остаётся общим

| Общая часть Velri-lib | Что остаётся у бэкенда |
| :--- | :--- |
| Формулы операций, формы тензоров, допустимые изменения состояния | Конкретные реализации операций |
| Проверка графа операций и подготовка графа запусков | Выбор собственных инструкций или GPU-кернелов |
| Размещение вычислений по разрешённым устройствам | Проверка того, подходит ли его устройство для предложенной задачи |
| Время жизни ресурсов, общий бюджет памяти и зависимости заданий | Выделение физической памяти и выполнение зависимостей средствами устройства |
| Слоты исполнения, учёт принятой работы и завершение при отмене | Запуск принятой работы и достоверный результат её завершения |
| Диагностика и общие тесты | Причины отказа, свойства устройства и данные для измерений |

Сборка модели из блоков, сеансы инференса, правила формирования батчей и выбор токенов остаются у Velri. Движок задаёт разрешённые устройства и лимиты ресурсов через API библиотеки; реализация этих ограничений при выполнении графа принадлежит Velri-lib.

Бэкенд не читает конфигурацию семейства модели и не выбирает смысл QSA, GDN или MoE по имени модели. Он получает операции с параметрами. Настройки самого устройства, например число CPU-потоков, проверяет его модуль в Velri-lib при создании контекста.

## Один C-интерфейс, несколько групп функций

У модуля есть регистрационная запись, а у открытого устройства — таблица функций и указатель на внутренние данные. Это обычные C-структуры. Не нужны наследование классов, глобальные конструкторы и отдельный плагин для каждой операции.

| Группа | Пример обязанностей |
| :--- | :--- |
| Регистрация | Имя, версия внутреннего интерфейса, проверка собственных настроек, перечисление устройств |
| Устройство | Открытие, свойства и ограничения, закрытие после освобождения зависимых объектов |
| Память | Проверка размера и выравнивания, выделение, освобождение, подготовка передач данных |
| Подготовка | `query_operation`, подготовка поддержанных операций, освобождение подготовленного исполнения |
| Исполнение | `submit` подготовленной работы с буферами и параметрами текущего шага |
| Завершение | `poll` или `wait`, статус работы, освобождение записи о завершении |

Названия показывают роли функций; точные сигнатуры будут закреплены при первой реализации. Общие помощники могут дать готовый завершённый результат для синхронного CPU-вызова, список регистраций и диагностику отказов. Бэкенду не нужно писать собственную систему сеансов или очередную копию этих помощников.

В таблице нет отдельных полей `gemm`, `rope`, `qsa` и десятков подобных функций. Операция определяется общим описанием, а нужный обработчик выбирается при подготовке. При добавлении операции перечень функций интерфейса не растёт. В реестре операций обновляются проверка и эталон; каждый бэкенд либо поддерживает новый вид, либо явно возвращает отказ.

Внутренние заголовки бэкендов находятся в `src/backend/` репозитория Velri-lib. Движок использует публичные заголовки библиотеки из `include/velri_lib/`; его собственный API моделей и запросов находится в `include/velri/` репозитория Velri. В общий интерфейс не попадают `VkBuffer`, очереди конкретного API или SIMD-типы. Для первого варианта все бэкенды собираются с одной версией исходников библиотеки. Стабильный ABI для сторонних бинарных плагинов пока не обещается.

## Как проверяется поддержка операции

Вопрос «умеет ли устройство GEMM?» слишком общий. Оно может поддерживать только некоторые типы, размеры или способы хранения. Поэтому `query_operation` получает описание конкретного случая:

- вид операции и её параметры;
- формы и типы входов и выходов;
- шаги по осям, раскладки и допустимые пересечения областей;
- виды памяти и свойства ресурсов, с которыми предстоит работать;
- чтения и изменения состояния;
- диапазоны размеров и индексов, которые могут меняться на шаге;
- требуемые правила численной точности.

Запрос не выполняет вычисления и не меняет модель. В ответе находятся причина отказа либо поддержанный вариант с условиями: нужная раскладка, выравнивание, временная и постоянная память, пределы размеров. Эти требования можно получить до окончательного выделения буферов. Если доступно несколько вариантов, подготовка рассматривает их в пределах заданного бюджета поиска.

Например, Vulkan-кернел может принимать FP32-матрицу, но требовать другую упаковку постоянных весов. Подготовка видит это требование, добавляет однократную упаковку и считает её память. Нельзя вернуть «поддерживается», а затем незаметно создать полную копию весов внутри каждого вызова.

Общий код проверяет правильность самой операции. Бэкенд проверяет свои ограничения. Обещание поддержки и последующая подготовка должны совпадать для одного устройства и того же описания. Нехватка памяти при реальном выделении или потеря устройства всё ещё возможны и возвращаются как ошибки.

Неизвестная оценка скорости остаётся неизвестной. Бэкенд не обязан выдавать выдуманное время, а признак поддержки не означает, что его вариант быстрее CPU.

## Что происходит при подготовке

Подготовка модели выполняется один раз в пределах выбранных лимитов:

1. Общий код проверяет граф, формы, чтения и записи состояния.
2. Он запрашивает варианты у разрешённых пользователем устройств.
3. Выбирает размещение, раскладки и необходимые передачи или преобразования данных.
4. Рассчитывает время жизни и общий объём памяти, включая упаковку весов и временные данные.
5. Каждый бэкенд готовит свои операции; общий код связывает их в задания для исполнения.
6. Создаются буферы сеанса и заранее предусмотренные слоты для работы, которая может выполняться одновременно.

Основная единица поддержки — операция. Для первых реализаций достаточно подготовить их по отдельности и собрать последовательность заданий. Бэкенд также может предложить объединённую реализацию подходящего участка графа. Это необязательное расширение: у участка должны сохраняться внешние входы и выходы, изменения состояния и доступные промежуточные результаты, которые нужны остальному графу.

Подготовка всего графа целиком не является обязательным методом бэкенда. Иначе автор каждого нового модуля был бы вынужден повторять планировщик. При этом общий интерфейс не запрещает пакетный запуск подготовленных операций и повторное использование команд.

Если требуемая операция не поддерживается, общий код может применить заранее описанное математически эквивалентное разложение или выбрать другое разрешённое устройство. При явном закреплении за устройством неподдержанный путь заканчивается ошибкой подготовки. Отказ бэкенда не даёт ему права скрытно запустить CPU-код или изменить формулу.

## Память и состояние

Ресурс памяти имеет владельца, устройство и непрозрачный для общего кода внутренний объект. Тензор ссылается на ресурс и добавляет смещение, форму и шаги. GPU-ресурс не выдаётся за обычный указатель, который CPU может разыменовать.

Общий план определяет, какие области нужны, их размеры и когда их можно переиспользовать. Бэкенд реализует физическое выделение с учётом требований устройства. Он сообщает фактический резерв, выравнивание и добавки, чтобы бюджет не учитывал только полезные элементы. Память, которую скрыто использует драйвер и для которой нет достоверного отчёта, отмечается отдельно как неизвестная.

K и V остаются ролями входов. Бэкенд не выделяет пару кэшей автоматически и не проверяет имя модели. Общий ресурс, рекуррентное состояние или восстановление одного значения из другого должны быть видны в графе и плане памяти.

Подготовленные веса неизменны и привязаны к исходному владельцу и версии данных, устройству, реализации и формату упаковки. Если два плана могут использовать одно представление, его можно разделить. Одинаковых размеров матриц для этого недостаточно. Источник и все одновременно нужные представления учитываются в бюджете; новые веса требуют новой подготовки или явного сброса прежней.

Неизменный подготовленный план может использоваться несколькими сеансами. Рабочая память, изменяемые параметры и команды, которые нельзя безопасно разделить, относятся к отдельному сеансу или слоту исполнения. Окончание одного шага не разрешает освободить веса, пока они нужны живым сеансам.

Прямой доступ CPU к ресурсу необязателен. Для доступных отображений должны быть отдельные правила начала и конца доступа. Бэкенд обеспечивает требуемые операции видимости памяти; это не перекладывается на код модели. Импорт внешней памяти также необязателен и не меняет её владельца без явного соглашения.

## Обмен между бэкендами без набора всех возможных пар

Новый бэкенд не должен реализовывать отдельную передачу для каждого уже существующего бэкенда. Базовый способ обмена проходит через обычную память CPU:

```text
ресурс устройства A → буфер передачи в RAM → ресурс устройства B
```

Каждый бэкенд поддерживает передачу своих данных в согласованный буфер хоста и обратно. Общий код соединяет два таких пути. Бэкенд сам решает, нужна ли ему дополнительная закреплённая память; её объём и время жизни должны быть известны плану. CPU может работать с совместимым буфером напрямую.

Передача байтов не преобразует раскладку сама по себе. Обмен использует заранее согласованное представление данных. Если внутреннее представление закрыто для другого бэкенда, нужна явная поддержанная упаковка или распаковка. Для формата без такого пути подготовка отказывает в данном размещении. Это относится и к состоянию, которое нельзя просто скопировать в другую раскладку.

Сначала производитель завершает запись; затем доступны данные для передачи и чтения потребителем. Буфер RAM нельзя переиспользовать, пока его использует хотя бы одна из передач. Объём и число таких буферов ограничены лимитами исполнения.

Прямые копии между устройствами, общая память и импорт внешних объектов могут быть добавлены как необязательные быстрые пути. Проверка совместимости находится в соответствующем модуле обмена. Отсутствие такого пути не требует переписывать общий планировщик и не мешает базовому обмену через RAM.

## Запуск и завершение

`submit` получает подготовленное задание, ссылки на ресурсы текущего сеанса, ограниченные динамические параметры и зависимости. На горячем пути не нужны поиск по имени бэкенда, повторная упаковка постоянных весов или выделение объекта на каждую скалярную операцию.

Результат запуска содержит **статус принятия** и, если работа принята, **объект завершения**. Даже когда после принятия части работы обнаружена ошибка, движок должен получить способ дождаться всех уже запущенных обращений к ресурсам. Сообщить только «ошибка» и потерять такую работу нельзя. При отказе до принятия бэкенд ничего не запустил и не удерживает переданные временные данные.

Завершение означает, что работа закончена и больше не использует свои заимствованные входы, параметры и рабочие буферы. Оно также содержит итоговый статус. Оно не делает GPU-память автоматически доступной CPU: требуемые передачи и операции видимости входят в подготовленный путь доступа.

Для синхронной реализации объект сразу завершён. Для асинхронной `poll` сообщает состояние без ожидания, а `wait` ждёт нужную работу, не заставляя останавливать все устройства. Объекты завершения и изменяемые данные берутся из заранее выделенных слотов и живут до последнего пользователя. Один такой объект может отслеживать пакет команд; отдельный аппаратный fence на каждую операцию не требуется.

Зависимости внутри одного бэкенда можно выполнять его собственными средствами. Для другого бэкенда используется общий порядок: дождаться производителя, выполнить нужную передачу и предоставить вход потребителю. Необязательная межустройственная синхронизация может убрать ожидание CPU, если её поддержка проверена. Ни обычный C-атомик, ни совпадение адресов памяти сами по себе такую поддержку не дают.

При отмене runtime перестаёт отправлять будущую работу и дожидается принятой. Принудительно прерывать уже выполняющийся кернел бэкенд не обязан. Для первой версии действует простое правило: отмена до принятия первой работы шага сохраняет прежнее состояние сеанса; отмена после принятия работы требует явного `reset` перед продолжением. Автоматический возврат к последнему подтверждённому токену не обещается, даже если часть заданий ещё не начала менять состояние.

Runtime фиксирует один итог шага. Отмена, пришедшая после успешного завершения, не отменяет уже выданный результат. После ошибки, затронувшей состояние, сеанс также нельзя продолжать без сброса. При потере устройства используется его процедура остановки и освобождения; пока безопасность освобождения не установлена, ресурсы не переиспользуются, а связанные сеансы считаются ошибочными.

## Как эти правила применяются к CPU и Vulkan

| Общая обязанность | CPU | Vulkan |
| :--- | :--- | :--- |
| Устройство | CPU-контекст и ресурсы доступных ОС ядер | Открытое Vulkan-устройство с проверенными возможностями |
| Постоянные веса | Исходная или подготовленная раскладка для выбранного кернела | Буферы и раскладки, поддержанные GPU-кернелом |
| Подготовка | Выбор SIMD/LLVM-варианта, диапазонов работников и рабочей памяти | Выбор шейдера, создание pipeline, подготовка ресурсов и команд |
| Исполнение | Обычный вызов или задания постоянному пулу | Отправка подготовленных команд в очереди |
| Завершение | Возврат функции либо завершение работников | Завершение отправленной работы средствами Vulkan |
| Передача данных | Доступ к совместимой памяти или копирование | Подготовленные копии и операции видимости через память хоста |

AVX2 и AVX-512 — варианты кернелов внутри CPU-бэкенда. Добавлять отдельный бэкенд для каждой SIMD-инструкции не требуется. CPU использует общий генератор C/LLVM для разных архитектур; независимый простой эталон остаётся доступен без LLVM во время запуска.

Vulkan-бэкенд переводит общие зависимости в нужные барьеры, ожидания и операции памяти. Для базового Vulkan 1.1 используются соответствующие этой версии средства; timeline semaphores и synchronization2 включаются только при проверенной поддержке. `vkQueueWaitIdle` после каждой операции не является общим способом исполнения плана. Примеры зависимостей приведены в [руководстве Khronos](https://docs.vulkan.org/guide/latest/synchronization_examples.html); примеры по этой ссылке используют synchronization2 и сами по себе не задают минимальную версию Velri.

## Регистрация, сборка и настройки

Предлагаемая структура внутри репозитория Velri-lib:

```text
src/backend/
    interface.h        общий внутренний контракт
    registry.c         поиск подключённых регистраций
    common/            помощники и общий путь передачи через RAM
    cpu/               регистрация, память, подготовка, CPU-кернелы
    vulkan/            регистрация, память, подготовка, шейдеры
    example/           будущий бэкенд по тому же контракту

tests/backend/         общие проверки, запускаемые для любого модуля
```

Список регистраций создаётся из явно включённых модулей при сборке. Автор добавляет каталог и его описание сборки; регистрационная функция попадает в список явной ссылкой. Это не зависит от побочных эффектов глобальных конструкторов или случайного сохранения объектного файла линкером. Небольшой список известных модулей и настроек сборки позволяет отличить выключенный модуль от неизвестного имени; он не подтягивает зависимости выключенных модулей.

CPU можно собрать без Vulkan SDK. Выключенный бэкенд не приносит свои заголовки, библиотеки и инструменты в обязательные зависимости. Для приложения подключённые модули остаются за общим C API. Политика зависимостей на C++ и условный выбор VMA рассматриваются отдельно в [dependencies.md](dependencies.md).

В конфигурации устройство обозначается как `<имя-бэкенда>:<индекс>`, например `cpu:0` или `vulkan:0`. Имя проверяется по реестру, а не по закрытому списку GPU API в парсере. Настройки модуля находятся в `backends.<имя>`. Они проверяются его обработчиком один раз и преобразуются во внутренние параметры. JSON модели не передаётся кернелам.

Для хранения на устройстве используется то же однозначное имя, например `store: "vulkan:0"`. `ram:0` и `disk` обозначают хранилища, а не вычислительные бэкенды. Прежнее проектное имя `device:0` заменено именем конкретного устройства: при нескольких бэкендах его смысл был бы неоднозначен. Полный пример находится в [config.md](config.md).

Индекс действует внутри конкретного запуска и не обещает неизменного порядка устройств между запусками. `inspect` показывает фактический идентификатор, бэкенд, применённые настройки и причину выбора. Неизвестный модуль, выключенный при сборке модуль и отсутствие подходящего устройства должны иметь различимую диагностику.

Динамическая загрузка `.dll` или `.so` — возможное дальнейшее расширение. Для неё понадобятся отдельные правила ABI и версий. Простое добавление исходного модуля сейчас не должно зависеть от предварительного решения этой задачи.

## Как начать с малого и проверить расширяемость

Первый вариант нового бэкенда может поддерживать передачу данных и одну операцию, например Linear в FP32. Этого достаточно, чтобы прогнать её тесты. Запуск целой модели возможен только после подготовки всех её операций: на этом бэкенде либо на других устройствах, разрешённых выбранным режимом.

Если разрешён смешанный план, переходы и их стоимость видны в отчёте. Переносить неподдержанную операцию на CPU посреди уже выполняющегося шага нельзя: состояние, форматы, память и зависимости должны быть согласованы заранее.

Общий набор тестов проверяет:

- поддержку и отказ на конкретных формах, типах, шагах и раскладках;
- численное совпадение с независимым эталоном, хвосты и границы памяти;
- общие хранилища и отсутствие неявных выделений K/V;
- передачу в RAM и обратно, включая неудобные размеры и преобразования;
- повторный запуск плана с разными данными и независимость нескольких сеансов;
- отказ до принятия работы, ошибку после принятия, ожидание и отмену без преждевременного освобождения;
- отсутствие повторной подготовки и необъявленных выделений на горячем пути.

Для проверки самого интерфейса нужен маленький тестовый бэкенд с намеренно ограниченной поддержкой и управляемым отложенным завершением. Он не обещает поддержку ещё одного GPU API. Если его подключение требует править модели или добавлять ветви в планировщике, граница модулей выбрана неудачно.

Порядок реализации: общий контракт и тестовый модуль → CPU → Vulkan → общий сценарий CPU/Vulkan. Начинать с промышленного третьего бэкенда ради проверки интерфейса не требуется.

## Почему выбрана такая граница

Таблица с отдельным указателем на каждый кернел проста для первых двух операций, но растёт при добавлении математики и плохо описывает разные форматы памяти. Обязательная компиляция всей модели каждым бэкендом, наоборот, заставляет повторять планирование и управление состоянием. Выбран промежуточный вариант: общий план и описания операций, собственные подготовленные реализации и необязательное объединение операций у бэкенда.

Разделение регистрации, устройства, буферов и исполнения используется также в [интерфейсе бэкендов GGML](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-backend-impl.h). Для Velri это ориентир по границам ответственности, а не обещание совместимости или копия API. Описанный здесь контракт учитывает наше явное владение состоянием и подготовку постоянной работы.
