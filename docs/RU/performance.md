# Производительность: модель физического потолка железа

Целевая платформа `lumen-rs` — рабочая станция или настольный ПК с одной потребительской видеокартой на 16–32 ГБ VRAM, процессором с двухканальной памятью DDR5 и NVMe-накопителем. Целевая нагрузка — крупная MoE или гибридная модель (на десятки и сотни миллиардов параметров), в которой:
- внимание (`Attention`), линейные рекуррентные слои (`Gated DeltaNet`), общие эксперты и часть слоёв размещены в **VRAM** и вычисляются на **GPU**;
- основная масса маршрутизируемых экспертов MoE размещена в системной **RAM** и вычисляется на **CPU**;
- крупные таблицы выборки (n-граммы, PLE) находятся на **NVMe-диске**.

---

## 1. Оценка относительно физических пределов оборудования ($\eta$)

Для каждой скомпилированной программы `Program` и профиля оборудования планировщик вычисляет аналитическую нижнюю границу времени шага $t_{\text{floor}}$, определяемую пропускной способностью памяти и задержками синхронизации, а команда `lumen bench` сопоставляет её с фактическим временем выполнения $t_{\text{measured}}$.

Отношение
$$\eta = \frac{t_{\text{floor}}}{t_{\text{measured}}} \in (0, 1]$$
показывает, какую долю от физического предела оборудования реализует движок. Оптимизация тем самым разделяется на две независимые задачи:
- **повышение КПД $\eta$ к единице** (оптимизация ядер CPU/GPU, сокращение накладных расходов синхронизации и перекрытие дисковых чтений);
- **снижение самого потолка $t_{\text{floor}}$** (перенос наиболее нагруженных слоёв в VRAM через `--auto`, уменьшение битности весов экспертов, увеличение размера батча).

## 2. Аппаратные ресурсы и их измерение (`lumen probe`)

Для каждого ресурса учитываются два показателя: **паспортный предел** (теоретический максимум шины или чипа) и **измеренный предел** (фактическая пропускная способность, достигаемая в микробенчмарке `lumen probe` и сохраняемая в `hw-profile.json`):

| Ресурс | Источник паспортного предела | Что измеряет `lumen probe` |
| :--- | :--- | :--- |
| **Чтение DRAM на узел** | Число каналов $\times$ 8 байт $\times$ частота памяти (SMBIOS) | Потоковое чтение памяти всеми рабочими потоками узла тем же паттерном доступа, что и в ядре экспертов MoE |
| **Чтение VRAM** | Ширина шины GPU $\times$ частота видеопамяти (атрибуты CUDA) | Чтение буфера в VRAM минимальным ядром формы GEMV |
| **Шина PCIe (H2D и D2H)** | Поколение и ширина линка (`sysfs`) | Копирование буферов разного размера из `pinned RAM` в VRAM и обратно |
| **Пересечение GPU ↔ CPU** | *(только измерение)* | Полный цикл (ping-pong) на флагах: `cuStreamWriteValue32` $\to$ спин-пул CPU $\to$ ответ CPU $\to$ `cuStreamWaitValue32` |
| **NVMe-накопитель** | Паспортные IOPS и задержка случайного чтения | Случайные чтения блоками по 4 КиБ при глубине очереди (QD) 1, 16 и 64 |
| **Вычислительный пик (GPU Tensor Cores / CPU int8)** | Пиковая производительность по документации чипа | Микробенчмарки матричных инструкций `mma` (GPU) и `vpdpbusd` (CPU) |

Итоговый отчёт приводит $\eta$ как от паспортного предела, так и от измеренного предела оборудования (что позволяет отделить потери внутри кода движка от аппаратных ограничений контроллера памяти).

## 3. Модель шага: потолок по критическому пути и потолок по ресурсам

Время выполнения одного сегмента ограничено снизу наиболее загруженным ресурсом: $t_{\text{seg}} \ge \max(\text{bytes}_r / \text{BW}_r, \text{FLOP} / \text{peak})$. Метод `Program::floor(&HwProfile)` рассчитывает два потолка:

1. **Потолок по критическому пути (одиночная последовательность, batch = 1):**
   Сумма времён сегментов вдоль цепочки зависимостей слоёв с учётом параллельного перекрытия независимых ветвей внутри слоя (например, вычисление общих экспертов на GPU одновременно с маршрутизируемыми экспертами на CPU) плюс измеренная задержка каждого пересечения GPU ↔ CPU.
2. **Потолок по ресурсам (предел при батчинге):**
   Величина $\max_r (\sum \text{bytes}_r / \text{BW}_r)$ по всему шагу в целом. Достижима только при перекрытии работы разных последовательностей в батче.

Команда `lumen inspect` выводит оба потолка с разбивкой по ресурсам и слоям, `lumen bench` сопоставляет их с замерами, а флаг `--trace` записывает временную шкалу сегментов (события GPU и метки спин-пула CPU).

## 4. Расчёт потолка на эталонном стенде

- **Конфигурация стенда:** RTX 5070 Ti 16 ГБ (GDDR7, 896 ГБ/с; PCIe 5.0 x16, ~63 ГБ/с в каждую сторону) + Ryzen 9 9950X (двухканальная DDR5-6000, паспортный пик 96 ГБ/с) + NVMe SSD.
- **Модель и размещение ([`examples/example-moe.json`](../../examples/example-moe.json)):** `Qwen3.8-Flash-Next` в формате LTQ 4.05 бит/вес; маршрутизируемые эксперты 45 из 48 слоёв размещены в RAM на CPU; эксперты 3 слоёв и остальные веса — в VRAM на GPU; таблица n-грамм — на NVMe-диске; длина контекста — 262 144 токена.

| Ресурс | Читаемые данные за 1 токен decode | Объём | Потолок по паспорту |
| :--- | :--- | :---: | :---: |
| **DRAM (CPU)** | 10 маршрутизируемых экспертов $\times$ 45 слоёв по 2.48 МБ | **1.11 ГБ** | **11.6 мс** |
| **VRAM (веса на GPU)** | 36 слоёв Gated DeltaNet (1.65 ГБ) + Hyper-Connections (1.28 ГБ в fp16) + `lm_head` (0.64 ГБ) + 12 слоёв Full Attention (0.48 ГБ) + общие эксперты (0.24 ГБ) + роутеры (0.13 ГБ) + эксперты 3 слоёв (0.07 ГБ) + проекции PLE (0.07 ГБ) | **4.54 ГБ** | **5.1 мс** |
| **VRAM (состояние GDN)** | Чтение и запись матриц состояния $36 \times 3\text{ МБ}$ в `fp32` | **0.23 ГБ** | **0.25 мс** |
| **VRAM (KV на 262k)** | Индексатор QSA (усреднённые ключи 65 536 блоков $\times$ 12 слоёв) + внимание ($\le 2048$ позиций $\times$ 12 слоёв) | **~0.25 ГБ** | **~0.3 мс** |
| **PCIe (GPU ↔ CPU)** | Вход и выход 45 CPU-сегментов по ~5 КБ | **0.45 МБ** | 90 пересечений $\times$ измеренная задержка |
| **NVMe-диск** | 16 строк n-грамм по 86 байт (кольца `TCQ4X`), промахи страничного кэша | **$\le 1.4$ КБ** | Скрыто за первыми слоями |

- **Потолок по критическому пути:** $5.6\text{ мс (GPU)} + 11.6\text{ мс (CPU)} - 0.25\text{ мс (перекрытие с общими экспертами)} \approx \mathbf{17\text{ мс}}$ плюс 90 пересечений — **около 58 токенов/с** на контексте 262k.
- **Потолок по ресурсам:** $11.6\text{ мс}$ (ограничен DRAM) — около 86 токенов/с (недоступен для одиночной последовательности).
- **Prefill со стримингом экспертов (`prefill-compute: "cuda:0"`):** каждый чанк прокачивает через PCIe 57 ГБ экспертов CPU-слоёв ($\approx 0.9\text{ с}$ на PCIe 5.0), что задаёт потолок **~1100 токенов/с** при чанке 1024 и **~4500 токенов/с** при чанке 4096.

### Факторы, снижающие сам потолок $t_{\text{floor}}$
- Перенос одного слоя маршрутизируемых экспертов из RAM в VRAM сокращает критический путь примерно на 0.23 мс/токен и требует 1.27 ГБ VRAM.
- Снижение битности экспертов на CPU линейно уменьшает время чтения из DRAM.
- Квантование матриц `Hyper-Connections` (занимающих 1.28 ГБ в `fp16` — более четверти трафика VRAM) напрямую сокращает GPU-составляющую шага.

## 5. Целевые показатели эффективности ($\eta$)

Цели по $\eta$ относительно измеренного потолка оборудования (`lumen probe`):

| Компонент | Целевое значение $\eta$ |
| :--- | :--- |
| **Ядро маршрутизируемых экспертов на CPU (`lumen-cpu`)** | $\ge 90\%$ измеренной пропускной способности DRAM |
| **Ядра GEMV и Attention на GPU** | $\ge 85\%$ измеренной пропускной способности VRAM |
| **Пересечение GPU ↔ CPU на флагах** | Не более измеренного ping-pong $+ 1\text{ мкс}$ |
| **Накладные расходы шага (запуск графа, сэмплинг, события)** | $\le 3\%$ времени шага |
| **Шаг decode целиком** | $\eta \ge 0.85$ от потолка по критическому пути |
