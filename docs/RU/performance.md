# lumen-rs — производительность: физический потолок

Oct 27, 2026 · @Vemloir

Типичная машина — одна потребительская видеокарта на 16–32 ГБ, настольный CPU с двухканальной DDR5 и NVMe. Типичная модель — MoE на десятки и сотни миллиардов параметров. Эксперты почти целиком считает CPU; attention, общие эксперты и плотные слои — GPU; большие таблицы выборки лежат на диске.

Мерило движка — железо, а не другие движки. Для каждой `Program` и машины планировщик считает нижнюю границу времени шага по физическим пределам ресурсов, а `lumen bench` кладёт рядом измеренное время. Отношение η = t\_floor / t\_measured показывает, сколько теряет движок сверх того, что запрещает физика. Работа делится на две части: поднимать η к единице и опускать сам потолок — размещением, битностью, батчем.

**Ресурсы и их потолки.** У каждого ресурса два числа: паспортное и измеренное.

| Ресурс | Паспорт — откуда | Измерение — `lumen probe` |
| --- | --- | --- |
| Чтение DRAM на узел | каналы × 8 байт × частота (SMBIOS) | потоковое чтение тем же шаблоном, что у ядра экспертов, всеми воркерами узла |
| Чтение VRAM | ширина шины × частота памяти (атрибуты CUDA) | чтение большого буфера ядром формы GEMV |
| PCIe, H2D и D2H | поколение и ширина линка (sysfs) | копии из pinned RAM разного размера |
| Пересечение GPU ↔ CPU | — | ping-pong на флагах: `WriteValue32` → спин CPU → запись CPU → `WaitValue32` |
| NVMe | IOPS и задержка случайного чтения | случайные чтения по 4 КиБ на глубине очереди 1, 16 и 64 |
| Тензорные ядра, CPU int8 | пиковая производительность по dtype | микробенчи `mma` и `vpdpbusd` |

Паспорт — физический потолок; измерение — то, что железо реально отдаёт любой программе (DRAM никому не выдаёт 100% паспорта). Итоговая метрика — η от паспорта; η от измерения отделяет потери самого движка от потерь железа. У задержек паспорта нет, их потолок — измерение. Профиль `lumen probe` сохраняется в `hw-profile.json`; его читают `inspect`, `bench` и авторазмещение. Паспортные числа, которые нельзя прочитать с устройства, задаются в профиле вручную.

**Модель шага.** Сегмент не может закончиться быстрее, чем самый загруженный ресурс: t\_seg ≥ max(байты\_r / BW\_r, FLOP / пик). Сегменты одного токена связаны зависимостями: слой ℓ+1 ждёт слой ℓ, CPU-участок слоя ждёт GPU-участок перед ним. Поэтому потолков два:

- **По критическому пути** — сумма сегментов вдоль цепочки зависимостей с перекрытием там, где ветви независимы (общие эксперты на GPU параллельно routed-экспертам на CPU), плюс измеренная задержка каждого пересечения GPU ↔ CPU. Это потолок одной последовательности.
- **По ресурсам** — max\_r(Σ байты\_r / BW\_r) по всему шагу. Его достигает только перекрытие работы разных токенов (микро-партии в батче); одной последовательности он недоступен.

`Program::floor(&HwProfile)` возвращает оба потолка с разбивкой по ресурсам и слоям; `lumen inspect` её печатает, `lumen bench` ставит рядом измерения, `--trace` пишет временную шкалу сегментов (события GPU и метки времени спин-пула), по которой видно, где теряется η.

**Эталонный стенд.** RTX 5070 Ti 16 ГБ (GDDR7, 896 ГБ/с; PCIe 5.0 x16, ~63 ГБ/с в каждую сторону) + Ryzen 9 9950X (двухканальная DDR5: 96 ГБ/с при DDR5-6000, фактическую частоту подставит `probe`) + NVMe. Модель — Qwen3.8-Flash-Next в LTQ 4.05 бит/вес, routed-эксперты 45 из 48 слоёв на CPU, n-gram-таблица на диске, KV в bf16. Байты на токен decode взяты из `quantization_config.json` EXL3-кванта той же битности (SC 4.05) — при равной битности объёмы те же:

| Ресурс | Что читается за токен | Объём | Потолок по паспорту |
| --- | --- | --- | --- |
| DRAM | 10 routed-экспертов × 45 слоёв по 2,48 МБ | 1,11 ГБ | 11,6 мс |
| VRAM, веса | DeltaNet 1,65 ГБ; hyper-connections 1,28 ГБ (fp16); lm\_head 0,64 ГБ; full attention 0,48 ГБ; общие эксперты 0,24 ГБ; роутеры 0,13 ГБ; routed-эксперты 3 слоёв 0,07 ГБ; PLE 0,07 ГБ | 4,54 ГБ | 5,1 мс |
| VRAM, состояние | DeltaNet: чтение и запись 36 × 3 МБ в fp32 | 0,23 ГБ | 0,25 мс |
| VRAM, KV на 262k | индексатор: усреднённые ключи 65 536 блоков × 12 слоёв; attention: ≤ 2048 позиций × 12 слоёв | ~0,25 ГБ | ~0,3 мс |
| PCIe | вход и выход 45 CPU-участков по 5 КБ | 0,45 МБ | 90 пересечений × измеренная задержка |
| NVMe | 16 строк n-грамм по 86 байт (кольца TCQ4X), только промахи кэша страниц | ≤ 1,4 КБ | скрыто за первыми слоями |

- Потолок по критическому пути: 5,6 мс GPU + 11,6 мс CPU − 0,25 мс перекрытия с общими экспертами ≈ 17 мс плюс 90 пересечений — около 58 ток/с на контексте 262k.
- Потолок по ресурсам: 11,6 мс (DRAM) — около 86 ток/с; одной последовательности недоступен.
- Prefill со стримингом экспертов (`prefill-compute`): каждый чанк гонит через PCIe все эксперты CPU-слоёв — 57 ГБ, ≈ 0,9 с. Это потолок ~1100 ток/с на чанке 1024 и ~4500 ток/с на чанке 4096, поэтому чанк для такого режима должен быть большим. К нему добавляется потолок тензорных ядер, его даст `probe`.

**Что двигает сам потолок**

- Слой routed-экспертов, перенесённый в VRAM, укорачивает критический путь примерно на 0,23 мс на токен и стоит 1,27 ГБ VRAM; авторазмещение ищет баланс между этим и контекстом.
- Битность CPU-экспертов уменьшает DRAM-часть линейно.
- Hyper-connections в fp16 — 1,28 ГБ, больше четверти VRAM-трафика: квантование этих матриц — самый дешёвый способ опустить GPU-часть.
- Спекулятивка амортизирует GPU-часть на принятые токены, но routed-эксперты при top-10 из 512 почти не пересекаются между токенами, поэтому DRAM-часть растёт почти линейно с k+1.
- Батч и микро-партии приближают потолок по ресурсам.

**Цели по η** (от измеренного потолка; от паспорта — итоговая метрика в отчёте):

| Что | Цель |
| --- | --- |
| Ядро routed-экспертов на CPU | ≥ 90% измеренной пропускной способности DRAM |
| GEMV и attention на GPU | ≥ 85% измеренной пропускной способности VRAM |
| Пересечение GPU ↔ CPU | не дольше измеренного ping-pong + 1 мкс |
| Накладные расходы шага (запуск графа, сэмплинг, события) | ≤ 3% шага |
| Шаг decode целиком | η ≥ 0,85 от потолка по критическому пути |

Отсюда порядок работы: CPU-ядро экспертов на пределе DRAM ([kernels.md](kernels.md)); путь синхронизации на каждом слое — флаги, спин-пул, перекрытие ([разделы 3 и 5 architecture.md](architecture.md#3-память-места-хранения-и-режимы-доступа)); `Fetch` с префетчем, чтобы диск не попадал на критический путь ([раздел 3 architecture.md](architecture.md#3-память-места-хранения-и-режимы-доступа)); prefill со стримингом экспертов ([раздел 5 architecture.md](architecture.md#5-планировщик-и-пайплайн)); кэш горячих экспертов в VRAM — после замера распределения роутинга на реальных трейсах.
