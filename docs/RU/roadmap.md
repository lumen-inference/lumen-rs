# lumen-rs — порядок реализации и риски

Oct 27, 2026 · @Vemloir

Сначала план размещения и эталоны, затем CPU целиком, затем CUDA и оффлоад; каждый шаг проверяется предыдущим.

1. `core`, `mem`, `config` с плоским планом и `lumen inspect` — план печатается раньше, чем появится первое ядро. Каркас `lumen-ref`. Архитектурные проверки CI из [раздела 8 architecture.md](architecture.md#8-расширяемость) — с первого коммита.
2. `format` и эталонный декодер `lumen-ltq` с golden-фикстурами из прототипа. Формат LTQ выбран и зафиксирован экспериментально ([ltq-design.md](ltq-design.md), [спецификация](ltq-format.md)); модели в LTQ до появления `lumen-quantize` даёт квантователь-прототип на Python. Параллельно — перенос квантователя: ядра Витерби и LDLQ на CUDA переходят из прототипа ([`ltq-research/src/cuda/tcq_viterbi.cu`](https://github.com/lumen-inference/ltq-research/blob/main/src/cuda/tcq_viterbi.cu)) в `lumen-cuda-kernels`, цикл LDLQ, профиль и DP — на Rust; сверка с прототипом по KLD.
3. CPU: GEMV LTQ, гибридные и плотные слои → `lumen run` целиком на CPU для Llama, Qwen3 и `qwen3_5_dense`. Дифф-тесты через `lumen-ref`: логиты против transformers на крошечных моделях (случайные фикстуры вроде `tiny-random-*` и `qwen4_exp_tiny_fixture`) и инвариантность к размещению — любой валидный `PlacementPlan` даёт те же логиты в пределах допуска.
4. CUDA: сначала attention на FlashInfer по страничному KV с нашими вариантами (списки блоков QSA, K = V, квантованный KV) и `GatedDeltaNet`, затем GEMV LTQ на потолке VRAM и CUDA Graphs → конфиг целиком на GPU.
5. Ядро оффлоада: банки экспертов, `Transfer`, протокол флагов, спин-пул; `qwen3_next`, `qwen3_5_moe`, gpt-oss и Qwen3-MoE с экспертами на CPU; `lumen probe`, `Program::floor` и первый замер η на стенде.
6. Диск: `RowTable`, `Fetch`, I/O-пул, префетч.
7. Prefill: reconstruct + GEMM на CUTLASS, чанки, `prefill-compute` с CPU-укладкой полосами по 16 строк, мёртвые строки. Обратный проход поддерживаемых блоков для Фишера в `lumen-quantize` — после того, как прямой проход стабилен.
8. Расширения архитектур: Qwen3.8-Flash-Next (QSA, hyper-connections, n-gram PLE поверх базы `qwen3_next`/`qwen3_5_moe`) и Gemma 4 (K = V, p-RoPE, общий KV, PLE, плотный MLP параллельно MoE); цель на стенде — η ≥ 0,85 от потолка по критическому пути (по паспорту он около 58 ток/с на контексте 262k).
9. Батчинг, prefix cache, сэмплинг на GPU, асинхронный шаг, спекулятивка (`NGram`, `Mtp`, `Gemma4Assistant`); затем сервер с OpenAI и Anthropic API.
10. Мультимодальность: `lumen-media`, энкодеры (`qwen3_5_*`, `qwen4_exp`, Gemma 4), эмбеддер без энкодера Gemma 4 12B, маски span'ов.

| Риск | Чем грозит | Что делать |
| --- | --- | --- |
| Граница Rust ↔ CUDA C++ | расхождение раскладки параметров между языками; ошибки, которых не видит компилятор Rust | `lumen-kabi` как единственная граница, заголовок от cbindgen, тесты запуска каждого ядра, compute-sanitizer в CI |
| Декод LTQ на GPU дороже табличных форматов (прототип — 0.45–0.72 от 4-битного табличного) | GEMV при batch 1 упирается в декод, а не в VRAM | int8 + `dp4a`, выборка через `prmt`, общая таблица в shared memory; замер против потолка VRAM в начале фазы 4 |
| CPU-декод LTQ на 2–2.6 бит/вес | на 6-ядерных Skylake / Zen 2 упор в вычисления: до ~25 % tokens/s с текущим ядром | сборка меток XOR-ом таблиц, путь VBMI; DP может не давать CPU-экспертам самые низкие форматы |
| Фишер требует обратного прохода | без весов Фишера DP вдвое хуже | обратный проход поддерживаемых блоков в `lumen-quantize`; до тех пор — Фишер из Python-прототипа |
| Чувствительность по калибровке не переносится на другие данные | «смелое» распределение бит хуже на других языках (до +55 % KLD) | разнообразная калибровка (языки, агенты, длинный контекст), сглаженный профиль DP |
| Время сборки и размер ядер CUDA (шаблоны FlashInfer и CUTLASS, специализации по форматам и архитектурам) | медленная сборка, большой бинарник | инстанцировать только нужные варианты, разнести `.cu`, sccache; SASS только для поддерживаемых архитектур |
| FlashInfer не покрывает наши варианты attention (блоки QSA по 4 токена, K = V, квантованный KV, σ-гейт) | attention потребует своего ядра | прототип в начале фазы 4; механизм вариантов FlashInfer или форк; запасной путь — своё ядро flash-decoding |
| Захват ожиданий на флагах в CUDA-граф | без него — графы по сегментам и больше запусков | протокол со сбросом флага потребителем; проверить в начале фазы 5 на целевом драйвере |
| Задержки диска (вытеснение кэша страниц, холодный NVMe) | скачки времени токена | префетч по известным адресам, I/O-пул вне горячего цикла, `disk.mlock` при достатке RAM |
| Откат рекуррентного состояния и его снимки | сложность спекулятивки и prefix cache у гибридных моделей | история в слоте, как в exllamav3; снимки только на границах ходов |
| Экспериментальные архитектуры меняются (`qwen4_exp`) | переделки после выхода финальной версии | особенности — параметры операторов; parity-тесты на крошечных фикстурах |
| Накладные расходы раздачи работы CPU на каждом слое | лишние микросекунды × 90 переходов на токен | спин-пул со статическим разбиением; η пересечений по `--trace` |
| Эрозия архитектуры по мере роста | особые случаи расползаются по планировщику, бэкендам и ядрам; каждая новая модель стоит дороже предыдущей | правила [раздела 8 architecture.md](architecture.md#8-расширяемость) — проверки CI с первой фазы; новый вариант `Op` — только с эталоном и обоснованием, почему его нельзя выразить параметрами |
