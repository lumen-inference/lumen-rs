# Внешние интерфейсы Velri

[English](../EN/api.md)

Это проект **API движка Velri**. Вычислительные ресурсы и исполнение находятся за ним в Velri-lib; токены, Model и Session — понятия движка. Program использует план библиотеки, Context — её контекст устройств. Velri-lib от этих объектов движка не зависит. См. [границу проектов](velri-lib.md).

Термины из этого документа собраны в [глоссарии](glossary.md).

**Статус: проект C API и приложений.** Публичных C-заголовков пока нет. В текущем Rust CLI работает `inspect`, а команды генерации, сервера и квантования ещё не готовы. Ниже описано, как должны работать будущие интерфейсы. Наличие функции в этом документе не означает, что её уже можно вызвать.

## Как приложение будет обращаться к библиотеке

Приложение сможет использовать вычислительный движок напрямую. Для этого ему не понадобятся CLI, HTTP-сервер, чат-шаблон или токенизатор. В минимальном варианте приложение передаёт token IDs, запускает шаг вычислений и получает логиты либо выбранные токены — в зависимости от режима.

Долгоживущие объекты будут представлены непрозрачными типами. Приложение сможет создавать их и обращаться к ним через API, а управление их внутренним устройством останется за библиотекой. У каждого объекта своя роль и свои ограничения времени жизни:

| Объект | За что отвечает и сколько живёт |
| :--- | :--- |
| Context | Хранит устройства, пул потоков и платформенные ресурсы. Должен жить дольше всех зависимых от него объектов. |
| Model | Хранит конфигурацию, веса и подготовленные представления модели. Одну модель могут использовать несколько сеансов. |
| Program | Хранит проверенный план исполнения для определённых модели, контекста и заданных пределов. |
| Session | Хранит изменяемое состояние последовательности и зарезервированную рабочую память. |

Каждой операции создания соответствует операция освобождения. Если от объекта ещё зависят живые объекты, попытка уничтожить его должна завершиться понятной ошибкой. Например, нельзя освободить контекст, пока он нужен сеансу, и оставить сеанс с указателями на уже освобождённую память.

Точные имена функций и размеры публичных дескрипторов будут закреплены при реализации первого работающего пути. Внутренние структуры библиотеки не входят в обещание стабильного ABI.

Приложение получает список устройств и выбирает их через общий API контекста. Регистрации бэкендов и их таблицы функций относятся к внутреннему [интерфейсу бэкендов](backends.md). Для добавления модуля в сборку не нужно менять API шага модели. Публичные заголовки не раскрывают типы зависимостей, Vulkan или другого API устройства; поддержка внешних бинарных плагинов пока не входит в обещание совместимости.

## Буферы и одновременные вызовы

Для каждого передаваемого буфера API явно указывает, кто им владеет. Это позволяет приложению понять, когда память можно изменить или освободить.

Первый вариант `step` будет синхронным. Приложение сохраняет заимствованный входной буфер до возврата из вызова; к этому моменту вызывающий поток получает готовый результат. Заимствованный результат сеанса остаётся действительным до следующей изменяющей его операции либо до уничтожения сеанса. Чтобы хранить результат дольше, приложение делает копию.

Внутри синхронного вызова бэкенды могут работать асинхронно через объекты завершения. Перед возвратом в приложение реализация `step` дожидается принятой работы и необходимых передач выходных данных.

Если позже понадобится асинхронный API, для него будет отдельный объект завершения и отдельные правила удержания буферов. Правила синхронного `step` нельзя автоматически переносить на такой интерфейс.

В одном сеансе может выполняться только один шаг одновременно. У разных сеансов независимое состояние, но их совместную работу через один контекст должен координировать планировщик этого контекста. В заголовках будет отдельно указано, какие функции разрешено вызывать параллельно. Возможность создать несколько сеансов сама по себе ещё не обещает ускорения от их одновременного запуска.

## Что происходит при ошибке

Функции возвращают статус выполнения. Возможные причины ошибки включают неверные аргументы, неподдержанную операцию, нехватку памяти или ёмкости, ошибку ввода-вывода и ошибку устройства. Диагностика должна сохранять причину и контекст, чтобы приложение могло объяснить сбой пользователю. Библиотека не завершает весь процесс и не использует `longjmp` через код вызывающей стороны.

До обращения к данным проверяются размеры и смещения, в том числе переполнение при умножении. Неверные входные параметры должны быть обнаружены до начала шага.

Ошибка во время уже начавшегося шага требует другого обращения. Если состояние успело измениться, сеанс помечается как непригодный для продолжения до явного `reset`. Автоматический `rollback` не обещается, пока он не реализован. Частично полученные данные нельзя выдавать за успешный результат: сначала должны завершиться все вычисления, которые его создают, и должна пройти проверка требований к численному результату.

## Как работает отмена

Во время шага может быть доступен отдельный запрос отмены. Сам запрос не означает, что все вычисления уже остановились. Память нельзя освобождать, пока к ней обращается незавершённое задание CPU или GPU.

Вызов завершения или сброса должен дождаться всех пользователей соответствующих ресурсов. Приложение должно различать три причины завершения: обычный `stop`, отмену по запросу и ошибку.

Если отмена принята до принятия бэкендом первой работы шага, сеанс остаётся в прежнем состоянии. Если работа уже принята, первый вариант API требует `reset` после завершения отмены. Продолжение с последнего подтверждённого токена без сброса не обещается: для него понадобятся отдельные правила отката состояния. Runtime фиксирует один итог шага, поэтому отмена после успешного завершения не отзывает уже готовый результат.

При потере устройства применяется процедура остановки бэкенда. Связанные ресурсы нельзя переиспользовать, пока не подтверждено, что их безопасно освободить.

## Текст и диалог поверх вычислений

Токенизатор и чат-шаблон будут адаптерами поверх вычислительного ядра. Их совместимость нужно проверять по точным token IDs, специальным токенам, обработке Unicode, byte fallback и потоковому декодированию. Проверка форматирования диалога проводится отдельно от проверки токенизации: правильное разбиение текста на токены ещё не доказывает, что сообщения оформлены так, как ожидает модель.

Неподдержанный чат-шаблон нельзя молча заменить приблизительным. Такая замена допустима только по явному выбору пользователя.

Метаданные модели определяют, как обрабатывать сообщения и специальные токены на выходе. Приложение получает события текста, reasoning и tool calls. Конкретные HTTP-протоколы остаются за пределами математических блоков. Библиотеки-кандидаты и вопросы, по которым решение ещё не принято, перечислены в [dependencies.md](dependencies.md).

## CLI и HTTP-сервер

Для командных приложений запланированы следующие возможности:

| Команда | Назначение |
| :--- | :--- |
| `inspect` | Показать запрошенное и разрешённое размещение, зарегистрированные бэкенды, фактические устройства, применённые настройки, возможности и доступные расчёты памяти. |
| `run`, `chat` | Запустить генерацию или интерактивный диалог через библиотеку. |
| `probe`, `bench` | Измерить оборудование, ядра и целый шаг; сохранить параметры и временную шкалу. |
| `pack` | Выполнить проверенную перепаковку весов с явной версией целевого layout. |
| `quantize` | Запустить отдельный инструмент калибровки и экспорта LTQ. |
| `serve` | Запустить необязательное приложение HTTP/SSE. |

Работающий сейчас Rust `inspect` и планируемые возможности C-приложений нужно различать. Эта таблица описывает целевой набор команд и их обязанностей.

HTTP-слой будет переводить запросы в команды runtime, а события runtime — в ответы клиенту. Планируется совместимость с выбранными версиями внешних API. Конкретный список поддержанных полей должен быть закреплён тестами адаптера: слово «совместимый» не означает, что реализованы все возможности внешнего сервиса.

У очередей запросов и выходных событий должны быть ограничения. Если клиент читает ответ медленно, сервер применяет backpressure либо отменяет запрос с объяснением причины. Неограниченно накапливать готовые токены в памяти нельзя.

Отключение клиента запрашивает отмену. После этого runtime дожидается завершения работы и освобождает состояние. Серверная библиотека не управляет временем жизни GPU-буферов. CivetWeb остаётся кандидатом до проверки того, что такое поведение можно обеспечить.
