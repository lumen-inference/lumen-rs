# LTQ — обоснование формата и квантователь

Oct 27, 2026 · @Vemloir

Почему у движка свой формат квантования, на чём он выигрывает и как устроен квантователь. Спецификация — [ltq-format.md](ltq-format.md); как формат встроен в движок — [раздел 4 architecture.md](architecture.md#4-веса-дескрипторы-и-загрузка).

**Почему LTQ.** Формат выбран экспериментально ([`ltq-research/`](https://github.com/lumen-inference/ltq-research)) против EXL3 — сильнейшего открытого формата того же класса — и табличных `IQ*_K` из GGUF. Метрика — средняя KL-дивергенция от BF16 с принудительной подстановкой токенов на двух трассах, которые не участвуют в калибровке: англоязычные диалоги Nemotron и многоязычная трасса (ru, zh, de, fr, es):

| Модель | Архитектура | С чем сравниваем | KLD LTQ относительно EXL3 (англ. / другие языки) |
| --- | --- | --- | --- |
| Llama-3.2-1B | плотная | штатный `convert.py`, 2.5…4.5 бит/вес | лучше или паритет во всех пяти точках |
| Llama-3.2-3B | плотная | то же | паритет на 2.5 и 3.0, −10 / −4 % на 3.44, паритет / −6 % на 4.0, −17 / −18 % на 4.5 |
| Qwen3-8B | плотная | то же, 3.0 / 3.44 / 4.5 | −10 / −5 %, −11 / −18 %, −28 / −31 % |
| Qwen3-30B-A3B | MoE, 128 экспертов | то же, 3.0 / 4.5 | **−52 / −51 %**, −14 / −12 % |
| Qwen3.5-4B | Gated DeltaNet + full attention | квантователь EXL3 поматрично на тех же гессианах, 3.0 / 3.5 / 4.0 | −14…−18 / −18…−21 % |
| Gemma 4 E4B | PLE, общий KV, sliding attention | то же (`convert.py` не поддерживает PLE Gemma 4) | −15…−26 / −17…−22 % |

Квантование LTQ на одной GPU в 2.4–7 раз быстрее конвертации EXL3 (Qwen3-8B — 4–5 мин, Qwen3-30B-A3B — 11–13 мин на RTX PRO 6000).

Откуда выигрыш — по абляциям:

- **Ядро квантования на уровне EXL3.** TCQ Унгербёка с 1024 состояниями, замкнутой решёткой, расширенными метками (до 16 подмножеств уровней) и таблицами, обученными на гауссовом источнике. На отдельных матрицах Qwen3-8B с ошибкой по отложенной половине калибровки разница с EXL3 по медиане слоёв — от −0.03 до +0.04 бита на каждом типе матриц.
- **Дробные скорости без штрафа смешивания.** Чётность младших некодовых бит пар (K − 0.5) и четвёрок (K − 0.25) даёт меню с шагом в четверть бита. EXL3 нативно умеет только целые скорости и 2.5 / 3.5, поэтому на 4.5 смешивает 4 и 5 бит по слоям — отсюда −28 % на 8B.
- **Битность по срезам строк по информации Фишера** (DP-рюкзак). На MoE при бюджете 3.0 внимание (3 % параметров) получает 4.4 бита ценой 0.05 бита экспертов — это и есть −52 % на Qwen3-30B. Без весов Фишера то же меню на 3B вдвое хуже.
- **Ограничение.** Чувствительность, измеренная на калибровке, плохо переносится на другие данные: «смелое» распределение (холодные эксперты на 2 бита) на многоязычной трассе 30B хуже на 55 %. Профиль DP поэтому сглажен, а калибровочные данные должны покрывать языки и задачи, на которых модель будут использовать.

**Против готовых квантов: Qwen3.8-27B** (`qwen3_5_dense`, 27.10). С опубликованными квантами того же размера: GSQ-RCO (GGUF от IST-DASLab, тип каждого тензора подобран градиентным поиском под бюджет) и EXL3 turboderp, включая самокалиброванный. Линейные слои декодера каждого кванта восстанавливаются в BF16 и меряются на одном стенде; эмбеддинги, lm\_head и прочие тензоры у всех в BF16, битность считается по одному набору матриц (24.3 млрд параметров) со всеми полями формата. KLD nem / mul, разница — парный бутстрап по диалогам ([`results/q27_report.txt`](https://github.com/lumen-inference/ltq-research/blob/main/results/q27_report.txt)):

| Бит/вес | LTQ | Соперник | Разница |
| --- | --- | --- | --- |
| 2.94 | 0.0246 / 0.0278 | GSQ-RCO IQ3\_XXS: 0.0480 / 0.0549 | **−49 / −49 %** |
| 3.00 | 0.0239 / 0.0259 | EXL3 SC 3.0: 0.0260 / 0.0263 | −8 / −1 % (в пределах шума) |
| 3.48 | 0.0119 / 0.0133 | GSQ-RCO IQ3\_S: 0.0221 / 0.0244 | **−46 / −46 %** |
| 3.50 | 0.0124 / 0.0130 | EXL3 3.5: 0.0186 / 0.0191 | **−33 / −32 %** |

Оговорка: калибровка LTQ (самокалибровка Qwen3.8-Flash-Next, чат и агенты) ближе по домену к оценочным трассам, чем imatrix GSQ-RCO, — проверка на нейтральной калибровке и внешней трассе ещё не сделана.

**Устройство.** Вес восстанавливается так:

```
x̃ = H₂₅₆(suh ⊙ x)
y[m] = Σ_b d_row[m] · 2^(e[m,b]/4) · Σ_{k ∈ b} q[m,k] · x̃[k] + bias[m]
q_t = gain[g] · lut[label(s_t) · 2^(K−1) + u_t]
```

- **Тайл** — 16 строк × 16 столбцов, 256 позиций в порядке строк. У позиции один кодовый бит и K − 1 некодовых. Состояние решётки — окно из 10 последних кодовых бит, решётка замкнута в тайле. Метка подмножества — свой бит плюс 1–3 чётности окна по маскам формата.
- **Масштабы:** fp16 на строку, показатель в \[−16, 15\] на (строку, 256-блок), хранится в int8, h-битный индекс усиления на 16 или 32 веса. Поворот входа — `suh` и блочный Адамар-256, выход не поворачивается.
- **Меню:** 19 форматов от 2.04 до 5.29 бит/вес, K = 2…5, целые, D2 и D4. Каждому срезу строк (256 строк внимания, 512 строк MLP, матрица эксперта целиком) квантователь назначает свой формат.

**Таблицы строк** (n-граммы Qwen3.8-Flash-Next, эмбеддинги, PLE) квантуются кольцами LTQ ([спецификация, раздел 9](ltq-format.md#9-таблицы-строк)). Строка режется на кольца длины 160–256; каждое кольцо — замкнутая решётка с fp16-масштабом, повёрнутая блочным Адамаром, а кольца строки лежат подряд. Строки независимы, поэтому выборка читает ровно нужные байты одним куском. На PLE Gemma 4 E4B кольца на 4.25 бита с поворотом дают KLD 0.0010 при 1.39 ГиБ против 0.0006 у int8 при 2.65 ГиБ; без поворота KLD в 2.4 раза выше. Плотное хранение (bf16, int8 с масштабом) остаётся для таблиц, где важна каждая сотая KLD.

**Квантователь** (`lumen-quantize`, прототип — [`ltq-research/src/`](https://github.com/lumen-inference/ltq-research/tree/main/src)). Модель проходит послойно, в памяти один слой:

1. Калибровочный прогон движком (`lumen-exec` на BF16-весах): гессиан входа каждой группы линейных слоёв с общим входом, по порядку исполнения. Калибровочный поток идёт через уже квантованные слои.
2. Фишер по строкам каждой матрицы: обратный проход по выборке собственных ответов модели (2 сэмпла на позицию, фиксированные случайные числа). Для этого нужен обратный проход поддерживаемых блоков — attention, Gated DeltaNet, MLP, MoE, PLE. Пока его нет в движке, Фишер берётся из Python-прототипа (`fisher_full.py`, `fisher_offload.py`).
3. Профиль: каждый срез строк один раз квантуется дешёвым табличным квантователем, а взвешенная по Фишеру ошибка, умноженная на откалиброванный коэффициент формата, даёт цену среза в каждом формате меню. DP-рюкзак распределяет форматы по срезам под бюджет бит/вес.
4. Квантование матрицы: `suh` (знаки и масштабы по Коши — Шварцу), Адамар-256, гессиан с демпфированием 0.2 от среднего диагонали, Block16-LDLQ по блокам 16 столбцов, тайлы 16×16 — Витерби с замкнутой решёткой на GPU (два прохода: окно 32 до середины, затем полный со сдвигом), затем полировка масштабов строк и `suh`.
5. Запись контейнера; реконструкция для следующих слоёв считается из записанных полей.
