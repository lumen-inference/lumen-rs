# Как собирать модель из блоков

[English](../EN/blocks.md)

Общие математические блоки принадлежат Velri-lib; адаптеры семейств в Velri выбирают, настраивают и соединяют их. См. [границу проектов](velri-lib.md).

Новая архитектура не должна требовать написания всего движка заново. Мы хотим описывать модель через готовые части: брать подходящие блоки, задавать их параметры и соединять в нужном порядке.

**Статус:** здесь описано устройство будущей реализации на C и Vulkan. Наличие механизма в примере не означает, что его кернел уже готов. Существующий Rust API и его ограничения вынесены в [rust-blocks.md](rust-blocks.md). Определения терминов — в [словаре](glossary.md).

## Операция, блок, слой и архитектура

Эти уровни отличаются размером задачи, которую они описывают.

| Уровень | Пример | Что задаёт автор |
| :--- | :--- | :--- |
| Операция | Линейная проекция, нормализация, выборка строк, расчёт attention | Какие данные получает, что вычисляет и какое состояние читает или меняет |
| Блок | MLP, MoE, attention с проекциями | Какие операции связаны друг с другом |
| Слой | Attention и MLP вместе с нормализациями и остаточными связями | Порядок блоков и движение данных между ними |
| Архитектура | Последовательность разных слоёв, входные embeddings и выходная голова | Полную схему модели, включая связи между слоями и дополнительные ветви |

Блок может содержать другие блоки. Например, MoE выбирает экспертов и объединяет их ответы, а каждый эксперт может использовать обычный MLP. Внутреннее устройство MLP при этом не нужно писать повторно.

Операция достаточно крупная, чтобы у неё могла быть эффективная реализация. Нам не нужен отдельный узел графа для каждой арифметической инструкции. При необходимости крупную операцию можно разложить на более простые для эталонного расчёта.

## Пример: один MLP в разных местах

Один из вариантов MLP состоит из двух входных проекций и одной выходной:

```text
input ──→ Linear(gate) ──→ Activation ──┐
                                      × ──→ Linear(down) ──→ output
input ──→ Linear(up) ──────────────────┘
```

Этот блок можно использовать как самостоятельный dense MLP или как эксперта внутри MoE. Во втором случае снаружи появляются выбор экспертов, передача им входов и объединение результатов. Сам MLP не обязан знать, где его вызвали.

Повторное использование блока означает повторное использование описания вычислений. **Веса и состояние не становятся общими автоматически.** Если два блока действительно делят веса или историю, это указывается отдельно.

У других MLP могут быть иные проекции и активации. Поэтому приведённая схема — один готовый блок, а не обязательное устройство каждого MLP в движке.

## Пример: гибридная архитектура

Рассмотрим гибридную схему с чередованием GDN и QSA. В этом примере слой GDN включает сам GDN, MoE и связи вокруг них. Слой QSA устроен похожим образом, но использует другой механизм смешивания информации между токенами.

Условно такую последовательность можно записать так:

```text
gdn_layer = Layer(
    mixer = GDN(...),
    feed_forward = MoE(router, experts = GatedMLP(...)),
    connections = ...
)

qsa_layer = Layer(
    mixer = Attention(
        projections = ...,
        position_transform = ...,
        selection = QSASelection(...),
        attention_core = ...
    ),
    feed_forward = MoE(router, experts = GatedMLP(...)),
    connections = ...
)

layers = Repeat([gdn_layer, gdn_layer, gdn_layer, qsa_layer], count)
```

Это пример записи идеи, **не готовый C API и не полное описание конкретной модели**. Повторение создаёт экземпляры слоёв; их веса и состояние сопоставляются отдельно.

В `connections` нужно явно указать порядок нормализаций, остаточные связи и другие переходы. Общая схема не навязывает pre-norm, gated MLP или одинаковый набор проекций всем семействам. В схеме с расширенным residual это также чтение и запись через GR Read и GR Write. Нельзя заменить их обычным сложением только потому, что у другой модели так устроен слой.

Кроме списка слоёв, архитектура описывает дополнительные ветви. Например, n-gram embedding может подключаться к определённому слою, а MTP — использовать отдельные выходы. PLE также подключается своими вычислениями и зависимостями. Эти механизмы не должны прятаться внутри attention или зависеть от номера модели в общем коде.

## Из каких частей состоит attention

Слова «использует attention» недостаточно, чтобы выполнить модель. Нужно описать несколько частей:

| Часть | Что нужно знать |
| :--- | :--- |
| Получение входов | Как вычисляются Q, K и V: через проекции, преобразование другого значения или чтение сохранённых данных |
| Учёт позиции | Как используется позиция токена, например через RoPE, и с какими параметрами |
| Выбор истории | Какие позиции доступны: весь разрешённый контекст, окно или выбранное подмножество |
| Расчёт результата | Какие формулы, масштабы, маски и нормализация применяются |
| Сохранение состояния | Что остаётся между шагами, где хранится и в каком порядке обновляется |

Full attention и sliding-window attention различаются набором доступных позиций. QSA и DSA могут иметь собственные алгоритмы выбора и собственные индексеры. Их нельзя корректно описать одним переключателем `sparse=true`.

Допустим, индексер сначала просматривает всю историю, а затем выбирает несколько блоков для attention. Сам attention читает только выбранные блоки, но работа индексера всё ещё включает полный просмотр. В описании и в замерах нужно учитывать обе части.

Flash-подобный кернел — способ быстро выполнить определённую математику attention, обрабатывая данные плитками. Это отдельный вопрос от того, какие позиции разрешено читать. Выбор позиций, формулы и способ их оптимизированного исполнения описываются раздельно.

## Почему состояние не равно двум буферам K и V

Attention получает данные в ролях K и V. Как эти данные хранятся — отдельное решение архитектуры.

Возможны разные схемы:

- K и V хранятся в разных областях памяти.
- Обе роли используют одну область, если это соответствует математике модели.
- Один вход сохраняется, а другой вычисляется из него.
- Оба входа получаются из общего латентного состояния.

Во всех случаях механизм один: объявить реальные хранилища, ссылки на них и нужные преобразования. Аллокатор выделяет память по этому описанию. Он не создаёт пару буферов по умолчанию и не проверяет имя семейства модели.

Если преобразование создаёт временные данные, заранее известны их размер и время жизни. Иногда можно объединить преобразование с потребителем и не записывать весь промежуточный результат в память. Для этого выбранный кернел должен явно поддерживать такой вход.

То же правило действует за пределами attention. GDN хранит своё рекуррентное состояние, свёртка — нужную историю, схема expanded residual — свои данные. Их размеры определяются соответствующим механизмом, а не общей формулой из числа attention-голов.

## Что должна сообщать операция

Чтобы подготовка смогла выбрать кернел и рассчитать память, у операции должно быть точное описание:

- вид вычисления и его параметры;
- входы и выходы: формы, типы данных и ссылки на ресурсы;
- действия с состоянием: чтение, запись или добавление в историю;
- смысл индексов, если операция обращается к выбранным элементам;
- требования к временным данным.

Веса, состояние сеанса и временная рабочая память имеют разных владельцев. Из описания должно быть понятно, кто отвечает за каждый ресурс и когда его можно использовать повторно.

Подготовка сравнивает требования конкретной операции с возможностями зарегистрированных бэкендов: учитывает шаги, допустимое пересечение памяти, свойства памяти, обращения к состоянию, ограниченные динамические размеры и требования к численным результатам. Бэкенд возвращает поддержанную реализацию с требованиями к раскладке, выравниванию и памяти либо причину отказа. Подготовка выбирает реализацию и явно указывает нужную упаковку, пересылки и рабочую память. Общий блок не выбирает имя бэкенда, AVX2, очередь Vulkan, размер subgroup или число потоков. Добавление устройства для уже существующей математики не требует менять этот блок; граница описана в [интерфейсе бэкендов](backends.md).

Для первой реализации достаточно фиксированного перечисления операций (enum) и общего реестра с таблицами обработчиков. У каждой операции должны быть проверка описания, диагностическое имя, независимый эталон и явный ответ бэкенда о поддержке. Внутренний C-интерфейс запрашивает поддержку операций и готовит реализации; для каждой новой операции в него не добавляется отдельный указатель на функцию. Отдельный бинарный интерфейс внешних плагинов нужен только при появлении реальной задачи для таких плагинов.

Бэкенд может поддерживать только часть операций. При подготовке можно выбрать объявленное эквивалентное разложение или другое устройство, разрешённое политикой размещения, с явными преобразованиями и пересылками. Если явно заданное размещение не поддерживается, подготовка возвращает ошибку. Необязательное объединение операций должно сохранять внешние значения, изменения состояния и промежуточные результаты, которые читаются за его пределами.

## Порядок добавления новой модели

1. **Разобраться в формулах и данных.** Выписать размеры, параметры, состав весов, состояние и порядок его обновления.
2. **Сопоставить веса из файла с блоками.** Одного распознавания имени семейства в конфиге недостаточно.
3. **Собрать схему из готовых блоков.** Описать слои, дополнительные ветви и все общие ресурсы.
4. **Добавить недостающий механизм.** Сначала попробовать собрать его из существующих операций. Если нужна новая операция, описать её в общем виде и написать простой эталон. Затем добавить оптимизированную реализацию.
5. **Проверить части и целую модель.** Сравнить результат с независимой реализацией, проверить несколько последовательных шагов и обработку одного текста целиком и по частям, включая эквивалентность prefill и decode.

Отдельно проверяем неудобные размеры, разные способы получения K/V, совместное использование памяти и отсутствие лишних выделений. Правильный результат одного шага ещё не гарантирует, что состояние останется правильным на следующем.

Семейство считается поддержанным после проверки полной модели. Сейчас регистрация семейства в Rust даёт чтение его конфигурации и сведений для `inspect`; это ещё не готовая генерация. Общий порядок реализации — в [плане работ](roadmap.md).
