# Архитектура `qwen4_exp` (`Qwen3.8-Flash-Next`)

Архитектура **`qwen4_exp`** (`Qwen3.8-Flash-Next`) расширяет гибридную базу [`qwen3_next` / `qwen3_5_moe`](qwen3_next.md) тремя дополнительными модулями: разреженным вниманием с индексатором (`QSA`), четырёхпоточными остаточными связями (`Hyper-Connections`) и послойными эмбеддингами на таблице n-грамм (`PLE`).

---

## 1. Сводная таблица параметров и модулей

| Узел | Параметры в `config.json` | Требования к движку |
| :--- | :--- | :--- |
| **Гибридный скелет 3 : 1** | 48 слоёв: 36 слоёв `GatedDeltaNet` и 12 слоёв `full_attention` (`full_attention_interval: 4`) | Ядро `DeltaNet` и слот рекуррентного состояния в `StatePool` ([раздел 4 architecture.md](../architecture.md#4-подсистема-памяти-четыре-класса-данных)) |
| **Разреженное внимание `QSA` в full-слоях** | `indexer_*`: 4 головы по 128, бюджет 2048 токенов, блоки по 4 токена | Индексатор отбирает для каждого запроса $\le 512$ блоков плюс незавершённый хвост с учётом причинной маски. Так как основное внимание читает не более 2048 позиций, KV-кэш full-слоёв на длинном контексте может храниться в системной RAM (`ZeroCopy`) |
| **Многопоточные связи `Hyper-Connections`** | `hc_count: 4`, `hc_lowrank: 320` | Скрытое состояние `residual` состоит из 4 параллельных потоков; перед подблоком потоки смешиваются во входной вектор (`HcMix`), выход подблока впрыскивается обратно с весами `block_inject_weight` (`HcInject`), а перед финальной нормой потоки сворачиваются (`hyper_connection_mixer`) |
| **Модуль `PLE` на таблице n-грамм** | `ple_*`, `ngram_*` | Дескриптор `RowTable` на NVMe-диске (`store: "disk"`) + упреждающий оператор `Fetch`; внутри слоя — проекция ключа на каждый поток, общее значение, гейт и разреженная причинная свёртка (`dilated causal conv`, ядро 4, шаг 3) |
| **Смесь экспертов `MoE`** | 512 маршрутизируемых экспертов (`top-10`, `intermediate_size: 640`) + 1 общий эксперт (640) с сигмоидным гейтом | Размещение маршрутизируемых экспертов в оперативной памяти на CPU |
| **Черновик `MTP`** | 1 дополнительный слой (внимание, MoE и Hyper-Connections) | Спекулятивный черновик `Mtp` со своим узлом размещения в плане (`mtp`) |
| **Позиционное кодирование `M-RoPE`** | `mrope_section: [11, 11, 10]`, чередующийся, `partial 0.25` от `head_dim = 256` | Трёхмерные координаты позиций $[3, T]$ |
| **Визуальный энкодер** | ViT на 27 блоков | Отдельная `Program` энкодера ([раздел 8 architecture.md](../architecture.md#8-рантайм-генерации-engine-спекулятивка-и-мультимодальность)) |

## 2. Устройство таблицы n-грамм и её оффлоад на диск

На каждой позиции токена вычисляются $(\text{ngram\_size} - 1) \times \text{heads\_per\_ngram} = 2 \times 8 = 16$ хэш-индексов (8 голов биграмм и 8 голов триграмм). Каждая голова возвращает строку из 160 значений, которые при конкатенации образуют вектор размерности $16 \times 160 = 2560$.

Полная таблица состоит из 16 секций по ~20 млн строк (точные размеры секций выводятся из `ngram_vocab_size_base`):
- в формате `bf16` таблица занимает **102 ГБ**;
- в формате `int8` (162 байта на строку с масштабом) — **~52 ГБ**;
- в кольцах LTQ `TCQ4X` (86 байт на строку) — **~28 ГБ**.

На один сгенерированный токен из этой таблицы требуется прочитать всего $16 \times 86 = 1376\text{ байт}$ ($\le 1.4\text{ КБ}$), причём индексы всех 16 строк определяются исключительно ID токенов и известны сразу после сэмплирования. Это позволяет хранить таблицу на NVMe-накопителе (`"ple": { "table": { "store": "disk" } }`) и подгружать строки в фоновом пуле ввода-вывода оператором `Fetch` без задержки критического пути.
