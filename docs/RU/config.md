# Конфигурация C/Vulkan-движка

[English](../EN/config.md)

Термины из этого документа собраны в [глоссарии](glossary.md).

**Статус: проект новой схемы.** Действующий Rust-парсер и существующие JSON-примеры описаны в [rust-config.md](rust-config.md). Пример на этой странице пока нельзя передать существующему CLI. Перенос конфигурации на новую схему — отдельный этап работы.

В новой схеме сохраняются JSON и три отдельных поля: `store`, `compute` и `prefill-compute`. Конфигурация читается один раз. После её проверки движок получает план размещения данных и вычислений, который можно использовать при выполнении модели.

Вычислительные устройства определяются через [реестр бэкендов](backends.md). Парсер разбирает имя вида `<бэкенд>:<индекс>` и проверяет его по реестру. Для добавления модуля не нужно добавлять его имя в отдельный `switch` внутри парсера или планировщика. Настройки каждого модуля собраны в `backends.<имя>` и проверяются его обработчиком при создании контекста.

То, что парсер понимает ключ, ещё не означает, что бэкенд умеет выполнить соответствующую операцию. Поэтому разбор JSON и проверка возможностей устройства — разные части подготовки.

## Где хранить данные и где считать

Поле `store` задаёт постоянное размещение данных. Поле `compute` выбирает, где выполнять decode. Для prefill можно отдельно задать `prefill-compute`; если оно не задано, используется `compute`.

В полях размещения предусмотрены следующие значения:

| Значение | Смысл в новой схеме |
| :--- | :--- |
| `cpu:0` | Контекст вычислений CPU. |
| `vulkan:0` | В `compute` — вычисления на выбранном Vulkan-устройстве; в `store` — хранилище этого устройства. |
| `ram:0` | Хранилище в памяти хоста. Оно не обещает размещение в конкретном NUMA-узле. |
| `disk` | Файловое хранилище. Загрузка нужных данных должна быть явно подготовлена. |

Номер устройства связывается с фактическим устройством при запуске. Команда `inspect` должна показывать его имя и идентификатор, чтобы можно было проверить, куда попали вычисления. Схема не предполагает, что в компьютере обязательно есть видеокарта NVIDIA.

Индекс относится к устройствам указанного бэкенда и не обещает постоянного порядка между запусками. `ram:0` и `disk` — обозначения хранения, их нельзя выбрать как вычислительный бэкенд. Устройство должно отдельно подтверждать, что поддерживает выбранный вид хранения или вычисления. На UMA память, которой управляет GPU-бэкенд, может находиться в общей физической RAM.

Имя `device:0` из прежнего проекта схемы больше не используем: с несколькими бэкендами непонятно, чьё устройство оно обозначает. В новом примере хранение явно привязано к `vulkan:0`. Это изменение проекта C-конфигурации; существующий Rust-парсер по-прежнему описан отдельно.

Старые значения `cuda:N` нельзя молча превращать в `vulkan:N`. Диагностика должна предложить миграцию конфигурации, после чего возможности выбранного устройства нужно проверить заново.

Хранить данные и считать можно в разных местах только при наличии поддержанной стратегии доступа или копирования и совместимого представления данных. Например, запись в конфигурации о хранении в RAM и вычислениях на GPU ещё не реализует передачу данных между ними. Подготовка должна проверить, что такой путь действительно существует. Общий обмен через RAM соединяет бэкенды; изменение раскладки требует явного поддержанного преобразования.

## Как настройки наследуются по дереву модели

Конфигурация сохраняет дерево компонентов модели. Это позволяет задать общее размещение на верхнем уровне, а затем изменить его для отдельных компонентов. Вниз по дереву наследуются только три поля размещения: `store`, `compute` и `prefill-compute`.

Настройки `backends.<имя>` через дерево модели не наследуются. Модуль один раз проверяет их при создании контекста и переводит во внутренние параметры; кернелы не получают JSON модели.

Для компонента конкретного слоя значение берётся из самого глубокого подходящего узла. Переопределение внутри селектора слоя имеет приоритет над правилом из общего поддерева слоёв. Пересекающиеся селекторы отклоняются, поэтому результат не должен зависеть от порядка ключей в JSON.

Допустимые пути компонентов задаёт описание конкретной модели. Нельзя требовать, чтобы у каждого attention одновременно были `q`, `k`, `v` и два кэша: устройство attention может отличаться от модели к модели.

Если правило ссылается на известный компонент, которого у этой модели нет, оно показывается как неприменимое. Опечатка в ключе считается ошибкой. Для селекторов, выходящих за пределы числа слоёв, поведение должно быть явно задано режимом строгости; оставлять его случайным результатом работы парсера нельзя.

## Пример для модели с экспертами

Следующий JSON показывает целевую схему:

```json
{
  "model": {
    "path": "model.vtq",
    "store": "vulkan:0",
    "compute": "vulkan:0",
    "hidden-layers": {
      "moe": {
        "routed-experts": {
          "store": "ram:0",
          "compute": "cpu:0",
          "prefill-compute": "vulkan:0"
        }
      }
    }
  },
  "backends": {
    "cpu": {
      "threads": 0,
      "reserve-cores": 1,
      "affinity": "auto"
    }
  }
}
```

На уровне модели здесь запрошены хранение и вычисления на `vulkan:0`. Для маршрутизируемых экспертов эти настройки переопределены: данные хранятся в `ram:0`, decode выполняется на `cpu:0`, а prefill — на `vulkan:0`. Такой выбор по-прежнему требует проверки доступа к данным и необходимых копирований. Раздел `backends.cpu` настраивает CPU-модуль; другие бэкенды получают свои разделы по тому же правилу.

Значение `threads: 0` просит движок автоматически выбрать число рабочих потоков из ресурсов, доступных процессу через ОС, с учётом резерва. Положительное значение запрашивает указанное число рабочих потоков. Число доступных логических CPU при этом нельзя считать числом физических ядер.

Если обязательную привязку потоков выполнить невозможно, подготовка должна завершиться ошибкой. В режиме `affinity: "auto"` допустим отказ от привязки с объяснением причины, а в режиме `"none"` привязка отключена.

## Пределы и проверка плана

В параметры подготовки входят лимиты контекста, токенов одного шага, последовательностей и памяти. Точные JSON-имена этих параметров и значения по умолчанию будут закреплены вместе с C API. Все прежние экспериментальные настройки не переносятся автоматически.

После применения правил размещения подготовка проверяет конкретные операции, формы, dtype, шаги по осям, раскладки данных, типы памяти и доступные ёмкости. Неизвестная операция или отсутствие необходимой GPU-возможности должны приводить к понятной ошибке. Бэкенд может поддерживать только часть операций, но у подготовленного плана целой модели должны быть реализации для всех нужных операций.

Неизвестное имя бэкенда, модуль, выключенный при сборке, и отсутствие подходящего устройства различаются в диагностике. Опечатки в собственных настройках модуля также не игнорируются. Понимание схемы настроек ещё не означает поддержку всех операций.

Явное закрепление неподдержанной операции за устройством приводит к ошибке подготовки. Разрешённый настройками режим может выбрать другое устройство, в том числе CPU, или заранее объявленное эквивалентное разложение. Такой выбор сопровождается показом фактического плана, причины, передач и их стоимости. Переключать неподдержанную операцию на CPU посреди шага нельзя. Точные имена и значения по умолчанию для режимов автоматического размещения ещё предстоит закрепить в новой схеме.

Команда `inspect` должна отдельно показывать запрос пользователя, результат применения правил размещения и проверенные возможности устройств. Для каждого значения показывается его происхождение. Это помогает понять, было ли оно задано прямо у компонента, унаследовано или получено при разрешении конфигурации.

Расход памяти считается по владельцам хранилищ с учётом padding, перепаковок и scratch. Если нужный расчёт ещё не реализован, поле отмечается как недоступное. Условная оценка не должна выглядеть как проверенное значение.
