# Вычислительные блоки и первый рабочий путь

[English](../EN/rust-blocks.md)

Ниже приведены точные типы и ограничения прежней реализации. Общую идею сборки модели объясняет [документ о блоках](blocks.md), а определения вынесены в [словарь](glossary.md).

Блок описывает, какие операции соединить. При сборке он добавляет их в `GraphBuilder`, а при обработке токенов самого объекта блока уже нет: исполнитель проходит подготовленное расписание. Так одна реализация MLP может использоваться в разных слоях, а устройство модели остаётся в её описании.

Рабочий пример — синтетический декодер (`../../crates/lumen-exec/examples/support/mod.rs`). Он собирает два слоя из общих блоков и запускается командой:

```sh
cargo run -p lumen-exec --example dense_decode
```

Это пример вычисления логитов из ID токенов на небольших заданных весах. Загрузка checkpoint, токенизатор и генерация текста через `lumen run` пока не подключены.

## Что описывает граф

`lumen-models::graph` разделяет три сущности:

| Сущность | Назначение |
| --- | --- |
| `ValueId` | Результат операции. У него есть тип, ширина строки и область строк: текущие токены или история конкретного хранилища. |
| `WeightId` | Объявление неизменяемого веса. Один вес можно использовать в нескольких операциях, в том числе одновременно как embedding и выходную проекцию. |
| `StoreId` | Владелец изменяемого тензора последовательности. Он хранит добавленные строки между шагами и не имеет заданной роли K или V. |

Идентификаторы принадлежат конкретному графу. Передать вес или значение из другого графа нельзя, даже если его числовой индекс совпадает. Формы и параметры проверяются при добавлении операций. Готовый `Graph` изменить нельзя.

`Component` задаёт путь для правил размещения; `Component::layer(2, "mlp/gate")` относится к третьему слою. Его ключ `hidden-layers/2/mlp/gate` используется для привязки данных веса. Имена из checkpoint должен переводить адаптер модели; исполнитель их не знает. Глобальный префикс `hidden-layers` зарезервирован, чтобы ключ глобального веса не мог совпасть с ключом веса слоя.

## Готовые блоки

| Блок | Вычисление и обязанности |
| --- | --- |
| `Linear` | Проекция `x Wᵀ + bias`; вес хранится отдельно. |
| `RmsNorm` | RMS-нормализация с epsilon и масштабом `w` либо `1+w`. |
| `GatedMlp` | `down(activation(gate(x)) * up(x))`. Доступны SwiGLU и GeGLU с tanh-аппроксимацией GELU, опционально — симметричное ограничение входов gate/up. |
| `AttentionBlock` | Причинное полное либо оконное внимание по трём явным входам Q/K/V. Поддерживает группировку голов и разные размерности K/V. Не создаёт проекции и хранилища. |
| `ProjectedAttention` | Готовая композиция отдельных Q/K/V-проекций, необязательного RoPE, двух явно переданных хранилищ, внимания и выходной проекции. |
| `PreNormResidual<B>` | `x + scale * B(norm(x))` для любого блока с одним входом и выходом. |

`Block::build` — удобный интерфейс для одного входа и выхода. Блоки с несколькими входами, например `AttentionBlock`, используют собственный метод сборки. Слои могут соединяться через обычные `ValueId`; обязательного общего класса слоя нет.

RoPE — отдельная операция: rotate-half в первых `rotary_dim` признаках каждой головы. Позиции текущих токенов начинаются с длины уже подтверждённой истории. Окно внимания включает позицию самого запроса.

Если сборка составного блока вернула ошибку, этот `GraphBuilder` следует отбросить: уже добавленная часть композиции не откатывается. Отдельные примитивные операции проверяют аргументы до изменения графа.

## Общее хранилище и производные входы

Хранилище объявляется отдельно от внимания. `append(store, x)` добавляет строки текущего шага и возвращает значение всей доступной истории. `read_store(store)` возвращает то же значение, без копирования и дополнительной аллокации. За шаг у каждого хранилища ровно один писатель; читать его можно из нескольких блоков и слоёв после писателя.

Например, после объявления `q`, `current`, `store` и веса преобразования:

```rust,ignore
let history = graph.append(store, current)?;
let derived = graph.linear(history, transform, None)?;
let out = attention.build(&mut graph, q, derived, history)?;
```

Здесь K получен преобразованием истории, а V использует её напрямую. Если поменять два последних входа местами, преобразованным станет V. Если передать `history` в обе роли, они разделят один буфер. В механизме хранения нет признака «сохранять только V» или ветвления по семейству.

В текущем исполнителе преобразование **всей истории** создаёт временный тензор её полного размера. Он явно включён в `activation_bytes`; экономия постоянного состояния не скрывает эту стоимость. Обработка производного входа частями и слияние преобразования с вниманием — следующие оптимизации. Оконное внимание пока ограничивает чтение, но сохраняет полную историю до `max_context`, без кольцевого буфера.

## Подготовка и шаг

`Program::prepare` получает граф, `PlacementPlan`, `DenseWeights`, пределы размеров и исполнителя. Он проверяет наличие и размеры всех весов, конечность чисел, размещение, поддержку операций и бюджет памяти. Веса привязываются по ключам объявлений. Неизвестные и недостающие ключи — ошибки.

Для весов, используемых только Linear, исполнитель выбирает физическое представление через `dense_layout`. `RowMajor` сохраняет обычную матрицу; `ColumnTiles` хранит полосы выходных столбцов с дополнением последней полосы нулями. Логические M/K отделены от физических размеров. Подготовка выполняется один раз, padding входит в бюджет, несколько потребителей используют одного владельца. Если тот же вес нужен embedding или другой операции, он остаётся row-major без дополнительной копии. Формат LTQ этим не меняется.

`Program::session()` создаёт состояние одной последовательности. Веса разделяются между сеансами через `Arc`; изменяемые буферы у каждого сеанса свои. `Session::run` принимает ID токенов и запускает неизменяемое расписание. `output` возвращает заимствованный срез результата, `position` — подтверждённую длину, `reset` начинает новую последовательность.

Новые строки записываются после подтверждённой границы истории. Только успешное завершение всех операций продвигает её. После ошибки результат недоступен, а следующий шаг перезаписывает неподтверждённые строки. Старые подтверждённые строки не меняются. Это контракт синхронного исполнителя; асинхронным бэкендам потребуется отдельно определить завершение работ.

`MemoryReport` показывает веса, постоянное состояние, временные тензоры и входные ID. Это зарезервированный объём данных для одного сеанса с одной долей общих весов; он не включает метаданные Rust, накладные расходы аллокатора, входные копии `DenseWeights` при подготовке и другие сеансы. Стековые блоки SIMD-ядер и служебная память пула потоков также не входят в отчёт о тензорах. Временные буферы графа пока не переиспользуются. Все вычислительные буферы резервируются до шага.

## Границы реализации и расширение

Сейчас работают одна последовательность, `ram:0` / `cpu:0`, dense-f32 веса и перечисленные операции. Вычисления выполняет `CpuExecutor` с выбираемыми Scalar, AVX2/FMA и AVX-512 реализациями. Независимый скалярный `lumen-ref` остаётся численным эталоном автотестов. Подробности, замеры и ограничения — в [cpu-performance.md](cpu-performance.md). CUDA, offload и квантованное состояние отклоняются. QSA, DSA, GDN, MoE, PLE и другие алгоритмы пока не реализованы в этом графе; они не подменяются полным вниманием или MLP.

Новый блок сначала собирается из существующих операций. Если их недостаточно, добавляется операция с явными входами, выходами, параметрами и ресурсами, затем её проверка и эталонное исполнение. Например, рекуррентному состоянию нужен самостоятельный контракт обновления: оно не должно притворяться добавлением строк истории.

Старый `Architecture → Layout` пока обслуживает разбор конфигов и `inspect`. Он ещё не строит новый граф. Для его хранилищ дерево размещения использует существующую категорию `KvCache` как категорию плотного чтения; она не определяет количество или роли физических буферов. Разреженный доступ требует отдельного описания при добавлении соответствующих алгоритмов.

Численный тест сравнивает декодер с независимым Python-расчётом (`../../crates/lumen-exec/tests/fixtures/generate.py`) при всех разбиениях входа на шаги. Отдельные тесты проверяют совместное и производное состояние, учёт временной памяти, ошибки форм и восстановление после ошибки уже выполненного append.
