# LTQ v1 — формат квантования весов lumen-rs

Oct 27, 2026 · @Vemloir

LTQ (*Lumen Trellis Quant*) — единственный формат квантованных матриц движка. Каждые 256 весов кодируются решётчатым квантованием (TCQ Унгербёка с 1024 состояниями) с замкнутой решёткой, обученными таблицами уровней и заголовком усиления на 16 или 32 веса. Битность назначается по срезам строк: внутри одной матрицы соседствуют форматы от 2 до 5.3 бит на вес, включая дробные скорости K − 0.5 и K − 0.25.

Документ фиксирует то, что пишет квантователь и читает движок: формулу восстановления веса, раскладку тайла, меню форматов и контейнер на диске. Эталон — [`ltq-research/src/ltq_format.py`](https://github.com/lumen-inference/ltq-research/blob/main/src/ltq_format.py): упаковщик и декодер по этому документу. Его самопроверка квантует гауссовы тайлы и кольца строк CUDA-квантователем и сверяет декод бит в бит: по 512 тайлов на каждый из 19 форматов меню и по 256 колец длины 160 на каждый из 17 форматов, допустимых для колец, — 0 несовпадений ([`results/ltq_format_selftest.json`](https://github.com/lumen-inference/ltq-research/blob/main/results/ltq_format_selftest.json)). Как формат встроен в движок, описывает [раздел 4 architecture.md](architecture.md#4-веса-дескрипторы-и-загрузка), а почему он такой — [ltq-design.md](ltq-design.md).

## 1. Линейный слой

Слой y = W·x + b с W размера \[M, K\]. При квантовании K дополняется нулями до кратного 256, M — до кратного 16.

```
x̃ = H₂₅₆(suh ⊙ x)                  поворот входа, один раз на вектор
y[m] = Σ_b d[m, b] · Σ_{k ∈ блок b} q[m, k] · x̃[k]  + bias[m]
d[m, b] = d_row[m] · 2^(e[m, b] / 4)
```

- `suh` — fp16-вектор длины K: знаки (случайные ±1, зерно квантователя) и масштабы входных каналов.
- H₂₅₆ — блочное нормированное преобразование Уолша — Адамара: каждый блок из 256 элементов умножается на матрицу Адамара 256 × 256 с множителем 1/16.
- b = k / 256 — номер 256-блока по K. `d_row` — fp16-масштаб строки; `e` — целый показатель в \[−16, 15\] на пару (строка, блок).
- q\[m, k\] — значение из тайла (раздел 2) без масштаба строки.

Выход не поворачивается: вращение выходов на реальных матрицах не дало выигрыша (абляции 26.10).

## 2. Тайл

Тайл — 16 строк × 16 столбцов: строки 16i..16i+15, столбцы 16·kb..16·kb+15, где kb = 0..K/16−1 (блок b = kb / 16). Внутри тайла позиция веса — t = 16·r + c (r — строка, c — столбец): обход по строкам. Все величины ниже относятся к одному тайлу.

**Решётка.** У каждой позиции один кодовый бит c\_t. Состояние позиции — окно из 10 последних кодовых бит, причём решётка замкнута: начало тайла продолжает его конец, поэтому начальное состояние не хранится.

```
s_t = Σ_{j=0..9} c_{(t − j) mod 256} · 2^j        (бит 0 — свой бит позиции)
```

**Метка** — номер подмножества уровней. Это бит позиции плюс чётности окна предыдущих бит по маскам формата:

```
label_t = (s_t & 1) | parity((s_t >> 1) & m₀) << 1 | parity((s_t >> 1) & m₁) << 2 | parity((s_t >> 1) & m₂) << 3
```

m₀ = 359 у всех форматов. Доп. маски m₁, m₂ есть только у части форматов (раздел 4) и дают 8 или 16 подмножеств вместо 4.

**Значение.** K − 1 некодовых бит u\_t выбирают уровень внутри подмножества, а индекс усиления g — множитель на `sub` подряд идущих позиций (sub = 16 — на строку тайла, 32 — на пару строк):

```
q_t = gain[g_{⌊t / sub⌋}] · lut[label_t · 2^(K−1) + u_t]
```

`lut` (float32, n\_labels · 2^(K−1) записей, порядок «метка, затем u») и `gain` (float32, 2^h записей) берутся из таблицы формата в файле. Их значения хранятся явно: формулу усилений 2^((g − (2^h − 1)/2)·step) разные устройства округляют по-разному, а декод обязан брать ровно те числа, что квантователь.

**Дробные режимы** связывают младшие биты u (u & 1) соседних позиций:

| Режим | Ограничение | Скорость |
| --- | --- | --- |
| нет | — | K бит на вес |
| D2 | у пары (2q, 2q+1) младшие биты равны | K − 0.5 |
| D4 | в четвёрке (4q..4q+3) сумма младших бит чётна | K − 0.25 |

Квантователь учитывает ограничение внутри Витерби, а декодер восстанавливает недостающие биты (раздел 3).

## 3. Поля тайла

Все поля — массивы u16, бит j слова w — элемент потока с номером 16·w + j (младшим битом вперёд).

| Поле | Слов u16 | Содержимое |
| --- | --- | --- |
| `codes` | 16 | кодовые биты c\_t: слово r — строка тайла r, бит c — позиция 16r + c |
| `planes` | 16 · (K − 2) | некодовые биты 1..K−2, по плоскости на бит, раскладка как у `codes` |
| `lsb` | 16 / 8 / 12 | младший некодовый бит: без режима — 256 бит; D2 — бит q относится к паре q; D4 — биты 3q, 3q+1, 3q+2 относятся к позициям 4q, 4q+1, 4q+2 четвёрки q, а бит позиции 4q+3 равен их XOR |
| `gains` | ⌈(256 / sub) · h / 16⌉ | индексы усилений подряд по h бит |

Байт на тайл — 2 · (16 + 16(K − 2) + |lsb| + |gains|), от 64 (TCQ2X0) до 168 (TCQ5X). У K = 2 поля `planes` нет, у h = 0 — поля `gains`.

## 5. Срезы строк

Матрица делится по строкам на срезы, и каждому срезу DP назначает свой формат. Срез — непрерывный диапазон строк, кратный 16: внимание обычно режется по 256 строк, MLP — по 512, эксперт MoE — одним срезом на матрицу. Поворот `suh` и масштабы `d_row`, `e` общие для всей матрицы. Эксперты MoE — отдельные матрицы со своими полями.

## 6. Контейнер

Модель — один файл `.ltq`, в котором и метаданные, и веса, как в GGUF: рядом движку ничего не нужно. Квантователь читает исходный чекпойнт BF16 (safetensors) и пишет этот файл. Квантованная матрица `{p}` (имя исходного `.weight` без суффикса) хранится в пяти тензорах:

| Тензор | dtype, форма | Содержимое |
| --- | --- | --- |
| `{p}.ltq.slices` | int32, \[S, 4\] | на срез: первая строка, конец (не включая), номер формата, смещение данных среза в байтах внутри `{p}.ltq.data` |
| `{p}.ltq.data` | uint8, \[байт\] | данные срезов подряд |
| `{p}.ltq.d_row` | fp16, \[M\] | масштаб строки |
| `{p}.ltq.e` | int8, \[M, K/256\] | показатель масштаба блока, значения в \[−16, 15\] |
| `{p}.ltq.suh` | fp16, \[K\] | знаки и масштабы входа |
| `{p}.bias` | как в исходнике | опционально |

**Данные среза** — четыре области подряд, каждая начинается с адреса, кратного 64 байтам:

```
codes  [T][16]  u16
planes [T][K−2][16]  u16
lsb    [T][|lsb|]  u16
gains  [T][|gains|]  u16
```

T = (строк среза / 16) · (K / 16). Тайлы идут по группам строк, внутри группы — по kb. Поля одного типа лежат рядом (SoA): ядро грузит коды, плоскости и усиления широкими чтениями, а бэкенд может перепаковать их под себя при загрузке ([раздел 4 architecture.md](architecture.md#4-веса-дескрипторы-и-загрузка)).

**Раскладка файла** (little-endian):

```
смещение размер содержимое
0        4      магия "LTQ\0"
4        4      u32: версия контейнера, 1
8        8      u64: длина заголовка H
16       H      заголовок: JSON в UTF-8, дополненный пробелами так, чтобы данные начинались с кратного 4096
16 + H   …      данные: тензоры; каждый начинается с кратного 64 байтам, таблицы строк — с кратного 4096
```

**Заголовок:**

```json
{
  "config": { "...": "config.json исходной модели" },
  "generation_config": { "...": "..." },
  "tokenizer": { "...": "tokenizer.json" },
  "tokenizer_config": { "...": "..." }, "chat_template": "...",
  "processor_config": { "...": "только у мультимодальных моделей" },
  "quantization": {
    "quant_method": "ltq", "version": 1,
    "formats": [
      { "name": "TCQ3X", "K": 3, "frac": "none", "masks": [359, 241], "h": 2, "sub": 16,
        "lut": [ ... float32 ... ], "gain": [ ... float32, 2^h ... ] }
    ],
    "row_tables": { "{p}": { "format": 0, "ring": 160, "hadamard": 32 } },
    "modules_not_quantized": ["lm_head", "model.embed_tokens", "..."],
    "bits_per_weight": 3.0, "calibration": { "...": "..." }
  },
  "tensors": { "{name}": { "dtype": "u8", "shape": [ ... ], "offset": 0 } }
}
```

В `tensors` dtype — один из `f32`, `f16`, `bf16`, `i32`, `i8`, `u8`; `offset` отсчитывается от начала области данных, размер следует из dtype и формы. `frac` — `none`, `d2` или `d4`. Значения `lut` и `gain` записываются как float32 без потерь (9 значащих цифр в JSON). Номер формата в `{p}.ltq.slices` — индекс в `formats`. Тензоры со `store = disk` читаются прямо из файла ([раздел 3 architecture.md](architecture.md#3-память-места-хранения-и-режимы-доступа)), отсюда выравнивание данных по страницам.

## 7. Эталонный декод

Порт `decode_tile` из [`ltq_format.py`](https://github.com/lumen-inference/ltq-research/blob/main/src/ltq_format.py) — эталон для крейта `lumen-ltq` и golden-тестов:

```rust
/// Значения тайла без масштаба строки: q[t] = gain[g] · lut[label · 2^(K−1) + u], t = 16·r + c.
fn decode_tile(f: &LtqFormat, codes: &[u16; 16], planes: &[[u16; 16]], lsb: &[u16], gains: &[u16]) -> [f32; 256] {
    let bit = |w: &[u16], i: usize| ((w[i >> 4] >> (i & 15)) & 1) as u32;
    let mut q = [0f32; 256];
    for t in 0..256 {
        let mut s = 0u32;                                     // окно 10 кодовых бит, решётка замкнута
        for j in 0..10 { s |= bit(codes, (t + 256 - j) % 256) << j; }
        let mut label = (s & 1) | (((s >> 1) & f.masks[0]).count_ones() & 1) << 1;
        for (i, m) in f.masks[1..].iter().enumerate() {
            label |= (((s >> 1) & m).count_ones() & 1) << (2 + i);
        }
        let mut u = match f.frac {
            Frac::None => bit(lsb, t),
            Frac::D2 => bit(lsb, t / 2),
            Frac::D4 if t % 4 < 3 => bit(lsb, 3 * (t / 4) + t % 4),
            Frac::D4 => bit(lsb, 3 * (t / 4)) ^ bit(lsb, 3 * (t / 4) + 1) ^ bit(lsb, 3 * (t / 4) + 2),
        };
        for p in 1..f.k - 1 { u |= bit(&planes[p - 1], t) << p; }
        let mut g = 0usize;
        for i in 0..f.h { g |= (bit(gains, (t / f.sub) * f.h + i) as usize) << i; }
        q[t] = f.gain[g] * f.lut[((label as usize) << (f.k - 1)) | u as usize];
    }
    q
}
```

Это эталон, а не путь ядра. Ядра не считают окно заново на каждой позиции: на CPU метки строки тайла собираются XOR-ом трёх табличных векторов (метка линейна по GF(2) от окна кодовых бит), на GPU берутся из общей таблицы «окно + u → значение» в shared memory ([kernels.md](kernels.md)).

## 8. Контракт квантователя

- Реконструкция, которую квантователь считает своей и по которой меряет ошибку, должна совпадать с декодом записанных полей: d\_row и e после полировки масштабов, `suh` в fp16, таблицы и усиления — ровно те числа, что легли в файл. Эталонный прототип хранит масштаб блока как fp16 произведение d\_row·c\_row·2^(e/4); при переносе в Rust полировка масштабов строки уходит в `d_row`.
- Каждый тайл квантуется Витерби с замкнутой решёткой (два прохода: окно 32 позиции до середины тайла, затем полный проход со сдвигом). Квантователь сам выбирает усиления и уровни; формат разрешает любую последовательность кодовых бит.
- Ограничение дробного режима выполняется для всех групп тайла. Декодер не проверяет его, а восстанавливает недостающий бит.

## 9. Таблицы строк

Таблицы выборки \[rows, dim\] — эмбеддинги, PLE, n-граммы — квантуются кольцами LTQ (`RowCodec::LtqRing`) или хранятся плотными (bf16 / fp16 / int8 с fp16-масштабом на кольцо). Строка режется на кольца длины L: L делит dim и кратно 16 (PLE Gemma 4 — 256, кусок строки на слой; n-граммы Qwen3.8-Flash-Next — 160, вся строка).

- **Кольцо** — та же решётка, что в тайле, только замкнутая по длине L: s\_t = Σ\_{j=0..9} c\_{(t − j) mod L} · 2^j; метки, значения и дробные режимы — как в разделе 2. Поля — как в разделе 3 с L вместо 256: `codes` и каждая плоскость — L/16 слов, `lsb` — ⌈L / 16⌉, ⌈L / 32⌉ или ⌈3L / 64⌉ слов, `gains` — ⌈(L / 16) · h / 16⌉ слов. Допустимы только форматы с sub = 16 (TCQ4W2, TCQ4W3 — нет).
- **Масштаб и поворот.** Значение кольца v = σ ⊙ H\_B(d · q), где d — fp16-масштаб кольца, H\_B — блочное нормированное преобразование Адамара размера B (наибольшая степень двойки, делящая L, не больше 256: 256 при L = 256, 32 при L = 160), σ — знаки ±1 длины L, общие на таблицу. Поворот обязателен: на PLE Gemma 4 E4B он снижает KLD в 2.2–2.4 раза при той же MSE — без него ошибку определяют выбросы координат.
- **Запись кольца** — fp16-масштаб, затем `codes`, `planes`, `lsb`, `gains` подряд; кольца строки идут подряд, поэтому выборка читает одну строку одним непрерывным куском. Байт на кольцо = 2 + байт полей; у TCQ4X при L = 160 — 86 байт против 162 у int8 с масштабом.
- **Контейнер:** `{p}.ltq_rows.data` uint8 \[rows, байт строки\], `{p}.ltq_rows.signs` int8 \[L\]; в заголовке — `quantization.row_tables`: `{"{p}": {"format": i, "ring": L, "hadamard": B}}`.

Измерено на PLE Gemma 4 E4B (таблица 5.25 ГиБ в bf16, всё остальное — BF16, [`results/g4_ple_gemma4.json`](https://github.com/lumen-inference/ltq-research/blob/main/results/g4_ple_gemma4.json)): TCQ3X с поворотом — 1.05 ГиБ, KLD 0.0023 / 0.0030; TCQ4X с поворотом — 1.39 ГиБ, KLD 0.0010 / 0.0011; int8 — 2.65 ГиБ, KLD 0.0006. Это 3 % и 11 % к KLD всей квантованной модели на 3.0 и 4.5 бит/вес соответственно. Битность таблицы выбирается по бюджету модели. Кольца длины 160 с B = 32 проверены по формату, но не по качеству — это делается на Qwen3.8-Flash-Next.

## 10. Вне v1

- **Упаковка `e` в 5 бит** вместо int8 (−0.012 бит/вес).
- **Раскладки бэкендов.** На диске лежит каноническая раскладка; CPU и GPU перепаковывают тайлы под свои ядра при загрузке или один раз через `lumen pack`.
