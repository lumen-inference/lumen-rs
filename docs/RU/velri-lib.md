# Velri и Velri-lib

[English](../EN/velri-lib.md)

**[Velri-lib](https://github.com/velri-inference/velri-lib) — отдельный вычислительный проект на C23.** Velri зависит от него; библиотека не зависит от движка. `external/velri-lib` — Git submodule, закреплённый на коммите библиотеки. Для совместной разработки можно указать отдельный соседний checkout. Ни Git, ни CMake не обновляют зависимость до меняющейся ветки автоматически.

Её основная задача — дать клиенту математические операции и средства создания,
подготовки и исполнения графов запуска кернелов. Velri использует этот API для
описания блоков модели; новый блок из уже поддерживаемых операций не требует
изменений библиотеки. Это целевое устройство, а не перечень готовых возможностей.

| Velri-lib | Velri |
| :--- | :--- |
| Представления тензоров, память, раскладки и типы чисел | Конфигурация модели и сопоставление имён весов |
| Математические операции и их кернелы | Переиспользуемые блоки MLP/attention/MoE, слои и архитектуры |
| Конструктор графа, проверка, выбор кернелов и слияние | Описание вычислений блока через API библиотеки |
| План памяти, упаковка весов, передачи и зависимости исполнения | Правила размещения, бюджеты памяти и пределы нагрузки |
| Регистрация и настройки бэкендов, устройства, работники CPU, очереди и завершение | Запросы, формирование батчей, генерация, токенизация и сервер |
| Заданные численные форматы и их математическое декодирование | Файлы модели, контейнеры и метаданные |
| Независимые эталоны операций и замеры кернелов | Качество модели, логиты и производительность целиком |

Например, блок gated MLP соединяет две операции Linear, активацию, поэлементное
умножение и выходную Linear. Построение графа только записывает эти операции,
значения и доступ к состоянию. При подготовке библиотека выбирает реализации
и строит граф запуска кернелов: задания, копирования, преобразования и зависимости
между ними. Несколько операций могут объединяться в один кернел, а одна операция
может требовать нескольких запусков. Готовый граф можно выполнять повторно с
новыми входами в подготовленных пределах. Модель не задаёт AVX-инструкции или
барьеры Vulkan. Общие композиции в библиотеке допустимы как удобные функции
построения графа, но не ограничивают способы сборки блоков в клиенте.

Velri управляет состоянием запросов и выбирает, какие последовательности объединить
в батч. Velri-lib планирует полученные вычислительные задания. Проекты не создают
конкурирующие пулы CPU. Отдельные слоты исполнения содержат изменяемые привязки и
рабочую память; неизменяемые планы и подготовленные веса можно разделять. Роли K/V
никогда не означают обязательного выделения двух буферов. Принятая работа удерживает
ресурсы до завершения, в том числе при отмене.

Все бэкенды разрабатываются и подключаются в Velri-lib. Библиотека перечисляет
устройства, проверяет настройки модулей, создаёт ресурсы и управляет их временем
жизни. Velri пользуется общим API, передаёт настройки и ограничения пользователя
и показывает полученную диагностику. В движке нет второго реестра устройств,
собственных вызовов GPU API и копий правил настройки бэкендов. Новый бэкенд для
известных операций не требует правок движка: меняются библиотека и её сборка.

Целевые форматы — **F64, FP16, BF16 и INT8**. Типы хранения, накопителя и результата
задаются отдельно; устройство должно поддерживать полную комбинацию. Для будущих
вещественных кернелов задаём требования к погрешности вместо общего требования
совпадать с одним последовательным FP64-циклом. Повторяемость проверяется отдельно.

## Что действительно перенесено

CPU Linear, независимый эталон, фиксированная фикстура, проверки корректности,
инструменты замеров, ARM toolchain и CI кернелов принадлежат Velri-lib. Входы
пока остаются FP32 с последовательным накоплением FP64: выделение не реализует
целевые форматы и не меняет арифметику. Граф, исполнитель и Vulkan остаются проектом.

В Velri остаётся интеграционный тест: подключить `<velri_lib/linear.h>` и цель
`VelriLib::cpu_linear`. Экспериментальный заголовок не является окончательным API
графа или стабильным ABI. Внутренние заголовки библиотеки не входят в интерфейс движка.

## Сборка с закреплённой зависимостью

```sh
git submodule update --init --recursive
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_C_COMPILER=clang
cmake --build build
ctest --test-dir build --output-on-failure
```

Для нового клонирования используем `git clone --recurse-submodules`. Обновление
библиотеки — явное изменение коммита submodule с интеграционными проверками.

## Сборка двух проектов

```sh
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_C_COMPILER=clang -DVELRI_LIB_SOURCE_DIR=../Velri-lib
cmake --build build
ctest --test-dir build --output-on-failure
```

Запускается интеграционная проверка и, по умолчанию, тесты корректности библиотеки.
Для установленной зависимости не задаём `VELRI_LIB_SOURCE_DIR`, а указываем
`-DCMAKE_PREFIX_PATH=/path/to/velri-lib-install`. Сейчас требуется пакет
`VelriLib 0.1.0 EXACT`. При отсутствии зависимости копия исходников не подставляется.
README библиотеки описывает самостоятельную сборку и установку.

Страницы архитектуры EN/RU библиотеки определяют её внутренние границы. Документация
движка сохраняет композицию моделей, форматы файлов, поведение запросов и исторические
замеры. Страницы бэкендов и исполнения здесь описывают ответственность Velri-lib,
пока подробные спецификации не переедут с соответствующими реализациями.
