# Вычислительные ядра на GPU и CPU (lumen-cuda-kernels и lumen-cpu)

В этом документе описано устройство вычислительных ядер `lumen-rs` на GPU (CUDA C++) и на CPU (AVX2 / AVX-512), а также алгоритмы быстрого параллельного декодирования решётчатого формата LTQ.

---

## 1. Быстрое декодирование решётки LTQ без побитового цикла

В отличие от табличных форматов квантования, в формате **LTQ** ([см. спецификацию](ltq-format.md)) номер подмножества (`label`) каждого веса зависит от чётности бит в **10-битном скользящем окне** предыдущих кодовых бит тайла $16 \times 16$. Поштучное вычисление этого окна для каждого веса в скалярном цикле требует 10–15 целочисленных инструкций на вес и ограничивает производительность.

**Ключевое свойство, используемое в ядрах:**
Функция чётности линейна над полем $GF(2)$ (сводится к операции `XOR`), а соседние веса в строке тайла опираются на перекрывающиеся 10-битные окна истории. Поэтому ядра на GPU и CPU **не вычисляют историю по одному весу**, а собирают метки подмножеств сразу для группы из 16–32 весов с помощью небольших предвычисленных таблиц в быстрой памяти (`shared memory` на GPU и кэш L1 на CPU) и векторных операций `XOR`.

## 2. Ядра на GPU (`lumen-cuda-kernels`)

На GPU собственные ядра на CUDA C++ декодируют формат LTQ и исполняют архитектурные операторы, библиотека **CUTLASS** обеспечивает плотный GEMM на стадии prefill и матричные инструкции MMA (CuTe), а **FlashInfer** служит основой для страничного внимания:

| Оператор | Реализация | Устройство ядра |
| :--- | :--- | :--- |
| **LTQ GEMV ($M \le 8$, Decode)** | Своё ядро CUDA C++ | Один варп на полосу строк тайла; входной вектор $\tilde{x}$ загружается один раз на группу строк. Значение веса выбирается из общей таблицы «10 бит окна + некодовые биты $\to$ `fp16`» в `shared memory` (4–32 КБ на формат), либо метка вычисляется через `__popc` по маскам с выборкой байтов через `__byte_perm` (`prmt`) и целочисленным умножением **`__dp4a`** на `int8`-активации. |
| **LTQ GEMM ($8 < M \le 32$)** | Своё ядро + CuTe MMA | Конвейер в стиле Marlin: декодирование тайлов LTQ в `shared memory` с последующей подачей на тензорные ядра (`mma.sync`). |
| **LTQ Prefill ($M > 32$)** | Свой `reconstruct` + **CUTLASS** | Распаковка тайлов ядром `reconstruct` во временный `fp16`-буфер чанками по $M$, затем плотный GEMM через CUTLASS. |
| **MoE (`mgemm`)** | Своё ядро CUDA C++ | Единая сетка блоков на все активные эксперты по таблице дескрипторов `ExpertBank`; токены сгруппированы по эксперту; поддерживаются разные форматы LTQ у разных экспертов. |
| **Адамар-256 + `suh`** | Своё ядро CUDA C++ | 8 элементов на поток $\times$ 32 потока варпа; все каскады бабочки Адамара выполняются в регистрах через `__shfl_xor_sync` вместе с умножением на `suh`. |
| **Декодирование строк (`RowTable`)** | Своё ядро CUDA C++ | Выборка строк таблицы (из VRAM или по PCIe через `ZeroCopy`), декодирование колец `LtqRing` (или `int8`) с масштабом кольца, блочный поворот Адамара $H_B$ и умножение на знаки. |
| **Внимание (`Attention`)** | **FlashInfer** + кастомные варианты | Страничное внимание по `KvPool`. Параметры: скользящее окно, синки внимания, маска, раскладка KV ($K$ и $V$, только $V$ с восстановлением $K$, разделяемый кэш) и её битность, выходной сигмоидный гейт из `q_proj`, разреженный список страниц от индексатора QSA, `softcap`; на decode — разбиение `split-K`. |
| **Индексатор QSA (`IndexerScore`)** | Своё ядро CUDA C++ | Вычисление очков блоков $\text{ReLU}(q \cdot k)$ по головам, отбор `top-k` блоков и усреднение ключей завершённых 4-токенных блоков. |
| **Gated DeltaNet (GDN)** | Своё ядро CUDA C++ | Блочный (chunked) алгоритм на стадии prefill (по образцу `flash-linear-attention`), рекуррентный шаг на стадии decode (с $L_2$-нормализацией $Q$ и $K$), причинная свёртка `short conv1d` и выходная норма `RMSNormGated`. |
| **Hyper-Connections (`HcMix`, `HcInject`)** | Своё ядро CUDA C++ | Смешивание 4 потоков перед подблоком, впрыск выхода обратно в потоки и свёртка потоков перед финальной нормой. |
| **Нормы (`RMSNorm`, `1 + w`, `RMSNormGated`), `RoPE`, `SwiGLU`/`GeGLU`, `Router`, `Sample`** | Свои ядра CUDA C++ | Поэлементные операции и варповые редукции, слитые с соседними операторами, и генератор случайных чисел Philox. |

### Особенности реализации на GPU
- **Варианты `RoPE` (`RopeSpec`):** стандартный; частичный (`partial`, Qwen) — вращаются первые $r$ измерений с частотами $\theta^{-2i/r}$; пропорциональный (`p-RoPE`, Gemma 4) — частоты $\theta^{-2i/d}$ для первых $p \cdot d / 2$ углов при полном $d$, остальные углы нулевые, `rotate-half` выполняется по всей голове (вращаются срезы $[0, p \cdot d / 2)$ и $[d/2, d/2 + p \cdot d / 2)$); `YaRN`; трёхмерный `M-RoPE` с разбиением углов на секции $(t, h, w)$.
- **Внимание внутри CUDA Graph:** поскольку размер сетки запекается в граф при захвате, а длины последовательностей меняются на каждом шаге, параметры разбиения `split-K` вычисляются на устройстве из буфера `StepInputs`. Страничный decode FlashInfer принимает список страниц на запрос (в который передаются блоки индексатора QSA).
- **Стоимость декодирования LTQ на GPU:** теоретический минимум — около 5–6 целочисленных операций и одно чтение из `shared memory` на вес. Прототип GEMV на `fp32`-FMA ([`ltq-research/src/cuda/ltq_matvec_bench.cu`](https://github.com/lumen-inference/ltq-research/blob/main/src/cuda/ltq_matvec_bench.cu), RTX PRO 6000) достигает 0.45–0.72 от потолка аналогичного ядра для 4-битного табличного формата (конфликты банков общей таблицы некритичны). Чтобы на потребительских картах (RTX 5070 Ti / 5080) при `batch = 1` упираться в пропускную способность VRAM, а не в декод бит, используются `int8`-активации с `__dp4a`, выборка значений через `__byte_perm` (`prmt`) и сборка меток сразу на 32 веса из битовых плоскостей.
- **Programmatic Dependent Launch (PDL) и базовый уровень ISA:** на GPU с архитектурой `sm_90+` запуск через `cudaLaunchKernelEx` с PDL позволяет следующему ядру начинать пролог до завершения записи предыдущего ядра. Минимальная поддерживаемая архитектура — `sm_80` (Ampere: `bf16`-MMA и `cp.async`).

## 3. Ядра на CPU (`lumen-cpu`)

Целевой ориентир скорости для CPU-бэкенда — измеренная пропускная способность оперативной памяти DRAM ([performance.md](performance.md)). Основная платформа — процессоры с поддержкой **AVX-512 (VNNI и VBMI)** (AMD Zen 4/5 и серверные Intel); для процессоров без AVX-512 предусмотрен путь на **AVX2**.

### Алгоритм работы CPU-ядра LTQ

1. **Подготовка входного вектора токена:**
   Входной вектор дополняется нулями до $K_{\text{pad}}$, умножается на `suh`, проходит блочное преобразование Адамара-256 и квантуется в `int8` блоками по 256 элементов с `fp32`-масштабом (среднеквадратичная погрешность квантования активаций в `int8` составляет около 0.9% RMS на вызов).
2. **Полосный обход матрицы (`CpuBand16`):**
   Ядро проходит горизонтальной полосой из 16 строк (высота одного тайла) вдоль оси $K$, удерживая аккумуляторы в векторных регистрах. Благодаря раскладке `CpuBand16` тайлы полосы лежат в памяти последовательно.
3. **Декодирование и умножение по 32 веса (две строки тайла):**
   - **Сборка меток (`label`):** метки 16 весов строки получаются побитовым `XOR` (`vpxor`) трёх 16-байтных векторов из предвычисленных таблиц в кэше L1 (9 бит истории + 2 байта строки, 16 КБ таблиц на формат), индексируемых байтами кодовых бит `codes`; биты метки сразу стоят на своих позициях в индексе уровня.
   - **Индекс уровня:** метка объединяется с некодовыми битами (`planes` и `lsb`; в режимах `D2` и `D4` младший бит восстанавливается сдвигом на байт и маской).
   - **Выборка из `lut` в `int8`:** выполняется инструкцией `vpshufb` на AVX2 (для таблиц из 32 или 64 записей — 2 или 4 `vpshufb` + `vpblendvb`) или одной инструкцией `vpermb` на AVX-512 VBMI.
   - **Скалярное произведение:** умножение `int8`-весов на `int8`-вход через `vpmaddubsw` / `vpdpbusd` (с переносом знака на вход через `vpsignb`), накопление суммы строки из 16 весов с масштабом $\text{gain} \times d$ в `fp32` и прибавление `bias` на выходе.

### Результаты измерений, диспетчеризация и разбиение работы на CPU

- **Измеренная скорость** (микробенчмарк на одном потоке Zen 5, данные в L2, путь AVX2, [`ltq-research/src/cpu/tcq_avx2_bench.c`](https://github.com/lumen-inference/ltq-research/blob/main/src/cpu/tcq_avx2_bench.c)): **25.6 млрд весов/с** при $K = 2$, **25.7** при $K = 3$, **23.3** при $K = 4$, **18.0** при $K = 5$ (дробные режимы `D2`/`D4` на 12–14% медленнее). Для сравнения: табличный `IQ3_K` из GGUF выдаёт 35 млрд весов/с, а `IQ5_K` / `IQ6_K` — 20–21 млрд весов/с на том же стенде. По подсчёту инструкций ядро выполняет **~290 операций на 256 весов** против теоретического минимума **~200 операций** для этого формата.
- **Баланс вычислений и памяти на целевых CPU:** на процессорах без AVX-512 (6 ядер Skylake / Zen 2, DDR4 ~40 ГБ/с) на форматах от **3+ бит/вес** ядро гарантированно упирается в пропускную способность памяти, как и GGUF. На сверхнизких форматах **2–2.6 бит/вес** на процессорах без AVX-512 возможен упор в вычисления: до **~25% потери tokens/s** на модели 2.5 бит/вес с текущим ядром (и до **~7%** при достижении теоретического минимума в 200 операций). На процессорах Zen 4/5 с AVX-512 вычислительный запас значительно выше.
- **Таблица диспетчеризации `[ISA][format]`:** набор инструкций `Isa::{Avx2, Avx512Bw, Vnni, Vbmi}` определяется один раз при старте (`is_x86_feature_detected!`); ядра компилируются как `#[target_feature]`-функции, специализированные константами `K`, числа подмножеств и дробного режима, и вызываются через двумерную таблицу указателей на функции `[ISA][format]`.
- **Статическое разбиение работы в спин-пуле:** в слоях MoE единицей работы является пара **`(эксперт, полоса из 16 строк)`** по активным экспертам. У моделей с мелкими экспертами (например, `Qwen3.8-Flash-Next` с матрицами экспертов $640 \times 2560$ и $k = 8$ активными экспертами) образуется $8 \times (1280 / 16) = 640$ единиц работы на `gate_up` и $8 \times (2560 / 16) = 1280$ на `down`, поэтому отсутствие накладных расходов на раздачу задач в спин-пуле критично.
- **Обработка батчей $M > 4$:** при $M > 4$ вычисление на CPU идёт пачками по 4 строки; большой prefill выгоднее передавать на GPU через настройку `"prefill-compute": "cuda:0"` ([раздел 7 architecture.md](architecture.md#7-компилятор-плана-lumen-exec-и-выполнение-шага)).

## 4. Верификация корректности ядер и источники

1. **Побитовая сверка `lumen-ltq`:** эталонный декодер в `lumen-ltq` проверяется на совпадение бит-в-бит с Python-эталоном [`ltq_format.py`](https://github.com/lumen-inference/ltq-research/blob/main/src/ltq_format.py) на золотых фикстурах всех 19 форматов меню и кольцевых таблиц.
2. **Поядерное и сквозное тестирование:** каждое SIMD- и CUDA-ядро проверяется против `lumen-ltq` на матрицах случайных размерностей, а полные графы моделей сверяются через эталонный бэкенд `lumen-ref` ([roadmap.md](roadmap.md)).
3. **Источники:** [NVIDIA CUTLASS & CuTe](https://github.com/NVIDIA/cutlass), [FlashInfer](https://github.com/flashinfer-ai/flashinfer), сравнение `cuda-oxide` против `CUDA C++` на GEMV LTQ: [`results/kbench_gemv_g4.json`](https://github.com/lumen-inference/ltq-research/blob/main/results/kbench_gemv_g4.json) и [`src/kbench/`](https://github.com/lumen-inference/ltq-research/tree/main/src/kbench).
