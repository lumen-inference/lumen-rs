# lumen-rs — ядра на GPU и CPU

Oct 27, 2026 · @Vemloir

На GPU тайлы LTQ декодируют наши ядра на CUDA C++; плотный GEMM уходит в CUTLASS, attention — в FlashInfer. Декод LTQ дороже табличных форматов: у веса есть метка, зависящая от 10 предыдущих кодовых бит. Но метка — линейная функция окна по GF(2), а окно у соседних весов общее, поэтому ядра собирают метки сразу для группы весов из небольших таблиц, а не считают их поштучно. Ниже — устройство ядер и что о них уже измерено прототипами ([`ltq-research/src/cpu/tcq_avx2_bench.c`](https://github.com/lumen-inference/ltq-research/blob/main/src/cpu/tcq_avx2_bench.c), [`ltq-research/src/cuda/ltq_matvec_bench.cu`](https://github.com/lumen-inference/ltq-research/blob/main/src/cuda/ltq_matvec_bench.cu)).

**GPU**

| Оператор | Реализация | Устройство ядра |
| --- | --- | --- |
| LTQ GEMV, M ≤ 8 (decode) | своё ядро | варп на группу строк тайла, x̃ тайла загружается один раз на R строк. Значение веса — одно чтение из общей таблицы «окно 10 бит + некодовые биты → fp16» в shared memory (4–32 КБ на формат) или метка через `popc` по маскам и чтение `lut`, продублированной по банкам; × gain × d; свёртка с x̃ |
| LTQ GEMM, 8 < M ≤ 32 | своё ядро, MMA через CuTe | конвейер в духе Marlin: декод тайлов в shared memory, затем MMA |
| LTQ, M > 32 (prefill) | свой `reconstruct` + CUTLASS | `reconstruct` тайлов в fp16-скретч чанками по M, затем GEMM на CUTLASS |
| MoE (mgemm) | своё ядро | одна сетка на все активные эксперты по таблице дескрипторов; токены сгруппированы по эксперту; у каждого эксперта свой формат |
| Адамар-256 | своё ядро | 8 элементов на lane × 32 lane, бабочки через warp shuffle; слит с ⊙suh |
| Декод строк | своё ядро | выборка строк таблицы, декод колец LTQ (или int8) с масштабом кольца, обратный Адамар блоками B, ⊙ знаки |
| Attention | FlashInfer + свои варианты | flash-attention по страничному KV; параметры: окно, синки, маска, раскладка KV (K и V, только V, чужой кэш) и её битность, выходной σ-гейт из `q_proj` (`qwen3_next`, `qwen3_5_*`), список блоков от индексатора, scaling, softcap; decode — split-K |
| Индексатор QSA | своё ядро | скоринг блоков relu(q·k) по головам, top-k блоков, усреднение завершённых блоков |
| Gated DeltaNet | своё ядро (образец — flash-linear-attention) | chunked-алгоритм на prefill, рекуррентный шаг на decode (с L2-нормой Q и K), causal short conv1d, выходная `RMSNormGated` (`norm(y) · silu(z)` по V-голове) |
| Hyper-connections | своё ядро | смешивание потоков перед подблоком, впрыск выхода, свёртка потоков перед финальной нормой |
| RMSNorm (обычная, `1 + w` и `RMSNormGated`), RoPE, SwiGLU/GeGLU (вкл. clamp gpt-oss), residual, softcap | свои ядра | поэлементные операции и редукции, слитые с соседями |
| Router + top-k, сэмплинг | своё ядро | варповые редукции, Philox |

- **RoPE** задаётся `RopeSpec`: default; partial (Qwen) — вращаются первые r измерений с частотами θ^(−2i/r); proportional (p-RoPE, Gemma 4) — частоты θ^(−2i/d) для первых p·d/2 углов при полном d, остальные углы нулевые, rotate-half по всей голове, поэтому вращаются измерения \[0, p·d/2) и \[d/2, d/2 + p·d/2); YaRN; M-RoPE — углы делятся на секции (t, h, w).
- **Attention в CUDA-графе.** Размер сетки в графе запечён, а длины меняются каждый шаг, поэтому разбиение split-K считается на устройстве по длинам из `StepInputs`. Страничный decode FlashInfer принимает список страниц на запрос, поэтому список блоков индексатора передаётся в этом виде; чего в нём нет (блоки QSA по 4 токена внутри страниц по 64, K = V, квантованный KV), проверяет прототип в начале фазы 4, до GEMV.
- **Стоимость декода LTQ.** Минимум — около 5–6 целочисленных операций и одно чтение shared memory на вес. Прототип GEMV на fp32-FMA (RTX PRO 6000) упирается в декод: 0.45–0.72 от потолка такого же ядра для 4-битного табличного формата. Конфликты банков общей таблицы оказались некритичны. Чтобы на 5070 Ti при batch 1 упираться в VRAM, а не в декод, нужны int8-активации с `dp4a`, выборка значений через `prmt` и метки сразу на 32 веса из битовых плоскостей. Это первая задача фазы 4; `__dp4a` и `__byte_perm` (`prmt`) — обычные интринсики CUDA.
- PDL (programmatic dependent launch через `cudaLaunchKernelEx`, sm\_90+) сокращает паузы между соседними ядрами decode: следующее ядро начинает пролог, пока предыдущее заканчивает.
- Нижняя граница — sm\_80 (Ampere): bf16-MMA и `cp.async`. В библиотеке ядер есть SASS для всех поддерживаемых архитектур, поэтому драйвер докомпилирует PTX только на GPU новее сборки.

**CPU** — эталон скорости — измеренный потолок DRAM ([performance.md](performance.md)). Основная цель — Zen 4/5 (AVX-512 VNNI и VBMI); Intel без AVX-512 и Zen 2 идут путём AVX2.

1. Вход по строке токена: дополнить нулями до K\_pad, ⊙suh, блочный Адамар-256, затем квантизация в int8 блоками по 256 с fp32-масштабом.
2. Ядро идёт полосой из 16 строк (группа строк тайла) по K, аккумуляторы в регистрах. На 32 веса (две строки тайла):
   - метки — XOR трёх 16-байтных векторов из таблиц, индексированных байтами кодовых бит (9 бит истории + 2 байта строки, 16 КБ таблиц на формат, лежат в L1); биты метки сразу стоят на своих местах в индексе уровня;
   - индекс уровня = метка | некодовые биты (сдвиг и маска плоскостей; у D2 и D4 младший бит восстанавливается сдвигом на байт и маской);
   - значение int8 — `vpshufb` по таблице уровней (16 записей; 32 или 64 записи — 2 или 4 `vpshufb` + `vpblendvb`, на VBMI — один `vpermb`);
   - `vpmaddubsw` / `vpdpbusd` с int8-входом (знак переносится на вход через `vpsignb`), сумма 16 весов строки — с масштабом gain × d в fp32.
3. Выход: + bias.

- **Измерено** (AVX2, один поток Zen 5, данные в L2): 25.6 млрд весов/с на K = 2, 25.7 на K = 3, 23.3 на K = 4, 18.0 на K = 5; дробные режимы на 12–14 % медленнее. Для сравнения: `IQ3_K` 35, `IQ5_K` / `IQ6_K` 20–21 на том же стенде. По подсчёту инструкций ядро тратит ~290 операций на 256 весов против теоретического минимума ~200 для этого формата.
- **Что это значит для целевых CPU** (6 ядер Skylake / Zen 2, DDR4 ~40 ГБ/с): на 3+ бит/вес ядро упирается в память, как GGUF. На 2–2.6 бит/вес по оценке — в вычисления: до ~25 % потери tokens/s на модели 2.5 бит/вес с текущим ядром, до ~7 % в минимуме. На Zen 4/5 с AVX-512 запас больше. Проверяется на реальных CPU в фазе 3.
- Точность int8-активаций — около 0,9% RMS выхода на вызов. Уровни таблиц в int8 — с масштабом формата; влияние округления на KLD проверяется дифф-тестами против `lumen-ref`.
- Диспетчеризация: `Isa::{Avx2, Avx512Bw, Vnni, Vbmi}` определяется один раз при старте; ядра — `#[target_feature]`-функции, специализированные константами `K`, числа подмножеств и дробного режима; таблица указателей \[ISA\]\[формат\].
- Работа делится статически: в MoE единица — пара (эксперт, полоса из 16 строк) по активным экспертам. У маленьких экспертов (Qwen3.8-Flash-Next: 640 × 2560) единиц много, поэтому накладные расходы на раздачу работы критичны — их и снимает спин-пул.
- M > 4 идёт чанками по 4 строки. Большой prefill выгоднее отдать GPU — `prefill-compute` в [разделе 5 architecture.md](architecture.md#5-планировщик-и-пайплайн).

**Корректность.** Эталон `lumen-ltq` сверяется бит в бит с [`ltq-research/src/ltq_format.py`](https://github.com/lumen-inference/ltq-research/blob/main/src/ltq_format.py) на golden-фикстурах: тайлы всех форматов меню, полученные реальным квантователем, и целые матрицы с масштабами и поворотом. CPU- и GPU-ядра сверяются с эталоном на случайных формах. Целиком модели сверяются через `lumen-ref` ([roadmap.md](roadmap.md)).
