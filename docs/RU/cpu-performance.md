# CPU-ядра: корректность и измерения

[English](../EN/cpu-performance.md)

**Текущая C-реализация:** [CPU Linear](cpu-linear.md). Описанные ниже исторические быстрые FP32-пути проверялись с допуском и не выполняют новое требование побитового совпадения. Их скорость нельзя выдавать за скорость новых точных C-кернелов.

> Отчёты об исторических замерах, исходные данные экспериментов и снимки старого кода хранятся локально в `docs/benchmarks/` и исключены из Git. Обычные пути к этим материалам служат справкой, а не ссылками для скачивания.

Здесь собраны подробности существующей реализации и история её измерений. Для знакомства с общим подходом сначала прочитайте [описание кернелов](kernels.md) и [правила измерений](performance.md). Незнакомые термины можно найти в [словаре](glossary.md).

> Этот документ относится к текущему Rust/C/LLVM CPU-пути. Исторические обозначения Lumen, команды и измерения сохранены для сравнения при [переносе Velri на C и Vulkan](architecture.md). Это не отчёт о новом C runtime.

`lumen-cpu` исполняет текущий dense-f32 граф через `CpuExecutor`. Доступны Scalar, AVX2 с FMA и AVX-512F. Поддержка инструкций проверяется при запуске; принудительный выбор недоступного ISA возвращает ошибку. Общий бинарник не требует `target-cpu=native`. `Isa::detect()` выбирает самый широкий поддержанный вариант; это не автоподбор по скорости на конкретной задаче.

`CpuExecutor::new(isa, threads)` создаёт постоянный частный пул работников, если потоков больше одного. На Linux работники закрепляются в пределах CPU-маски вызывающего потока: сначала выбираются физические ядра, затем их SMT-соседи. Порядок работников учитывает NUMA-узел, общий кеш, ядро и SMT. Топология берётся у ОС, без предположений о нумерации CPU конкретного процессора. Маска вызывающего потока и системные настройки не меняются. Выбор внутреннего диспетчера описан ниже.

`CpuExecutor::with_threading(isa, CpuThreading { .. })` также поддерживает автоматический размер (`threads = 0`), резерв ядер, распределение по NUMA-узлам и политику привязки. `Auto` сообщает причину перехода к свободному размещению, `None` отключает привязку, `Required` возвращает ошибку, если закрепление не удалось. Конструктор дожидается проверки всех работников. Явное число потоков сохраняется, включая превышение числа CPU в свободном режиме; превышение лимита Rayon отклоняется. Результат доступен через `worker_cpus()` и `placement_note()`. `Default` по-прежнему исполняет на вызывающем потоке; адаптивный выбор для матриц уточняет, стоит ли использовать работников пула. Однопоточный пул с `Required` выполняет матрицы и attention на закреплённом работнике.

Параметры [CPU-конфига](rust-config.md) передаются в этот API через `lumen_engine::cpu_executor`. Адаптер готов, но CLI для реальной модели ещё не подключён. Синтетический декодер принимает число потоков: например, `cargo run --release -p lumen-exec --example dense_decode -- avx512 32`.


## Сравнение с AOCL, BLIS, OpenBLAS и LIBXSMM (2026-11-08)

Общий FP32-стенд сравнил текущий Lumen с AOCL-BLAS 5.3.2, upstream BLIS 2.1, OpenBLAS 0.3.34 и LIBXSMM 2.1.0. Итоговая серия: 405 отдельных процессов, по пять повторов, по 21 отсчёту; 108 проверок корректности прошли. На Ryzen 9 9950X с лимитом 16 потоков prepared GEMM 256×4096×4096 дал **4,381 TFLOPS у Lumen**, **4,309 у AOCL prepared** и **4,291 у LIBXSMM с измерительным адаптером**. Ориентир арифметического потолка по частотным счётчикам этих запусков Lumen — **4,823 TFLOPS**, то есть около **90,8%** для нашего результата.

Cached GEMV 1024×1024: **1,075 TFLOPS у Lumen prepared**, 0,733 у OpenBLAS, 0,641 у LIBXSMM; условный ориентир доставки весов из L2 — **2,689 TFLOPS**, доля Lumen около **40,0%**. BLIS выполнял этот GEMV одним потоком при большем заданном лимите. На узком GEMM N=4 медиана LIBXSMM выше нашей: **2,045 против 1,963 TFLOPS**, с большим разбросом по процессам. Streaming GEMV с весами 512 МиБ у основных многопоточных вариантов лежит около **0,033–0,036 TFLOPS**; физический потолок RAM не установлен. Это повторные линейные вызовы, без расходов графа; подготовка весов измерена отдельно. Все формы, потоки, стоимость подготовки, исходники и ограничения (`../benchmarks/linear-libraries-2026-11-08/README.md`).

## Подготовленные веса в графе и проверки результатов (2026-11-08)

`Program::prepare` теперь выбирает физический `DenseLayout` через исполнителя и один раз упаковывает веса, используемые только Linear. Padding учитывается до выделения памяти; несколько Linear и сеансов разделяют одного владельца. Общие embedding/projection остаются в одном row-major представлении. Шаг графа заимствует веса без копирования и выделения метаданных. Проверки NaN/Inf сохранены, но переписаны в редукцию, которую компилятор векторизует.

В сравнении полного синтетического пути embedding → Linear → проверка → reset на 16 закреплённых работниках cached GEMV вырос с **0,507 до 0,643 TFLOPS для AVX2**, с **0,537 до 0,645 для AVX-512**. GEMM 256×4096×4096 вырос с **1,919 до 2,038** и с **3,175 до 3,625 TFLOPS** соответственно. Это эффективная производительность с расходами графа. Отдельный prepared GEMV остался около **1,05–1,07 TFLOPS**, AVX-512 GEMM — около **4,39 TFLOPS**; в расширенной серии есть небольшие регрессии до 2,8%. Арифметический C-кернел не менялся. Профили, замеры, проверки ARM и ограничения (`../benchmarks/linear-bottlenecks-2026-11-08/README.md`).

В итоговых таблицах также приведены ориентиры потолка и доля от них: GEMM на 16 ядрах — **2,473 TFLOPS AVX2 / 4,803 TFLOPS AVX-512**, cached GEMV при доставке весов из L2 — **2,674 TFLOPS**. Это условные расчёты по частотам предыдущей калибровки; точный потолок последних запусков не измерен. Самостоятельный AVX-512 GEMM достигает около **91,4%** такого ориентира, cached GEMV — **40,0%**; полный граф — **75,5%** и **24,1%** соответственно.

## Уточнение циклов и измерений (ночь 2026-11-08)

Остатки prepared GEMV теперь переиспользуют групповую арифметику и независимое накопление для одиночного тайла, без увеличения объёма хранимых весов. В сохранённом сравнении AVX2 N1/M1025/K1023 на 16 работниках ускорился **0,758 → 0,931 TFLOPS** (парный прирост +22,48%), а M256/K1024 — **0,343 → 0,407 TFLOPS** (+19,41%). Крупный prepared GEMM AVX512 остаётся около **4,4 TFLOPS**. Изменение принято с ограничениями: короткие вызовы M49/K2–4 на одном закреплённом работнике сохраняют регрессии, а выбор Adaptive остаётся нестабильным. Замеры, проверки и ограничения (`../benchmarks/linear-night-2026-11-08/prepared-tail/README.md`).

Общий LLVM-генератор использует две независимые цепочки накопления GEMV, когда геометрия целевого вектора объединяет две узкие полосы подготовленных весов. Для одной широкой полосы сохраняется прежний цикл. Это не проверка модели CPU; формат весов и объём памяти не изменились. В повторном сравнении на 16 работниках AVX2, матрица 1024×1024, получено **0,892 → 1,021 TFLOPS**. AVX-512 остаётся около **1,07 TFLOPS**. Случай K=3 потерял около 2%; измерения других форм и ограничения сохранены в ночном отчёте (`../benchmarks/linear-night-2026-11-08/README.md`).

Блочный GEMM теперь переиспользует веса между шестью строками, если хватает регистров целевой архитектуры. Прямые проходы по всему K и дополненные выходные хвосты сохраняют четыре строки: переход на шесть замедлял часть малых и узких матриц. В отдельном сравнении подготовленного GEMM 256×4096×4096 на 16 работниках получено **2,111 → 2,259 TFLOPS для AVX2** и **4,310 → 4,413 для AVX-512**; cached GEMV практически не изменился. Генерация арифметики остаётся общей, формат весов и ограничения временной памяти сохранены. Скорость на реальном ARM пока не измерена.

Узкие подготовленные матрицы теперь хранят только нужные веса: при M=1/K=1024 AVX-512 использует **4 КиБ вместо 256 КиБ**, а полный вызов даёт **0,00195 → 0,112 TFLOPS**. Это устранение лишнего дополнения, а не такой же прирост широких слоёв. Общий цикл подготовки, её выделение в холодный код и выравнивание входа prepared-кернела на 32 байта проверены вместе. В широком cached GEMV AVX2 остаётся возможная потеря около **1%**; первоначальные 5% для пула из 32 потоков не повторились в дополнительном сравнении. Исправление принято с этим ограничением. На этапе исправления хранения прошли 151 native release-тест и по 17 тестов AArch64/ARMv7 через QEMU; все исходные замеры и отклонённые варианты сохранены в ночном отчёте.

Адаптивный prepared GEMM теперь также подбирает разбиение по строкам и столбцам. В итоговом сравнении вытянутый AVX2 GEMM N4096/M256/K4096 ускорился с **1,960 до 2,236 TFLOPS**, а нечётный N1025/M257/K4096 — с **1,333 до 2,054 TFLOPS** (парные изменения +13,81%/+54,18%). Основной AVX-512 GEMM остаётся около **4,38 TFLOPS**, prepared cached GEMV — около **1,07 TFLOPS**. Сохранены и потери: однопоточный AVX-512 M1 замедлился на 9,02%, обычный cached GEMV с Adaptive — на 5,05% по парным блокам. Последнее совпадает с изменением выбранного режима чтения весов и не доказывает замедление самой арифметики на 5%. Повторная проверка исходного режима в конце обучения не гарантирует оптимального выбора. Итоговые замеры и ограничения (`../benchmarks/linear-night-2026-11-08/README.md`) включают контрольные серии и отклонённое сокращение однопоточного пути. Итоговые исходники прошли 160 release-тестов CPU, 135 без default features, 270 тестов workspace и по 39 целевых тестов на ARM/QEMU, а также форматирование и Clippy.

Число потоков в конфигурации задаёт размер пула. В замерах cached GEMV с Fixed/Required пул на 32 потока использует **16 активных физических работников**; метка `cached32` не означает 32 одновременно считающих SMT-потока. Число задач может дополнительно ограничивать активность: для N96/M3 получается двенадцать задач при шестнадцати настроенных работниках. Небольшая работа может остаться на вызывающем потоке. Adaptive может выбрать другую группу; она указана в сохранённом расписании.

Профили и диагностические частотные счётчики уточнили прежнее сравнение с потолком: частота реального GEMM отличается от синтетического FMA-теста, в котором значения сходятся к постоянным битовым шаблонам. Снимки счётчиков вокруг измеряемого участка дали для AVX-512 GEMM **4,37 TFLOPS** при условном арифметическом ориентире **4,80 TFLOPS**, рассчитанном по наблюдаемой частоте. Это около 91% данного ориентира, а не измеренная загрузка аппаратуры и не доказательство, что осталось лишь 9% запаса.

Для cached GEMV ограничение другое. По опубликованной AMD ширине пути L2→L1D и отдельно наблюдавшейся частоте получается условный ориентир **2,67 TFLOPS** на 16 ядрах, если веса доставляются из L2 и прочие затраты пренебрежимо малы. Реальный полный вызов остаётся около **1,07 TFLOPS**. В отдельной диагностике с 256 повторениями внутри каждого задания GEMV дал **1,72 TFLOPS**, но это другой режим исполнения. Контрольное чтение показало похожую медиану с большим разбросом; считать его физическим потолком нельзя. Источники, диапазоны и условия сравнения приведены в ночном отчёте (`../benchmarks/linear-night-2026-11-08/README.md`).

Опция `LUMEN_BENCH_WARMUP_MS` задаёт минимальную длительность разогрева вне замера; по умолчанию 0 сохраняет прежний минимум вызовов. Длительный разогрев сам по себе не гарантирует стабильную частоту или размещение потоков.

## Подготовленные неизменные веса (2026-11-08)

С `llvm-kernels` вызов `cpu.prepare_linear(&weights, m, k)` создаёт собственную выровненную матрицу. Если выход уже одного SIMD-вектора целевой архитектуры, веса сохраняются по строкам без дополнения; более широкие матрицы получают блочное размещение с дополненным последним блоком. Формат и соответствующий кернел выбираются вместе при подготовке. Объект можно многократно передавать в `cpu.linear_prepared(&input, &prepared, bias, &mut output)`. Подготовка хранит одну копию; `prepared.payload_bytes()` сообщает занимаемый объём. Исходную матрицу после этого можно освободить. Если сохранить оба объекта, останутся обе копии. Подготовленный объект требует той же политики ISA исполнителя; его можно разделять через ссылку или `Arc`.

Повторные вызовы не упаковывают веса. Большой prefill сохраняет блокирование для кеша и до 64 КиБ промежуточных сумм на активный кернел, плюс небольшой буфер выходного хвоста. Две попытки убрать блокирование замедлили GEMM и были отклонены. GEMV обрабатывает независимые выходы нескольких полос весов; геометрия определяется компилятором. История подбора работников отделена от обычных матриц и доступна через `prepared_linear_schedule(rows, m, k)`.

Для подготовленного GEMM адаптивная политика также сравнивает до трёх разных разбиений по строкам и столбцам на полной группе физических работников. Запрашиваются 2, 4 или 8 групп строк; реальные участки вычисляются из текущей формы и ширины блока. Прежние варианты числа работников сохраняются. Поле `requested_row_groups` показывает запрос до округления. Режим Fixed сохраняет прежнее разбиение.

На 16 закреплённых работниках Fixed cached GEMV дал **0,891 → 1,003 TFLOPS**, основной GEMM — **4,291 → 4,362**, GEMM с длинным K — **4,014 → 4,363**. Без закрепления работников подготовленный GEMM проиграл обычному пути; первоначальную упаковку также нужно окупить повторными вызовами. Эти исторические замеры относятся к явному API; последующая интеграция в граф с учётом бюджета описана выше. Все результаты, ограничения и воспроизведение (`../benchmarks/linear-prepared-2026-11-08/README.md`).

Все рабочие пулы теперь используют один фиксированный протокол отправки, включая свободное размещение и один Required-работник. Привязка к ядрам остаётся отдельной настройкой. Это убирает периодическое выделение блоков очереди Rayon, найденное тестом ARM. Обычный cached GEMV без закрепления дал **0,218 → 0,649 TFLOPS**. Rayon остался только в сравнительных тестах; следующие разделы сохраняют историю прежних диспетчеров.

## Адаптация числа работников

По умолчанию `CpuExecutor` использует `LinearPolicy::Adaptive`. Для каждой формы матриц он сравнивает исполнение на вызывающем потоке, половину и всю доступную группу физических ядер, а при наличии SMT — также настроенную группу логических работников. Без подтверждённой топологии сравниваются группы настроенного пула. GEMV может выбрать обычное или последовательное чтение строк весов, в том числе на одном, двух и четырёх работниках. Ёмкость LLC задаёт начальную подсказку, а выбор уточняют измерения реальных вызовов. Названия процессоров в выборе не участвуют.

Обучение одной формы использует до 36 успешных вызовов, получивших доступ к данным обучения, если запись не вытесняется. Каждый вызов вычисляет результат ровно один раз; дополнительных матриц, копий весов и выделений памяти нет. Конкурирующий вызов, обошедший занятую блокировку обучения, не добавляет наблюдение. При создании исполнителя выполняются четыре пустых отправки в пул для оценки цены передачи работы. Проба исполнения на вызывающем потоке допускается по оценке времени работы и передачи задания; гарантии задержки эта оценка не даёт. У каждого кандидата есть свой обычный вызов для прогрева и три измеряемых вызова. После сравнения кандидатов исходный режим получает ещё один вызов для прогрева и три измеряемых вызова. Для переключения медиана кандидата должна быть лучше лучших результатов исходного режима в начале и конце обучения. Финальная проверка не возобновляет пропущенные пробы исполнения на вызывающем потоке. Один случайно быстрый замер кандидата не определяет выбор. Финальная проверка может выявить заниженную скорость исходного режима в начале обучения. Если оба окна измерений отличаются от последующей работы, выбор всё ещё может оказаться неудачным. После выбора таймер и блокировка обучения уходят из обычного пути. Ограниченный кеш хранит 32 записи; вытеснение может запустить обучение заново. Для прогрева доступна константа `LinearPolicy::MAX_LEARNING_CALLS`. У одного закреплённого работника `Required` вычисления остаются на работнике.

Первые вызовы могут иметь другую задержку, чем установившийся режим. `cpu.linear_schedule(rows, m, k)` позволяет посмотреть обученное ограничение числа задач и режим GEMV вне измеряемого участка; `None` означает, что подходящей завершённой записи нет. При изменении нагрузки системы, размещения памяти или переходе между холодными и горячими весами старый выбор может устареть: постоянного переобучения нет. Создание нового исполнителя сбрасывает историю. `cpu.with_linear_policy(LinearPolicy::Fixed)` выбирает прежний детерминированный диспетчер для сравнений и задач, где обучение нежелательно. Фиксированный режим сохраняет его старые пороги; адаптивный их не использует.

Стенд `bench_linear` принимает `LUMEN_LINEAR_POLICY=adaptive|fixed`, явно сообщает режим и прогрев. Результаты и ограничения проверки (`../benchmarks/linear-adaptive-2026-11-02/README.md`). Ограничение ресурсов на 9950X проверяет работу с меньшим пулом; оно не заменяет замеры другого CPU. ARM/QEMU проверяет корректность, а не скорость ARM.

## Передача коротких задач работникам (2026-11-07)

Закреплённый пул отмечает спящих работников в битовых масках. При отправке задания забираются только биты выбранной группы; `unpark` вызывается для этих работников. Активно ожидающим работникам разрешение на пробуждение не нужно. Цепочка атомарных операций AcqRel RMW связывает публикацию задания с регистрацией сна и последней проверкой работника перед сном. Биты исключённых работников сохраняются. Состав групп определяется существующей топологией, без условий по модели CPU.

При неизменной ручной арифметике кешируемый GEMV `[1024, 1024]` дал **0,865 → 0,945 TFLOPS** на 16 работниках и **0,880 → 0,950** на 32. Общий LLVM-путь тоже выигрывает от пула, но арифметический эксперимент сохраняет регрессии отдельных форм. Проверены гонки при входе в сон, группы через границы машинного слова и обе разрядности ARM. Измерения, оставшиеся потери и проверки (`../benchmarks/linear-gemv-followup-2026-11-07/README.md`).

## Общий LLVM-кернел

### Экспериментальная обработка остатка SIMD (2026-11-07)

Фича `lumen-cpu/experimental-dot-kernels` включает векторную обработку остатка в общем LLVM-кернеле и одновременно включает `llvm-kernels`. После развёрнутого цикла кернел обрабатывает оставшиеся полные SIMD-векторы; скалярным остаётся меньше одного вектора. Каждый выход суммируется отдельно средствами LLVM. Обычная `llvm-kernels` сохраняет прежний алгоритм. Геометрия определяется целевой платформой; таблиц моделей CPU и отдельной реализации ARM нет.

Кандидат прошёл тесты workspace и release, Clippy, проверку Rust 1.89 и исполнение на AArch64/ARMv7 через QEMU. Новые тесты проверяют точные численные результаты, bias, невыровненные входы, промежутки между выходами, независимость NaN/Inf и границы защищённых страниц. Покрыто сочетание полного развёрнутого цикла, векторного остатка и скалярного хвоста. Скорость настоящего ARM пока не измерена.

Кандидат **включается только явно**. В продолжении прежний цикл и цикл с векторным остатком разделены на функции; выбор зависит от геометрии целевого вектора и цепочек накопления. Fixed K=65 восстановился с **0,078288 до 0,091945 TFLOPS**; с обновлённым обучением и пулом Adaptive cached8 дал **0,636343 → 0,740650**. Fixed cached8 по-прежнему ниже предыдущей экспериментальной сборки на 7,2%, а обновлённой сборки без фичи — на 2,0%. В новом отчёте (`../benchmarks/linear-gemv-followup-2026-11-07/README.md`) сохранены все формы, отклонённые варианты, исходники и исходные измерения. Первый отчёт (`../benchmarks/linear-dot-2026-11-07/README.md`) оставлен как история этапа. Цель достижения аппаратного потолка остаётся открытой.

Проверки также нашли прежнюю гонку запуска свободно размещённого пула Rayon: служебная память стеков могла выделяться после возврата конструктора. В той версии конструктор дожидался пустого broadcast на каждом работнике; нынешний фиксированный пул также устраняет периодические выделения памяти очередью. После исправления тест аллокаций прошёл 80 запусков подряд, включая обучение адаптивной политики и установившееся исполнение. Выделения при создании пула остаются вне вызовов инференса.

Приём обработки векторного остатка сопоставлен с [MIT-проектом gemm](https://github.com/sarah-quinones/gemm/blob/main/gemm-common/src/gemv.rs) и реализован в нашем генераторе без копирования чужих исходников и добавления зависимостей. Для сравнения нужны отдельные сборки с `--features llvm-kernels` и `--features experimental-dot-kernels`; `--all-features` тоже включает эксперимент. Бенчмарк печатает `llvm_dot_schedule=baseline|experimental`.

### Существующий путь

Cargo feature `llvm-kernels` включает общий высокопроизводительный путь GEMM/GEMV для dense-f32. С ним обычные `CpuExecutor::default`, `new` и `with_threading`, включая фабрику engine, выполняют `Linear` сгенерированным кодом. Для engine и CLI есть одноимённый feature. `CpuExecutor::with_native_linear(isa, options)` оставляет явный доступ к прежним AVX-кернелам для сравнения и отката. Сборка без feature сохраняет прежний путь и не требует LLVM.

Один генератор (`../../crates/lumen-cpu/codegen/linear.rs`) описывает векторные редукции, внешние произведения и транспонирование весов. Общее расписание (`../../crates/lumen-cpu/codegen/linear.c`) и упаковка (`../../crates/lumen-cpu/codegen/packing.c`) задают переиспользование весов между строками, границы плиток и добавление bias. Ширина плитки уменьшается при узком выходе, а число строк в ней выводится из того же бюджета регистров. LLVM TargetTransformInfo сообщает ширину вектора и число регистров для целевой платформы; из них выводится геометрия. Отдельного алгоритма ARM и таблиц под модели CPU нет. AVX2/FMA и AVX-512F различаются флагами компиляции и проверяются перед вызовом.

Размеры rows/M/K, шаг строки выхода и bias остаются параметрами времени выполнения. Хвосты строк, столбцов и K не требуют выравнивания или дополнения пользовательских тензоров. Большой GEMM использует до 32 КиБ упакованных весов и до 64 КиБ промежуточных сумм на стеке активного вызова. Полной копии весов и heap-аллокаций при успешном вычислении нет. Кешируемый GEMV переиспользует вход между несколькими выходами; матрицы, превышающие обнаруженную суммарную ёмкость кеша, читаются последовательными строками через тот же генератор редукции.

Для сборки нужны Clang/LLVM 18+ и development-пакет LLVM с заголовками, библиотекой и `llvm-config`. Clang и `llvm-config` должны иметь одинаковую основную версию; локально проверен 21.1.8. `LLVM_CLANG`, `LLVM_AR`, `LLVM_CONFIG` и `LLVM_CXX` позволяют задать пути. Небольшая C++-утилита запрашивает свойства целевой платформы на машине сборки; она и libLLVM **не входят в готовое приложение**. Кернелы компилируются заранее для Cargo TARGET. JIT и компилятор во время инференса не нужны, новых Rust-крейтов нет.

```sh
cargo build --release -p lumen-cli --features llvm-kernels
cargo build --release -p lumen-cpu --features llvm-kernels --example bench_linear
LUMEN_LINEAR_KERNEL=llvm taskset -c 0-15 target/release/examples/bench_linear avx512 16 256 4096 4096 21 required 0 2 0
LUMEN_LINEAR_KERNEL=native taskset -c 0-15 target/release/examples/bench_linear avx512 16 256 4096 4096 21 required 0 2 0
```

Прямой API: `lumen_cpu::llvm_linear(x, w, bias, out, m, k)`. Явное создание исполнителя: `with_llvm_linear(options)` либо `with_llvm_linear_for_isa(isa, options)`. Подготовка и вызов Program не меняются. Входные буферы могут совпадать друг с другом, выход с ними не пересекается; неверные размеры отвергаются до записи. Допускаются изменение порядка суммы, объединение multiply-add и изменение знака нуля. Предположения об отсутствии NaN/Inf не используются; длинные редукции и упакованный путь проверены отдельно во всех доступных профилях.

Пул также учитывает реальный OS CPU вызывающего потока. Если выбранный работник закреплён на том же CPU, вызывающий поток и этот работник прекращают активное ожидание раньше. Это устраняет обнаруженную конкуренцию за один CPU без изменения affinity пользователя. Корректность публикации и времени жизни заимствованных заданий не зависит от этой подсказки.

Проверены x86-64 AVX2/AVX-512 и исполнение того же генератора на AArch64 и ARMv7 под QEMU, включая 32-битный ABI, упаковку и выходы с промежутками. Скорость настоящего ARM пока не измерена. Итоговые замеры, ревью, исходники и ограничения (`../benchmarks/linear-packed-2026-11-01/README.md`). Предыдущий скалярный прототип (`../benchmarks/linear-universal-2026-11-01/README.md`) сохранён как история измерений и заменён этим путём.

## Реализованные операции

- **Linear:** decode GEMV использует независимые аккумуляторы; малые группы токенов разделяют загрузки весов. Prefill упаковывает веса в ограниченные стековые блоки и вычисляет несколько строк внешними произведениями. Работники делят выходные признаки, а при узком выходе — ещё и группы токенов. Полной дополнительной копии весов нет. Упаковка требует до 8 КиБ для AVX2 и до 32 КиБ для AVX-512 на работника. Выбранные AVX-512 плитки дополнительно используют до 64 КиБ временных сумм: всего до 96 КиБ стекового буфера. Подробности текущего выбора кернелов и замеры приведены ниже.
- **RMSNorm:** SIMD-редукция и масштабирование, обычные веса и `1+w`. Для экстремальных величин есть скалярный расчёт с более широким накоплением.
- **SwiGLU / GeGLU:** векторное приближение экспоненты через приведение диапазона и полином шестой степени. Редкие численно сложные элементы обрабатываются отдельно. GeGLU соответствует tanh-аппроксимации GELU; clamp симметрично ограничивает оба входа.
- **Residual и RoPE:** векторные умножения/сложения. Углы RoPE пока вычисляются скалярно в f64 и переиспользуются между головами; это остаётся затратной частью.
- **Attention:** причинное полное/оконное GQA, разные размерности K/V и общее хранилище. QK вычисляется один раз для позиции, softmax обрабатывается блоками по 64 scores с 512 байтами стекового буфера. Полной матрицы scores или копии истории нет. Decode распределяет независимые головы между работниками; prefill распределяет строки запросов. Оценка ошибки dot учитывает компенсацию больших слагаемых и scale; при повышенном риске dot пересчитывается в f64.
- **Lookup и append:** копирование срезов без покомпонентного обращения к реестру буферов.

Бэкенд получает проверенные входные срезы и отдельный изменяемый выход один раз на операцию. Входы могут ссылаться на один буфер; выход не может пересекаться с ними. После ядра проверяется конечность результата, поэтому ошибочный шаг по-прежнему не подтверждает изменённую историю.

## Проверки

`cargo test --workspace` включает сравнение каждого доступного ISA с независимыми эталонами. Проверяются невыровненные данные, остатки векторов, нечётные матрицы, bias, разные головы и окна, позиции RoPE, экстремальные числа и ошибочные размеры. Составной декодер также сравнивается с Python-фикстурой при всех 32 разбиениях входа. Общие и производные хранилища и восстановление после ошибки проверяются и для CPU-исполнителя.

CI дополнительно запускает `cargo test --release -p lumen-cpu -p lumen-exec`, чтобы проверять оптимизированный машинный код. Недоступный ISA пропускается; для полного покрытия обеих SIMD-реализаций нужна машина с AVX-512F и AVX2/FMA. Минимальная версия Rust — 1.89; AVX-512 intrinsics доступны в [стандартной библиотеке](https://doc.rust-lang.org/core/arch/x86/fn._mm512_fmadd_ps.html).

Допуски указаны в самих тестах: например, векторные операции обычно проверяются с абсолютной и относительной ошибкой порядка нескольких `1e-6`, attention — `2e-5 * max(1, abs(reference))` на тестовом наборе, декодер — с абсолютной ошибкой `2e-5`. Это проверяемые диапазоны для фикстур, а не универсальная гарантия для любых плохо обусловленных входов. SIMD/FMA и порядок суммирования изменяют округление.

## Как воспроизвести измерения

```sh
cargo build --release -p lumen-cpu --examples
# ISA, потоки, токены, выходные признаки, входные признаки, число замеров, необязательная привязка:
taskset -c 0 target/release/examples/bench_linear avx512 1 128 2048 2048 21
taskset -c 0-15 target/release/examples/bench_linear avx512 16 1 8192 8192 21 required
# Отдельные операции: ISA, число замеров, число повторений малых ядер:
taskset -c 0 target/release/examples/bench_ops all 21 512
# Attention: ISA, потоки, токены, история, Q-головы, KV-головы, размеры K/V, замеры:
taskset -c 0-7 target/release/examples/bench_attention avx512 8 1 2048 32 8 128 128 25 required
# Наблюдаемая скорость чтения: ISA, потоки, МиБ, число замеров:
taskset -c 0-15 target/release/examples/bench_ceiling avx512 16 256 21
# Синтетическая скорость FMA в регистрах: ISA, потоки, итерации, замеры:
taskset -c 0-15 target/release/examples/bench_fma avx512 16 1000000 9
```

`bench_linear` включает проверки размеров и работу пула, но не подготовку графа, привязку буферов или итоговую проверку конечности из диспетчера. Время создания буферов и прогрева исключено. «Effective GB/s» — минимальный объём весов, входа и выхода, делённый на время; это не измеренный трафик контроллера памяти. В `bench_ops` скорость QK+PV не учитывает softmax FLOPs. Проверяйте checksum и допуски, а не побитовое совпадение разных ISA.

Два калибровочных примера дают наблюдаемые ориентиры на том же оборудовании: потоковое чтение и независимые FMA в регистрах. Ни один не является универсальным физическим потолком модели. Кэши, ограничения частоты и мощности, число активных ядер, SMT, планировщик ОС и размер задачи меняют результат. Скорость реальной генерации должна измеряться отдельно после подключения реальной модели.

`bench_linear` и `bench_attention` печатают проверенную привязку работников; `none` позволяет сравнить свободное размещение. После аргумента affinity у `bench_linear` доступны смещение выхода, число вызовов на выборку и смещение входа/весов. Смещения задаются в элементах f32 от границы 64 байт (`0..15`); выбранное выравнивание печатается в отчёте. Например, `avx512 16 256 4096 4096 41 required 0 8 0` задаёт 64-байтное выравнивание всех трёх матриц. Контракт ядра допускает любое естественное выравнивание f32.

## Компактная плитка выходных сумм, 2026-11-01

Для части AVX-512 GEMM промежуточные суммы теперь хранятся в компактной плитке и записываются в выходную матрицу один раз. Это ограничивает повторные записи в невыровненные границы полос работников. Выбор сохраняет прежние условия wide-кернела и дополнительно требует не более 256 локальных строк, K от 1024 и адрес либо шаг выхода, не кратный 64 байтам. Упаковка весов занимает 32 КиБ, суммы — ещё 64 КиБ. Временный буфер остаётся на стеке выбранной функции; порядок K и добавление bias не меняются.

На 16 физических ядрах Ryzen 9 9950X большой GEMM с выходом +12 байт вырос с **4,064 до 4,292 TFLOPS**. Для 129 токенов и преобразования 1025 → 1057 признаков, выход +4 байта: **2,628 → 3,064 TFLOPS**. Это медианы медиан трёх процессов, по 41 выборке из восьми вызовов. Вариант для всех форм и запись последнего K-блока прямо в выход отклонены из-за регрессов. Дополнительное деление и вызов в промежуточном диспетчере также устранены.

Общего ускорения всех путей нет: отдельный контроль AVX2 GEMM дал **2,224 → 2,208 TFLOPS**; кешируемый AVX-512 GEMV с весами 4 МиБ — **0,864 → 0,850 TFLOPS**. Код арифметики GEMV и пула в этом этапе не менялся; причина этих небольших потерь пока не установлена. Короткие задачи сохраняют заметный разброс процессов. Прошли 188 тестов workspace, 87 release-тестов CPU/executor, Clippy, fmt, Rust 1.89 и независимое ревью. ## Постоянное распределение работы, 2026-11-01

Рабочий движок теперь использует постоянные назначения задач работникам, когда они закреплены на разных физических ядрах. Одни и те же полосы матрицы обрабатываются на тех же ядрах при повторных вызовах. При SMT, неизвестном или свободном размещении остаётся Rayon. Исполнитель владеет одним пулом; общий интерфейс обслуживает и linear, и attention. Число потоков и правила привязки в конфиге сохранены.

Простаивающие работники засыпают. Вызывающая операция выбирает длительность активного ожидания: короткий GEMV избегает лишнего засыпания, attention раньше освобождает ядро. Это общий параметр диспетчера; вычислительные кернелы и описания моделей от него не зависят. Однопоточный `Required` сохранил прямой запуск на закреплённом работнике. Веса остаются в исходном формате, постоянных копий не добавлено.

## Интеграция кернелов и опорный профиль, 2026-11-01

Большой AVX-512 GEMM теперь использует плитку 4×64 с глубиной упаковки 128 и стековым буфером 32 КиБ, выровненным на 64 байта. Этот путь включается при как минимум 128 строках **у одного работника**, ширине его полосы от 64 признаков и подтверждённом размещении работников на разных физических ядрах. Остаток ширины обрабатывает прежний кернел с сохранением полного шага выходной строки. Разбиение распределяет целые плитки между работниками равномерно; узкий выход дополнительно делит токены.

Для однострочного GEMV с весами, превышающими удвоенную суммарную ёмкость выбранных LLC, добавлен последовательный проход по строкам весов с восемью аккумуляторами. Условие также требует не менее восьми работников и восьми полос. Неизвестная ёмкость кеша сохраняет прежний путь. Метаданные читаются при создании исполнителя; повторной упаковки всей модели или дополнительного постоянного хранилища нет. Выбор основан на форме и топологии, без названий моделей и процессоров.

Это задаёт направления следующей работы: уменьшение стоимости распределения коротких задач и упаковки/внутреннего цикла GEMM. Доли CPU-времени не равны долям задержки вызова и не доказывают насыщения FMA или памяти. Аппаратные события `perf` здесь недоступны; clock sampling не измеряет кеш-промахи и причины простоев.

Профили собраны с периодом 2 мс только вокруг измеряемых вызовов. Проверка сырых пакетов подтвердила отсутствие выборок вне этого интервала и точное совпадение CPU-тиков с отчётами. Отдельная серия отклонена: после восстановления файла со старой датой Cargo использовал экспериментальную библиотеку. После принудительной пересборки проверены символы текущего диспетчера. Отчёты и аудит (`../benchmarks/linear-integration-2026-11-01/profiles/audit.json`), разбиение инструкций (`../benchmarks/linear-integration-2026-11-01/ranges.json`), команды воспроизведения (`../benchmarks/linear-integration-2026-11-01/reproduce.txt`).

После пересборки прошли 172 теста workspace и 71 тест release для CPU/executor, Clippy с запретом предупреждений, форматирование и проверка всех целей на Rust 1.89. Журналы (`../benchmarks/linear-integration-2026-11-01/verification/results.json`). Условный FP32-предел для 16 ядер при одновременных 5,7 ГГц — **5,8368 TFLOPS**; это предположение о частоте, а не измеренный устойчивый потолок этой серии. SMT не удваивает число физических вычислительных блоков.

## Сравнение после привязки работников

На том же Ryzen 9 9950X 2026-10-31 сравнивались сохранённый старый бинарник и текущий в режимах `none` и `required`, release/LTO. Каждый случай запускался в трёх отдельных процессах, порядок случаев перемешивался. В таблице — медианы медиан процессов. Все варианты ограничены CPU-масками `0–7`, `0–15` или `0–31`; индивидуальная привязка есть только в `required`. Prefill ниже: 256 × 4096 × 4096, по 51 измерению на процесс.

| ISA / потоки | До, без привязки | Сейчас, без привязки | Сейчас, с привязкой | Изменение к исходному |
| --- | ---: | ---: | ---: | ---: |
| AVX2 / 8 | 1.19 TFLOPS | 1.21 TFLOPS | 1.24 TFLOPS | +4.3% |
| AVX2 / 16 | 1.24 TFLOPS | 1.24 TFLOPS | 2.14 TFLOPS | +72.2% |
| AVX2 / 32 | 2.06 TFLOPS | 1.83 TFLOPS | 1.87 TFLOPS | -9.2% |
| AVX-512 / 8 | 2.22 TFLOPS | 2.16 TFLOPS | 2.24 TFLOPS | +1.3% |
| AVX-512 / 16 | 2.19 TFLOPS | 2.24 TFLOPS | 3.71 TFLOPS | +69.2% |
| AVX-512 / 32 | 2.69 TFLOPS | 2.61 TFLOPS | 3.49 TFLOPS | +29.9% |

На 32 работниках AVX-512 медианы процессов с привязкой лежали в пределах 2,428–2,463 мс, до изменения — 2,849–3,241 мс. На 16 работниках с привязкой диапазон составил 2,293–2,428 мс. Таким образом, 32 потока ускорились относительно прежней реализации, но на этой форме остались примерно на 6% медленнее 16. У AVX2 на 32 потоках улучшения нет, а диапазон с привязкой шире: 4,078–5,993 мс. Поэтому привязка настраивается и не обещает ускорения любой задачи.

Decode (8192 × 8192, AVX-512 / 32) остался около 4,09 мс. На меньших матрицах и attention разброс между запусками заметнее; полный журнал сохраняет эти случаи и выбросы. Частоты, фоновая нагрузка и размещение NUMA-памяти не фиксировались. Checksum совпадают между версиями и политиками при одинаковых ISA, размерах и числе потоков; разные разбиения могут менять округление f32.

Отдельный эксперимент из пяти процессов по 501 измерению сравнил постоянные матричные блоки на работниках с динамическим планировщиком Rayon, при контролируемом выравнивании выхода. Часть случаев AVX-512 ускорилась, AVX2 немного замедлился, а выбросы задержек стали хуже. Постоянное распределение убрано: итоговая реализация меняет размещение работников, сохраняя динамический планировщик и арифметику ядер.

Журнал (`../benchmarks/2026-10-31-threading.txt`), все измерения (`../benchmarks/2026-10-31-threading.json`), скрипт сравнения (`../benchmarks/compare-threading.py`), эксперимент с постоянными блоками (`../benchmarks/2026-10-31-threading-static-experiment.json`). Скрипту нужны сохранённые бинарники до и после изменения; CPU-маски описывают этот компьютер и требуют адаптации на другом железе.

## Проверка гипотез об упаковке GEMM

2026-10-31 на том же Ryzen 9 9950X отдельный диагностический бинарник сравнил семь вариантов AVX-512 GEMM. Процесс работал только на CPU 15 с `nice -n 19`; сборка — `rustc -C opt-level=3`. Измерялось само ядро без `CpuExecutor`. В таблице — медианы девяти замеров после двух прогревов каждого варианта, с перемешиванием порядка вариантов в каждом раунде. Форма: 256 × 4096 × 4096; выход выровнен на 64 байта.

| Вариант | Время ядра, мс |
| --- | ---: |
| Исходная упаковка блоками K=128 | 29,117 |
| Те же блоки, scratch через `MaybeUninit` | 29,135 |
| Сохранённые упакованные веса, блоки K=128 | 28,204 |
| Сохранённые упакованные веса, весь K за проход | 26,325 |
| Упаковка блоками K=1024, без полной копии весов | 28,259 |

Отказ от нулевой инициализации scratch измеримого выигрыша здесь не дал. Сохранённая упаковка с проходом по всему K повысила производительность примерно на 10,6% и сократила время на 9,6%. При смещении выхода на 12 байт время изменилось с 30,047 до 26,307 мс. Однако оба варианта с сохранёнными весами требуют дополнительных 64 МиБ для этой формы. Упаковка в заранее выделенный буфер отдельно заняла 3,69–3,74 мс; сумма её медианы и медианы ядра исключает выделение памяти и не является сквозным замером. Проход по всему K меняет и повторное использование данных, и накладные расходы блоков K, поэтому результат не доказывает одну конкретную причину ускорения.

Увеличение стекового блока без полной копии весов дало неодинаковый результат: на 128 × 2048 × 2048 выигрыш почти отсутствует, на 8 × 512 × 4096 варианты K=256/512/1024 медленнее исходного. Для последнего случая использованы 11 замеров по четыре вызова. Эти результаты одного ядра нельзя переносить на 16/32 потока или сквозной инференс; основной код не изменён.

Все семь вариантов побитово совпали с исходным по всем выходам проверенных матриц. Дополнительно прошли независимый эталон f64 на девяти малых формах с bias и без него и проверку 16 выбранных выходов каждой большой матрицы. Полный журнал, включая отдельные замеры (`../benchmarks/2026-10-31-gemm-hypotheses.txt`), скрипт подготовки эксперимента (`../benchmarks/gemm-hypotheses.py`), измерительный код (`../benchmarks/gemm-hypotheses-main.rs`).

## Продолжение: размер плитки и рабочий буфер GEMM

Следующая серия сравнила 16 вариантов на одном ядре того же Ryzen 9 9950X: CPU 15, `nice -n 19`, отдельный бинарник с `rustc -C opt-level=3`. После двух прогревов использовались семь замеров; повтор большой матрицы — девять, малый случай — девять по четыре вызова. Упаковка включена во время, выделение памяти вынесено за замер; полной копии весов нет. Контроль `heap128_r8` сохраняет исходную плитку 8×32 и K=128, используя переданный буфер вместо стекового.

Хороший баланс скорости и памяти показал `wide4x64_k128`: плитка из четырёх строк и 64 выходных столбцов, K=128, всего 32 КиБ scratch. Общий измерительный код выделял больший буфер для остальных вариантов вне вызовов ядра. Ниже — медианы и прирост пропускной способности относительно исходного ядра; выход выровнен на 64 байта, кроме указанного смещения.

| Форма N × M × K | Исходное ядро, мс | 4×64/K128, мс | Прирост |
| --- | ---: | ---: | ---: |
| 256 × 4096 × 4096 | 29,197 | 27,967 | +4,4% |
| Та же форма, повтор | 29,297 | 28,011 | +4,6% |
| 128 × 2048 × 2048 | 3,754 | 3,585 | +4,7% |
| 64 × 1024 × 8192 | 4,349 | 4,093 | +6,3% |
| 256 × 4096 × 4096, выход +12 байт | 30,208 | 28,515 | +5,9% |

В ассемблере горячий цикл 4×64 содержит 16 FMA, четыре broadcast и четыре загрузки весов — 28 инструкций на шаг K, без spill. Увеличение числа строк до 12/14 не помогло; разворачивание K по два уменьшило число инструкций, но не дало устойчивого ускорения. Компактный буфер частичных сумм дал около 3% на выровненном большом выходе и 6% при смещении. Упаковка всей глубины K требовала 512 КиБ при K=4096 и давала примерно 3–5% на большой матрице, но снижала производительность малого случая примерно на 7%.

На 8 × 512 × 4096 вариант 4×64 был примерно на 1% медленнее `heap128_r8`. Здесь упаковка включалась принудительно; основной код для восьми строк выбирает другой путь. Эти результаты не подтверждают ускорение многопоточного исполнения или сквозного инференса; основной код не изменён.

Все 16 вариантов прошли побитовое сравнение с исходным и независимый эталон f64 на 21 малой форме с bias и без него. Для каждой измеряемой формы проверены все выходы побитово и 16 выбранных значений по f64. Полный отчёт и замеры (`../benchmarks/2026-10-31-gemm-panels.txt`), генератор эксперимента (`../benchmarks/gemm-panels.py`).

## Многопоточный GEMM и профиль времени

Продолжение 2026-10-31 проверило варианты на 16 физических ядрах и 32 SMT-потоках Ryzen 9 9950X. Лучший устойчивый результат основной серии на 16 работниках: **3,746 → 4,016 TFLOPS**, прирост **7,2%**. Это экспериментальное ядро 4×64/K128; в рабочий движок оно пока не перенесено, поскольку на другой форме обнаружен регресс.

Основная задача — 256 токенов, преобразование 4096 входных признаков в 4096 выходных: `X[256,4096] × W[4096,4096]ᵀ → Y[256,4096]`. Числа ниже — медианы медиан трёх отдельных процессов. В каждом процессе было 41 измерение по восемь вызовов, порядок вариантов перемешивался. Упаковка весов, проверка размеров/ISA и работа постоянного пула включены; выделение памяти и проверки правильности вынесены за замер. Работники закреплены индивидуально: CPU 0–15 либо пары 0,16,1,17,…,15,31. Диагностический бинарник собран с `rustc -C opt-level=3 -C codegen-units=1 -C debuginfo=1`, без Cargo LTO.

| Работники и вариант | TFLOPS | Прирост к своему исходному ядру | Доля расчётных 5,8368 TFLOPS |
| --- | ---: | ---: | ---: |
| 16, исходное 8×32/K128 | 3,746 | — | 64,2% |
| 16, 4×64/K128 | 4,016 | +7,2% | 68,8% |
| 32 SMT, исходное 8×32/K128 | 3,478 | — | 59,6% |
| 32 SMT, 4×64/K128 | 3,498 | +0,6% | 59,9% |
| 32 SMT, 4×64/K64 | 3,612 | +3,9% | 61,9% |

Расчётный ориентир для FP32 FMA: `16 ядер × 2 FMA × 16 чисел × 2 операции × 5,7 ГГц = 5,8368 TFLOPS`. Здесь предполагаются **5,7 ГГц на всех ядрах**; это не измеренная частота многопоточной нагрузки. SMT не удваивает физические исполнительные блоки. Основания: [блок-схема Zen 5 от AMD](https://hc2024.hotchips.org/assets/program/conference/day2/24_HC2024.AMD.Cohen.Subramony.final.pdf#page=9) и [характеристики 9950X](https://ir.amd.com/news-events/press-releases/detail/1202/amd-unveils-next-gen-zen-5-ryzen-processors-to-power-advanced-ai-experiences).

Отдельная калибровка независимыми FMA в регистрах дала **5,538 TFLOPS** на 16 закреплённых работниках и **5,521 TFLOPS** на 32. Основной GEMM достигает 72,5% первого измеренного ориентира. `cpuinfo_avg_freq` собирался отдельно, но его показания не синхронизированы с интервалами GEMM и не заменяют точные счётчики частоты. Поэтому они не используются для вычисления «точного процента физического потолка». Семантика этого интерфейса описана в [документации Linux](https://www.kernel.org/doc/html/latest/admin-guide/pm/cpufreq.html).

Границы результата существенны. На 1024 токенах с теми же признаками один процесс дал **3,845 → 4,280 TFLOPS**; это другая задача. На 64 токенах, 8192 → 1024 признака, два сравнения дали **3,213 → 2,979** и **3,203 → 2,921 TFLOPS**: 4×64/K128 медленнее примерно на 7–9%. На основной форме со смещением выхода на 12 байт было **3,616 → 3,921 TFLOPS**. Более мелкие задания, раздельные очереди CCD и упаковка входа перед каждым вызовом устойчивого общего выигрыша не дали. Последняя включала собственную стоимость и дополнительный буфер входа размером 4 МиБ.

Последующее сравнение других вариантов на 32 потоках показало заметный дрейф абсолютных результатов: исходное ядро дало 3,051–3,355 TFLOPS, компактный буфер сумм — 3,230–3,528 TFLOPS, а 4×64/K64 — 3,316–3,436 TFLOPS. Поэтому таблица выше описывает конкретную повторённую серию, а не окончательный выбор ядра для SMT. Температура, частоты и фоновая нагрузка не фиксировались.

### Что показало профилирование

Аппаратные события `perf` недоступны при текущем `perf_event_paranoid=4`. Вместо них использован установленный `gprofng collect app -p 2`: семплирование адресов выполняющихся инструкций, без изменения настроек системы. Пять профилей покрывают весь процесс, включая прогревы и проверки; основная форма выполнялась 101×32 раза, форма с 64 токенами — 101×128. Доли ниже относятся к суммарному **CPU-времени работников**, а не к последовательным отрезкам времени одного GEMM.

| Область кода | Исходное ядро, 256 токенов | 4×64/K128, 256 токенов | Исходное, 64 токена | 4×64/K128, 64 токена |
| --- | ---: | ---: | ---: | ---: |
| Упаковка весов | 8,84% | 10,10% | 18,73% | 19,65% |
| Внутренний цикл K: загрузки, адресация, FMA | 83,61% | 84,47% | 67,72% | 63,27% |
| Повторная загрузка частичных сумм | 4,67% | 1,93% | 2,95% | 8,09% |
| Запись сумм | 0,72% | 0,99% | 0,45% | 0,57% |
| Остальное внутри ядра | 0,66% | 0,70% | 0,63% | 0,66% |
| Вне выбранного ядра | 1,50% | 1,81% | 9,52% | 7,76% |

На большой форме основная работа находится в матричном ядре. Для формы с 64 токенами прирост семплированного CPU-времени нового ядра составил 4,172 с; из них 3,888 с пришлись на область повторных загрузок сумм. Это полезное направление поиска, но не доказательство промахов кеша: профили не измеряют аппаратные причины задержек. Более того, полное время двух процессов под профилировщиком почти совпало — 5,159 и 5,148 с; регресс скорости подтверждают отдельные запуски без профилировщика.

Проверка этого направления дала неоднозначный результат. Уменьшение K до 64/32 ухудшило форму с 64 токенами. Сохранение плитки 8×32 и увеличение K до 1024 дало **2,905 → 3,103** и **2,968 → 3,130 TFLOPS** в двух парных запусках, ценой рабочего буфера 128 КиБ вместо 16 КиБ. Проход по всему K был медленнее. Автоматического выбора на основании этих нескольких форм пока нет.

Доли получены суммированием непересекающихся диапазонов инструкций; их сумма проверена против полного времени функции. Вложенное время Rayon `wait_until_cold` включает выполняемый внутри GEMM и не означает ожидание. Семпл на FMA также не измеряет задержку самой FMA. Заблокированное время потока в эту CPU-выборку не входит.

Все проверенные варианты прошли побитовое сравнение полного выхода с исходным, независимый эталон f64 на 24 малых формах с bias и без него, проверки хвостов строк/столбцов и незатронутых промежутков между выходными полосами. Это проверки диагностического стенда; производственный `linear.rs` в этой серии не менялся.

Артефакты: замеры и команды (`../benchmarks/2026-10-31-gemm-multicore.txt`), генератор (`../benchmarks/gemm-multicore.py`), стенд (`../benchmarks/gemm-multicore-main.rs`), профили (`../benchmarks/2026-10-31-gemm-profile.txt`), разбиение профиля (`../benchmarks/2026-10-31-gemm-profile-breakdown.json`), скрипт проверки диапазонов (`../benchmarks/gemm-profile-ranges.py`), телеметрия частот (`../benchmarks/2026-10-31-gemm-frequency.json`). Инструкции воспроизведения находятся в конце журнала замеров.

## Профиль рабочего executor: GEMM и GEMV

В следующей серии 2026-10-31 профилировался непосредственно `CpuExecutor::linear` из рабочей сборки. Сбор включался только вокруг измеряемых вызовов; выделение памяти, создание пула, прогрев и проверки f64 оставались снаружи. Сохранены бинарный хеш, снимки исходников, отчёты и независимая проверка периода семплирования (`../benchmarks/linear-profile-2026-10-31/sampling-audit.json`).

| Задача | Потоки | Внутри функции кернела | Rayon/Crossbeam и `sched_yield` |
| --- | ---: | ---: | ---: |
| GEMM: 256 токенов, 4096 → 4096 признаков | 16 | 98,63% | 1,14% |
| Та же задача | 32 | 96,72% | 2,99% |
| GEMM: 64 токена, 8192 → 1024 признака | 16 | 87,87% | 11,15% |
| GEMV: один токен, 8192 → 8192, веса 256 МиБ | 16 | 99,49% | 0,45% |
| GEMV: один токен, 1024 → 1024, веса 4 МиБ | 16 | 14,81% | 84,20% |
| Та же задача, вызов на одном закреплённом ядре | 1 | 99,48% | 0% |

Это доли суммарного **exclusive CPU time**, а не доли задержки одного вызова. Функция кернела включает вычисления, упаковку и обращения к памяти. Остаток приходится на другие функции. Аппаратные счётчики по-прежнему недоступны: эти данные не измеряют промахи кэша, простои портов или физический предел памяти.

В большом GEMM внутренний K-цикл занимает 84,73% CPU-выборки процесса, упаковка — 9,32%, загрузки частичных сумм — 3,28%. У задачи с 64 токенами соответствующие доли — 65,14%, 18,77% и 2,69%. Разбиение проверено по непересекающимся диапазонам инструкций: данные (`../benchmarks/linear-profile-2026-10-31/ranges.json`), скрипт (`../benchmarks/linear-profile-ranges.py`).

Для GEMV с весами 4 МиБ отдельно измерена задержка без профилировщика: три процесса на каждое число потоков, по 31 выборке из 1024 вызовов, порядок запусков перемешан. Медианы медиан составили **0,062 / 0,102 / 0,188 / 0,253 / 0,219 / 0,142 TFLOPS** для **1 / 2 / 4 / 8 / 16 / 32** потоков. Поэтому большая доля работы пула не означает, что один поток быстрее; на этой форме лучшими из проверенных оказались восемь. Автоматического выбора числа работников по этим замерам пока нет. Исходные замеры (`../benchmarks/linear-profile-2026-10-31/cached-gemv-threads/manifest.json`).

Проверена и гипотеза лишней адресации GEMM. Вынос адресов восьми входных строк сократил цикл с 37 до 30 инструкций в одном диагностическом бинарнике и дал около 2% в парных замерах. Однако в сборке рабочего движка выигрыш не повторился: основная форма дала 3,842 → 3,821 TFLOPS, а форма с хвостами — 1,666 → 1,587 TFLOPS. Изменение откатили; проверки корректности прошли, но критерий производительности — нет. Сравнение рабочих сборок (`../benchmarks/linear-profile-2026-10-31/addressing-production-comparison.json`).

В установленном GNU gprofng 2.46 обнаружен дефект запуска таймера: главный поток семплировался раз в 100 мс при заявленных 2 мс. Первую серию исключили. Для приведённых результатов использован отдельный диагностический модуль, ограниченный точным build ID профилировщика; системные библиотеки и движок от него не зависят. Повторная проверка подтвердила период 2 мс, отсутствие предупреждений и отсутствие семплов вне измеряемого интервала. Причина дефекта (`../benchmarks/linear-profile-2026-10-31/collector-timer-evidence.txt`), команды воспроизведения (`../benchmarks/linear-profile-2026-10-31/reproduce.txt`).

## Исходные замеры до привязки работников

Исторический результат на Ryzen 9 9950X: замер 2026-10-31, Rust 1.97.1, release с LTO; один поток привязан к CPU 0, 16 работников ограничены CPU 0–15 (по одному логическому CPU каждого физического ядра). Каждый работник внутри маски отдельно не закреплён. Значения ниже — медианы 25 замеров после прогрева. Это не результат текущего размещения по умолчанию; для аналогичного свободного режима укажите `none`.

| Матрица / режим | AVX2, 1 поток | AVX-512, 1 поток | AVX2, 16 потоков | AVX-512, 16 потоков |
| --- | ---: | ---: | ---: | ---: |
| Decode: 1 × 8192 × 8192, 256 МиБ весов | 4,897 мс | 4,835 мс | 3,805 мс | 3,966 мс |
| Эффективная полоса decode | 54,8 ГБ/с | 55,5 ГБ/с | 70,6 ГБ/с | 67,7 ГБ/с |
| Prefill: 128 × 2048 × 2048 | 6,724 мс | 3,675 мс | 0,567 мс | 0,564 мс |
| Производительность prefill | 159,7 GFLOP/s | 292,1 GFLOP/s | 1893,3 GFLOP/s | 1902,3 GFLOP/s |

Скалярный f32-путь на одном потоке дал 25,531 мс для decode и 187,983 мс для prefill. Для этих форм AVX-512 на одном потоке быстрее примерно в 5,3 и 51 раз соответственно. Это сравнение конкретных ядер, не скорости генерации модели.

Калибровка потокового чтения 256 МиБ дала 76,1 ГБ/с для AVX2 на 16 работниках; decode достиг около 93% этого наблюдаемого ориентира. Исходная калибровка AVX-512 FMA в регистрах дала 365,5 GFLOP/s на одном потоке и 2876,0 GFLOP/s на 16 работниках. Последующая индивидуальная привязка работников показала, что второе значение существенно занижало доступную арифметическую производительность. Его нельзя использовать как потолок железа или знаменатель при оценке эффективности. Разные калибровки не являются взаимозаменяемыми потолками.

AVX-512 здесь ускоряет вычислительный prefill на одном ядре, но не выигрывает у AVX2 в многопоточном decode. Автоматически считать самый широкий ISA самым быстрым нельзя. Не следует переносить эти коэффициенты на другой CPU, размер матрицы, холодную память или сквозной инференс.

Полный журнал команд и результатов (`../benchmarks/2026-10-31-cpu.txt`) сохраняет размеры, checksum и число повторений.

## Ограничения

Этот этап покрывает плотные f32-операции. Быстрые LTQ/BF16/INT8-пути, GPU и offload ещё предстоят. Prefill attention пока не использует матричное блочное QK для нескольких запросов. Графовые активации ещё не переиспользуются; оконная история сохраняется целиком, а производные представления истории могут материализоваться целиком.

`MemoryReport` считает тензорные данные. Фиксированные стековые блоки ядер, стеки и служебная память работников в него не входят; их надо учитывать отдельно в общем бюджете процесса. Привязка пока использует Linux sysfs и API планировщика; на других платформах `Auto` сохраняет свободное размещение с диагностикой. Привязка NUMA-памяти ещё не реализована; граф использует подготовленные веса для исключительных потребителей Linear; адаптивное расписание и явный API подготовленных матриц описаны выше. Достижение физического потолка не объявляется на основании одного набора микробенчмарков.
